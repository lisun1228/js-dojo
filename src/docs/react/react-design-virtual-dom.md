## 1.1 谈谈你对 React 的理解 / React 的设计思路

> 原题：**45.**「组件化、虚拟 DOM、单向数据流。」**52.**「声明式、组件化、单向数据流。」
> 两题答案几乎一样，只有三个名词。这是**最容易被判为"背的"**的一种答法。

### 核心原理

React 官方定义只有一句话：**"一个用于构建用户界面的 JavaScript 库"**——注意是 **library**，不是 framework。它只负责视图层（View），路由、状态、请求全部交给生态。

它的设计可以收敛成一个公式和三个决策：

```
UI = f(state)
```

| 决策 | 具体做法 | 解决的问题 |
|---|---|---|
| **声明式** | 你描述"目标状态长什么样"，React 算"从当前到目标要改哪些 DOM" | 不再手写 `createElement/appendChild/removeChild` 的步骤序列，消除"中间态不一致"这一类 bug |
| **组件化** | 组件 = 可组合的、自包含的 UI 单元；数据通过 props 向下流 | 复用靠**组合**而不是继承；状态与视图放在一起，内聚性高 |
| **单向数据流** | props 只读，子组件不能改父状态，只能通过回调上报 | 数据流向可追踪，状态变化有唯一入口，调试时可回溯 |

支撑这三点的运行时机制是三件套：

```
JSX ──编译──▶ ReactElement 树 ──Reconciler──▶ Fiber 树 ──Renderer──▶ 真实 DOM
                                    │
                              Scheduler 排优先级、切时间片
```

- **Reconciler**：算"哪变了"（diff）；
- **Scheduler**：决定"什么时候算、算多久"（并发的基础）；
- **Renderer**：真正落地（`react-dom` / `react-native` / `react-three-fiber`）。

### 答题思路与要点顺序

1. **先给定性**：React 是视图层库，核心公式 `UI = f(state)`。（10 秒，定调）
2. **三个设计决策**：声明式 / 组件化 / 单向数据流，各配一句"解决什么问题"。（30 秒，这是骨架）
3. **往下沉一层**：这三点的实现依赖"虚拟 DOM + 协调 + 调度"。（20 秒，展示你懂原理而不只是口号）
4. **给一个自己的判断**：React 的核心竞争力不是性能，而是"心智模型统一 + 生态最厚 + 跨端能力"。（20 秒，这是加分项）
5. **收尾**：可以补一句 React 18 之后的方向——并发渲染让"更新的优先级"也变成可编程的。

### 口述参考

> 我会从"它解决什么问题"来理解 React。React 官方定位是一个构建 UI 的库，核心思想可以写成一个公式：UI 是 state 的函数。围绕这个公式它做了三个设计决策。第一是声明式，我只需要描述某一刻界面应该长什么样，从当前状态到目标状态要改哪些 DOM，交给 React 去算，这样就不会出现我手写 DOM 操作时那种中间态不一致的 bug。第二是组件化，组件是自包含的单元，复用靠组合而不是继承。第三是单向数据流，props 只读，子组件想改数据只能通过回调通知父级，所以数据流向永远可追踪。
>
> 往下一层看，这三点是靠虚拟 DOM、协调器和调度器实现的：JSX 编译成 ReactElement 树，协调器做 diff 算出最小变更，渲染器落到真实 DOM，而调度器负责什么时候算、算多久，这也是 React 18 并发渲染的基础。
>
> 我个人对 React 的判断是，它的核心竞争力其实不是性能，而是这套心智模型足够统一，加上生态和跨端能力——同一套组件模型可以跑在 Web、Native 和小程序上。

### 常见追问

| 追问 | 应答要点 |
|---|---|
| React 是框架还是库？ | 官方定位是库，只管视图层。正因为不管路由/状态/请求，才长出 Redux、React Router 这套生态；代价是"选型成本"落到团队身上 |
| 声明式到底"声明"了什么？ | 声明的是"状态 → UI"的映射关系，不是"操作步骤"。副作用（请求、订阅、DOM 操作）需要靠 useEffect 这类"逃生舱"显式声明 |
| 单向数据流是绝对的么？ | 不是。子改父靠回调，跨层级靠 Context；Context 本质还是"向下流"，只是跳过了中间层。真正双向绑定只有受控组件那一层（value + onChange 来回） |
| React 的"不可变"指什么？ | 指 state 更新要产生新引用（`{...state, a: 1}`），因为 React 靠引用比较判断"变没变"，这也是 memo/PureComponent 能生效的前提 |

### 加分点与易错点

- ✅ **加分**：主动区分"库/框架"；能提到 Scheduler 的存在；能说出"React 的价值是可预测性，不是绝对性能"。
- ⚠️ **易错**：只背"组件化、虚拟 DOM、单向数据流"三个词，不解释各自解决什么问题——这是最典型的"背题"信号。
- ⚠️ **易错**：把"单向数据流"说成"数据只能单向流动，所以不能双向绑定"。受控组件就是双向的，只是实现方式是"state → value → onChange → setState"的闭环。

## 1.2 虚拟 DOM 是什么？React 为什么要用它？

> 原题：**1.**、**47.**、**57.** 三题同义，答案都是「用 JS 对象描述 UI，状态变化先 diff，最小化真实 DOM 操作。好处：性能优化、跨平台。」

### 原答案的问题

这句话**技术上不算错，但埋了一个雷**：它暗示"虚拟 DOM 比真实 DOM 快"。这是前端面试最经典的反问陷阱——面试官下一句往往是「那虚拟 DOM 一定比直接操作 DOM 快吗？」

正确答案是：**不一定。**

| 对比对象 | 谁快 | 原因 |
|---|---|---|
| 虚拟 DOM vs **全量重渲染**（innerHTML 重刷） | 虚拟 DOM 快 | 只更新差异部分，避免整树重建与样式重算 |
| 虚拟 DOM vs **手写最优 DOM 操作** | 手写快 | 虚拟 DOM 多了"建树 + diff"的 CPU 开销，且无法利用业务先验知识跳过比较 |

所以虚拟 DOM 的真实价值排序是：**声明式抽象 > 跨平台 > 性能兜底**。React 团队自己也说过，virtual DOM 的主要收益是 "declarative, composition, 和心理模型的简化"，性能只是"保证下限"。

### 核心原理

**它是什么**：一个用普通 JS 对象描述 UI 的树。JSX 编译后得到的 `ReactElement` 长这样：

```js
// <div id="a">hi</div>
{
  $$typeof: Symbol(react.element), // 防 XSS：从服务端 JSON 注入的元素不会被当成 React 元素
  type: 'div',
  key: null,
  ref: null,
  props: { id: 'a', children: 'hi' },
}
```

**完整链路**：

```
① 编写     JSX
② 编译     Babel / SWC：React 17 之前 → React.createElement()；17 之后 → jsx() from react/jsx-runtime（自动引入，无需 import React）
③ 生成     ReactElement 树（不可变的普通对象）
④ 转换     Reconciler：ReactElement → Fiber 树（可变、可中断的工作单元）
⑤ 比较     diff：新旧 Fiber 树对比，标记 flags（Placement / Update / Deletion）
⑥ 提交     commit：一次性把变更打到真实 DOM
```

**为什么要这一层**（四条理由，按重要性排）：

1. **声明式**：开发者只描述结果，`f(state)` 负责算过程。没有这层中间表示，"算出最小变更"这件事就得开发者自己干。
2. **跨平台**：协调逻辑与宿主环境解耦。同一棵树可以交给 `react-dom`（DOM）、`react-native`（原生 View）、`react-pdf`、`react-three-fiber`（WebGL）。
3. **性能兜底**：diff 让"更新成本"与"UI 规模"解耦，避免"改一个字段重刷整个列表"。它保证的是**下限**，不是上限。
4. **可编程性**：树是可序列化的对象，所以能做 SSR、时间旅行调试、快照测试、React DevTools 的组件树。

### 答题思路与要点顺序

1. **给定义**：JS 对象的 UI 描述，是"代码"和"真实 DOM"之间的中间层。（15 秒）
2. **讲链路**：JSX → ReactElement → Fiber → diff → commit → DOM。（30 秒，展示你不是只会定义）
3. **讲动机**：声明式、跨平台、性能兜底、可编程性。（30 秒，四条里重点讲前两条）
4. **主动纠偏**：「顺便说一句，虚拟 DOM 不是一定比原生操作快……」。（15 秒，**这一句是最强的加分项**）
5. **可选下沉**：ReactElement 是"不可变的描述"，Fiber 是"可变的、可中断的工作单元"，两者别混为一谈。

### 口述参考

> 虚拟 DOM 是用 JS 对象描述 UI 的一棵树，它是 React 代码和真实 DOM 之间的中间层。链路是：我写 JSX，编译成 ReactElement 对象树；协调器把它转成 Fiber 树，用 diff 对比新旧两棵树，标记出哪些节点要新增、更新、删除；最后 commit 阶段一次性把变更打到真实 DOM 上。
>
> 为什么要这一层，我觉得主要是三点。第一是声明式，我描述结果，算差异这件事由框架做，如果没有中间表示，那"算出最小变更"就得我自己写。第二是跨平台，协调逻辑和宿主环境解耦了，同一份组件可以渲染成 DOM、原生 View 或者 WebGL。第三才是性能，它是兜底——保证我不会因为改一个字段就把整个列表重刷。
>
> 这里我想补充一点，虚拟 DOM 并不一定比直接操作 DOM 快。它比全量重渲染快，但比手写的最优 DOM 操作慢，因为多了建树和 diff 的 CPU 开销。所以它的核心价值是抽象能力和可维护性，性能是保证下限。

### 常见追问

| 追问 | 应答要点 |
|---|---|
| 虚拟 DOM 一定比真实 DOM 快吗？ | 不一定（见上表）。分对手：快于全量重渲染，慢于手写最优更新。框架卖的是"下限"和"可维护性" |
| ReactElement 和 Fiber 什么关系？ | Element 是"不可变的描述"（每次渲染都新建）；Fiber 是"可变的、带指针的工作单元"，能在中断后恢复。Element 是输入，Fiber 是运行时状态载体 |
| diff 复杂度为什么是 O(n)？ | 因为做了三个假设（同层比较、类型不同直接替换、key 标识），放弃了树的最小编辑距离（那是 O(n³)），见 [02 册 2.3](/doc/react-rendering-fiber-diff) |
| 为什么 `$$typeof` 用 Symbol？ | 防止 XSS：服务端返回的 JSON 里伪造 `{type:'div', props:{dangerouslySetInnerHTML}}` 不会被当成 React 元素渲染 |
| JSX 是模板引擎吗？ | 不是，是 `createElement` 的语法糖，编译期就变成函数调用，运行时没有模板解析开销。这也是它比模板字符串更灵活（可以写表达式）的原因 |
| 不用虚拟 DOM 行不行？ | 行，Svelte 编译期生成精确 DOM 操作，Vue 3 用编译期 patchFlag 减少运行时比较。取舍是：编译时优化依赖静态分析，动态性强的场景仍需要运行时比较 |

### 加分点与易错点

- ✅ **加分**：主动区分 ReactElement / Fiber；说出 `$$typeof` 的 XSS 用途；对比 Svelte 的编译时路线。
- ⚠️ **易错**：说"虚拟 DOM 是 JS 对象，所以操作 JS 对象比操作 DOM 快"——**这是双重错误**：一是建树本身有成本，二是 DOM 操作慢指的是"读写布局属性引发重排"，不是"所有 DOM 操作都慢"。
- ⚠️ **易错**：说"虚拟 DOM 只更新变化的节点"——准确说是"只更新 diff 判定需要变更的节点"，diff 本身也有成本。

## 1.3 函数组件和类组件有什么区别？

> 原题：**17.**「函数组件：简洁、Hooks、无 this。class 组件：生命周期、this。现在推荐函数组件。」
> **49.**「同第 17 题。」

原答案是对的，但太"表面"。这题真正在考的是：**你理解不理解"每次渲染都是一个快照"这个心智模型**——这是函数组件最容易出事的地方，也是最容易讲出深度的地方。

### 核心原理

| 维度 | 类组件 | 函数组件 |
|---|---|---|
| **心智模型** | 一个**实例**，有 `this`，状态挂在实例上，生命周期方法在"时间轴"上被调用 | 一次**函数调用**，每次渲染都是一个独立的闭包快照，状态由 React 在 fiber 上托管 |
| **状态载体** | `this.state`（可变对象） | `useState` 返回的 `[value, setter]`（value 是常量快照） |
| **副作用组织** | 按生命周期分散：`componentDidMount` 里塞请求、订阅、埋点 | 按**关注点**聚合：多个 `useEffect`，一个 effect 一件事 |
| **逻辑复用** | HOC / render props（造成嵌套与"props 来源不明"） | 自定义 Hook（普通函数调用，无嵌套） |
| **this 问题** | 需要 `bind` 或用箭头函数属性 | 没有 this |
| **能力盲区** | 全部能力 | 不能直接做 ErrorBoundary（`componentDidCatch` / `getDerivedStateFromError` 只有 class 有）、没有 `getSnapshotBeforeUpdate` |
| **压缩/调试** | 方法名是字符串，难以压缩；热更新易失效 | 无方法名，易压缩；Hooks 顺序调换会在 lint 层报错 |
| **性能** | 有实例创建开销（可忽略） | 每次渲染重建闭包（可忽略，真正成本在子组件渲染） |

**最关键的一条**：

> 类组件里 `this.state` 指向**最新的值**；函数组件里 `state` 是**那次渲染的快照**。

```js
function Counter() {
  const [count, setCount] = useState(0);

  const handle = () => {
    setTimeout(() => {
      // 这里的 count 永远是这个闭包创建时那一次的值
      alert(count); // 点 5 次，3 秒后弹出的是点击瞬间的值，不是 5
    }, 3000);
  };
}
```

这就是"stale closure（闭包陷阱）"，是函数组件最容易出的 bug，也是面试官区分"用过"和"懂"的分水岭。

### 答题思路与要点顺序

1. **一句话定性**：类是"实例 + 生命周期"，函数是"每次渲染一个快照"。（10 秒）
2. **能力对比**：Hooks 已经覆盖了 class 的几乎全部能力，只有 ErrorBoundary 和 getSnapshotBeforeUpdate 还留在 class。（20 秒，显示你知道边界）
3. **写法与复用**：副作用按关注点聚合 vs 按生命周期分散；自定义 Hook vs HOC/render props。（25 秒，这是 React 团队推荐函数组件的核心理由）
4. **坑**：stale closure 与 this 绑定的对比。（25 秒，这是深度分）
5. **结论**：新代码用函数组件，class 只用于 ErrorBoundary 与维护老代码。

### 口述参考

> 我会从心智模型上区分。类组件是一个实例，状态挂在 this 上，生命周期方法沿着时间轴被调用；函数组件是一次函数调用，每次渲染都是一个独立的闭包快照，状态其实托管在 fiber 上。
>
> 这个差别带来两个后果。第一是副作用的组织方式，类组件里一个 componentDidMount 往往塞了请求、订阅、埋点，相关逻辑被拆到不同生命周期里；函数组件用一个 effect 一件事，按关注点聚合，逻辑复用也从 HOC 的嵌套变成了自定义 Hook 的普通函数调用。
>
> 第二是坑不一样。类组件的坑是 this 绑定；函数组件的坑是闭包，useState 拿到的是那次渲染的快照，不是最新值，setTimeout 里读到的就是旧的，这也是为什么经常要用函数式更新或者 ref 来绕过。
>
> 能力上 Hooks 基本追平了，只有 ErrorBoundary 和 getSnapshotBeforeUpdate 还必须在 class 里写。所以新代码我会用函数组件，class 只用来写错误边界或者维护老项目。

### 常见追问

| 追问 | 应答要点 |
|---|---|
| 函数组件每次渲染都重新创建函数，性能差吗？ | 函数创建成本极低（纳秒级），真正的成本是**子组件重渲染**。所以优化点是 `memo` / `useCallback`，而不是"避免函数重建" |
| Hooks 能完全替代 class 吗？ | 不能。ErrorBoundary（`componentDidCatch`）、`getSnapshotBeforeUpdate`（滚动位置）仍需要 class；老代码也没必要重写 |
| 为什么 React 团队推荐函数组件？ | ① 逻辑复用更自然 ② 副作用按关注点聚合 ③ 对机器友好（易压缩、易做编译期优化，React Compiler 只面向函数组件）④ 避免 this 与生命周期带来的心智负担 |
| 函数组件的 state 存在哪？ | 不在闭包里，在 `fiber.memoizedState` 的 hook 链表上。闭包只是"读到"了那次渲染的值，见 [04 册 4.3](/doc/react-hooks-principles) |
| 怎么解决 stale closure？ | ① 函数式更新 `setX(v => v + 1)` ② 把值放进依赖数组 ③ 用 `useRef` 存最新值 ④ `useEffectEvent`（实验性）/ 自定义 `useLatest` |

### 加分点与易错点

- ✅ **加分**：能说出"闭包快照"并给出 setTimeout 的具体例子；能说出 class 仍有不可替代的场景（ErrorBoundary）。
- ⚠️ **易错**：说"函数组件没有生命周期"——它有，只是用 `useEffect` 表达，且语义是"同步外部系统"而不是"在某个时刻执行"。
- ⚠️ **易错**：说"类组件性能更好/更差"——这个层面没有意义，差异量级远小于一次多余的子组件渲染。

## 1.4 React 和 Vue 有什么区别？

> 原题：**74.**「React：JSX、灵活、生态大。Vue：模板、约定、上手快。」**78.**「同第 74 题。」

这类题**最忌讳站队**。正确姿势是：**给维度、讲取舍、不下优劣结论**。下面按"面试官最认的五个维度"组织。

### 核心原理（五个维度）

| 维度 | React | Vue |
|---|---|---|
| **视图描述** | JSX：JS 的完整表达力，本质是 `createElement` 调用 | SFC 模板：受限的 DSL，编译期可静态分析；也支持 JSX |
| **更新触发** | **显式**：`setState` / `dispatch`，靠**不可变 + 引用比较**判断变化 | **隐式**：Proxy 拦截读写，**自动依赖收集**，改了就更新 |
| **diff 策略** | 纯**运行时** diff（同层 + key，O(n)） | **编译时 + 运行时**：`patchFlag`、静态提升、Block Tree，跳过静态节点 |
| **逻辑复用** | Hooks（函数式）；HOC / render props（历史方案） | Composables（`useXxx`，本质相同）；mixin（已废弃） |
| **生态形态** | 只做视图层，路由/状态/请求由社区提供（React Router、Redux/Zustand、TanStack Query） | 官方全家桶（vue-router、pinia），约定统一，选型成本低 |
| **学习曲线** | 入门需要理解 JSX + 不可变 + Hooks 规则；进阶到并发/Fiber 很深 | 模板直观、API 收敛，上手快；进阶到响应式系统也很深 |
| **跨端** | React Native（成熟）、react-three-fiber、小程序（Taro） | uni-app、Weex（已边缘化） |

### 一个最能体现深度的对比：**"怎么知道数据变了"**

```
React：setState(newObj) → 引用变了 → 标记 fiber 需要更新 → 重新执行组件函数 → diff 出变更
       （如果原地改 obj.a，引用没变 → memo/SCU 认为没变 → 不更新，这就是"必须不可变"的原因）

Vue：  state.a = 1 → Proxy 的 set 拦截 → 触发依赖 → 精确通知用到 a 的渲染 effect
       （粒度是"属性级"，不需要 diff 全树，也不需要手动不可变）
```

- React 的路线：**把"变更检测"成本转移给开发者（不可变 + 显式 set）**，运行时更简单、更可预测。
- Vue 的路线：**把"变更检测"成本转移给框架（Proxy + 依赖收集）**，开发体验更顺，但对代理不友好的场景（大数据量、频繁创建对象）有额外开销。

### 答题思路与要点顺序

1. **先定框架**：不说谁好，说"两者解决同一问题的不同取舍"。（10 秒）
2. **按维度铺开**：视图描述 / 更新机制 / diff 策略 / 生态形态，每维度一句话对比。（45 秒）
3. **挑一个维度讲深**：选"变更检测"，讲不可变 vs 响应式，落到"所以 React 里必须返回新对象"。（30 秒，这是深度分）
4. **给适用场景**：团队小、要快、要统一约定 → Vue；要跨端、要极强灵活性、招人市场大 → React。（15 秒）
5. **收尾**：两者在互相靠拢——Vue 3 有了组合式 API，React 有了 React Compiler 做编译期优化。

### 口述参考

> 我不太会比较谁更好，我觉得是两个不同取舍。可以从几个维度看。
>
> 视图描述上，React 用 JSX，本质是 JS，表达力完整；Vue 用模板，是受限的 DSL，换来编译期能静态分析。更新机制是最大的差别：React 是显式的，setState 之后靠不可变的引用比较判断变没变；Vue 是隐式的，Proxy 拦截读写，自动做依赖收集。所以 React 里必须返回新对象，原地改属性是不生效的，这是很多 Vue 转 React 的人踩的第一个坑。
>
> diff 上，React 是纯运行时的同层比较加 key；Vue 3 在编译期就打好了 patchFlag，静态节点能提升或者跳过，运行时要做的比较更少。
>
> 生态上，React 只做视图层，路由状态请求都得自己选，自由但选型成本在团队；Vue 是官方全家桶，约定统一，上手快。
>
> 所以我的判断是：要跨端、要极强灵活性、看重招人市场，选 React；团队小、要快、要统一约定，选 Vue。而且两者在互相靠拢，Vue 3 有了组合式 API，React 也在用 Compiler 做编译期优化。

### 常见追问

| 追问 | 应答要点 |
|---|---|
| 为什么 React 必须不可变，Vue 不用？ | React 靠引用比较（`===`）判断"要不要更新"，原地修改引用不变 → 被判为无变化；Vue 靠 Proxy 拦截，赋值就触发。代价是 React 每次更新要复制对象，Vue 要维护代理与依赖表 |
| Vue 的响应式比 React 性能好吗？ | 更新粒度更细（属性级），但 React 18 的并发与时间切片在"长任务不阻塞交互"上更强。场景不同，不能一概而论 |
| React 的 diff 比 Vue 慢吗？ | 单次 diff 通常 Vue 更快（静态节点被编译期跳过）；但 React 的瓶颈通常在"组件函数重执行"而不是 diff 本身 |
| 你会怎么选型？ | 给判断依据：跨端需求、团队背景、生态成熟度、招聘难度、是否已有设计系统。避免只说"我更喜欢 X" |
| Vue 的 mixin 和 React 的 HOC 有什么共同问题？ | 都是"隐式注入"：数据来源不透明、命名冲突、嵌套层级深。这也是两边都转向组合式 API / Hooks 的原因 |

### 加分点与易错点

- ✅ **加分**：用"变更检测"这条主线串起两者差异；指出两者在互相靠拢；能给出**选型决策依据**而不是偏好。
- ⚠️ **易错**：说"React 更适大项目"——这是无根据的断言，Vue 一样能撑大项目，真正的差异在"团队约定成本"和"生态可选性"。
- ⚠️ **易错**：说"Vue 是双向绑定，React 是单向"——Vue 默认也是单向数据流（props 向下），`v-model` 只是语法糖。

## 本册自测

1. 用一句话说清「虚拟 DOM 比直接操作 DOM 快」这句话错在哪。
2. Fiber 和 ReactElement 的本质区别是什么？为什么需要两个东西？
3. 函数组件里 `setTimeout` 读到旧 state，根因是什么？三种解法各是什么？
4. 如果面试官说"Vue 的响应式比 React 先进"，你怎么接？
5. `$$typeof: Symbol(react.element)` 是干什么用的？去掉会有什么安全问题？
6. 面试官问"React 是框架吗"，你从哪三个角度回答？

<details>
<summary>自测参考答案要点</summary>

1. 它只快于"全量重渲染"，慢于"手写最优更新"；虚拟 DOM 的真实价值是声明式抽象与跨平台，性能只是保证下限。
2. Element 是不可变的描述（每次渲染新建），Fiber 是可变的、带 `return/child/sibling` 指针的工作单元，能被中断后恢复；前者是输入，后者是运行时状态载体（含 hooks 链表、优先级、副作用标记）。
3. 闭包快照：函数组件每次渲染生成独立闭包，读的是那一次的值。解法：函数式更新、把值放进依赖、用 ref 存最新值。
4. 不站队：Vue 的更新粒度更细（属性级 + 编译期跳过静态节点），React 的并发能力在"长任务不阻塞交互"上更强；两者解决的是不同层面的问题。
5. 防止 XSS：服务端 JSON 伪造的"React 元素"不会被当元素渲染。
6. 官方定位是 library；只管视图层，路由/状态/请求交给生态；跨端靠 Renderer 抽象，不是框架级全家桶。
</details>
