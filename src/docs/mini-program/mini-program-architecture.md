## 一、先背这段 30 秒结论

- **双线程**：逻辑层 AppService 跑在 JSCore，负责 JS 执行、业务逻辑与数据处理；渲染层跑在 WebView，负责 WXML/WXSS 解析与视图渲染。
- **隔离**：两层不共享内存、不能直接调用，所有交互经微信客户端（Native）中转。
- **数据驱动**：视图更新统一走 `setData`，逻辑层序列化数据，Native 转发，渲染层反序列化后执行数据更新算法。
- **取舍**：换来安全隔离、跨端一致与渲染可控，代价是跨线程通信开销。

## 二、双线程到底怎么分工

| 维度 | 逻辑层 AppService | 渲染层 WebView |
| --- | --- | --- |
| 运行环境 | iOS：JavaScriptCore；Android：V8 / JSCore；开发者工具：Chromium 内核 | iOS：WKWebView；Android：XWeb（原 X5） |
| 实例数量 | **全局一个**，所有页面共用 | **每个页面一个 WebView** |
| 职责 | 执行 JS、发请求、处理事件回调、维护 `data`、调用 `setData` | 解析 WXML/WXSS、生成节点、绑定事件、布局与绘制 |
| 能拿到 | `wx.*`、`App/Page/Component`、`getApp()` | 基础库注入的渲染逻辑，业务代码不进入 |
| 拿不到 | `window` / `document` / DOM API | 不能直接执行业务 JS |

补充约束：

1. 逻辑层单例，页面共享同一 JS 运行时；全局变量、定时器、事件监听需在 `onUnload` 自行清理，否则内存泄漏或串页。
2. 渲染层每个页面一个 WebView 实例，页面栈上限 10 层，超出用 `redirectTo` 替换或 `reLaunch` 重开。
3. 两层物理隔离，只能传可序列化数据（JSON 能表达的值），函数、DOM 节点、实例不能过桥。

## 三、setData 全链路（架构题的最高频追问）

```js
// 只传路径 + 变化的值
this.setData({ 'list[0].name': 'Tom' });
```

链路：

```
逻辑层 setData（路径 + 值）
  → JSON 序列化
  → Native 桥（iOS：WKWebView messageHandlers；Android：evaluateJavascript / JSBridge）
  → 渲染层反序列化
  → 数据更新算法（diff）
  → 更新视图
```

关键结论：

- 跨线程只能传 JSON 可表达的数据，函数、DOM 节点、实例无法传递。
- **文档规定**：单次 `setData` 的数据不超过 1024KB；性能评分另要求 `JSON.stringify` 后不超过 256KB、每秒调用不超过 20 次。
- 性能因素：官方文档给出两项——组件 Shadow 树总节点量、本次更新的数据量，前者影响更大。

优化手段：

| 手段 | 说明 |
| --- | --- |
| 只传变化路径 | `this.setData({ 'obj.name': v })`，不要 `setData(this.data)` |
| 减小数据体积 | 不往 `data` 塞列表全量、图片 base64、长文本 |
| 合并调用 | 同一轮的连续变更合并成一次 `setData`（组合更新），减少通信次数 |
| 避开高频场景 | `onPageScroll`、`touchmove` 中不 `setData` |
| WXS 响应事件 | WXS 在渲染层执行，事件处理不经逻辑层，适合高频交互 |
| 纯数据字段 | `options: { pureDataPattern: /^_/ }`，`_` 开头的字段不进 `data`、不参与通信 |
| 控制节点与动画 | 长列表用 `recycle-view` 或虚拟列表；复杂动画用 CSS 或 Skyline worklet |

## 四、为什么拿不到 DOM API

分三层：

**环境层**：逻辑层跑 JSCore，只提供 ECMAScript 标准能力，没有浏览器宿主环境，`window`、`document`、`localStorage`、`XMLHttpRequest` 都不存在。`wx.request`、`wx.setStorage` 是微信注入的 Native 能力。

**设计层**：渲染层有 DOM，但微信不向逻辑层暴露引用：

- **安全**：小程序代码来自第三方，能操作 DOM 就能注入脚本、读取敏感信息、绕过平台管控。
- **可控**：更新入口收敛到 `setData`，平台才能统一做 diff、渲染调度、性能监控与错误拦截。
- **跨端**：WKWebView、XWeb、Skyline 的节点模型不同，业务只面对「数据 + 模板」，才能一套代码多端运行并允许替换渲染引擎。

**开发层**：用数据间接操作视图，正规路径有三条：

- 改数据 → `setData` → 视图更新（主流）
- `wx.createSelectorQuery()` 查询尺寸/位置，只读
- Canvas 2D、Animation API、`wx.createIntersectionObserver` 处理绘制、动画与曝光

小程序把命令式 DOM 操作换成了声明式数据驱动，牺牲灵活性换安全与跨端一致。

## 五、小程序原理：从代码到界面

按编译期 → 启动期 → 运行期：

**1. 编译期（开发者工具）**

- `WXML` → 编译成生成虚拟节点树的 JS 函数（不是 HTML 字符串直出）
- `WXSS` → 编译成普通 CSS，`rpx` 运行时按屏幕宽度换算
- `JS` → 语法转换、ES6+ 兼容、按页面/分包拆 bundle
- `JSON` → 页面配置、窗口配置、组件声明

**2. 启动期**

- 客户端下载代码包（有缓存，二次启动走本地包）→ 校验 → 注入逻辑层
- 逻辑层执行 `app.js` 的 `onLaunch` → 渲染层初始化第一个 WebView → 加载基础库 → 首页 `onLoad/onShow/onReady`
- 冷启动 vs 热启动：热启动（后台 5 分钟内再次打开）省去包加载与初始化

**3. 运行期**

- 渲染层用基础库把 WXML 虚拟节点映射成自定义节点（WebView 渲染下如 `wx-view`），再由浏览器引擎布局绘制
- 逻辑层负责全部 JS
- 用户点击 → 渲染层捕获事件 → 经 Native 序列化后送到逻辑层 → 回调执行 → 可能 `setData` → 回到渲染层更新
- 点击并触发 `setData` 至少跨两次线程通信（事件上行 + 数据下行）

**Skyline**：用自绘渲染替代 WebView，渲染在独立线程，支持 worklet 动画、更好的手势与长列表性能，通过 `app.json` 的 `"renderer": "skyline"` 开启；兼容性与组件/样式支持有差异。

## 六、面试话术（可直接背的口语版）

- **架构**：逻辑层 JSCore 单例管算，渲染层 WebView 每页一个管画，两层经 Native 中转，不能直接调用。
- **setData**：逻辑层序列化 → Native 转发 → 渲染层反序列化 → diff → 更新视图；成本来自数据拷贝、通信与数据更新算法。
- **无 DOM**：JSCore 无浏览器宿主，平台又故意不暴露 DOM 引用，以保证安全、可控与跨端。
- **优化**：减少 `setData` 的数据量、频次与 Shadow 树节点量，高频交互交给渲染层能力。

## 七、追问预判（附答法）

| 追问 | 答法 |
| --- | --- |
| 为什么不把逻辑与渲染放一个线程？ | 放一起就退化成普通 H5，JS 长任务会阻塞渲染；分开后逻辑层死循环不阻塞渲染绘制，但会阻塞事件回调 |
| 逻辑层单例，多页面怎么隔离？ | 页面栈隔离页面实例，JS 运行时共享；全局变量、定时器、监听在 `onUnload` 清理 |
| 能直接改样式吗？ | 通过 `setData` 改 `class`/`style`，本质仍是数据驱动；`SelectorQuery` 只能读位置与尺寸 |
| 冷启动怎么优化？ | 分包 + 分包预下载、`lazyCodeLoading: requiredComponents`、控制主包体积、减少同步 API、骨架屏 |
| Skyline 和 WebView 渲染的区别？ | WebView 把 WXML 映射成 WebView 中的 DOM 节点；Skyline 自绘渲染、独立渲染线程、worklet 动画；代价是兼容性与组件/样式支持差异 |

## 八、易错点 & 加分点

**易错：**

- 把小程序当 H5：它是 WebView + Native 的混合体，H5 只是渲染层的一部分。
- 把「两层由 2 个线程管理」简化成「一逻辑线程 + 一渲染线程」：渲染层每个页面一个 WebView，部分平台多个 WebView 共享线程。
- 认为 `setData` 是增量更新所以快：它传的是你指定的那部分数据，渲染层再执行数据更新算法。

**加分点：**

- 官方能力：Skyline 自绘渲染、`lazyCodeLoading`、分包预下载。

## 九、一分钟速记卡

```
双线程：逻辑层 JSCore（单例，管算） + 渲染层 WebView（每页一个，管画）
通信：  Native 桥，只能传可序列化数据
setData：序列化 → 跨线程 → 反序列化 → diff → 更新视图
性能：  Shadow 树节点量 > 数据量；文档规定单次数据 ≤ 1024KB
无 DOM：JSCore 无宿主 + 故意沙箱 + 跨端统一 → 只能数据驱动
原理：  WXML→虚拟节点函数，WXSS→CSS，JS→逻辑层，运行时映射成自定义节点
优化：  少传、传路径、少频次、纯数据字段、虚拟列表、WXS、CSS 动画
```
