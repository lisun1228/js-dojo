# 小程序 · 01 架构与双线程模型

> **本篇合并原题：** 1. 说说微信小程序的架构？ / 2. 为什么小程序里拿不到 DOM 相关的 API？ / 3. 小程序的双线程分别做的什么事情？ / 4. 简述微信小程序原理？
>
> **为什么合并：** 这四问的答案内核是同一个「双线程模型 + 通信桥」，只是入口不同——问架构要讲分层，问双线程要讲分工，问原理要讲编译与运行，问 DOM 要讲设计取舍。面试时你只要把这一套讲透，四问通吃。
>
> **出现频率：** 极高。小程序岗位基本第一问就是它。

---

## 一、先背这段 30 秒结论

> 微信小程序是**双线程架构**：**逻辑层（AppService）跑在 JSCore 里**，负责 JS 执行、业务逻辑、数据处理；**渲染层跑在 WebView 里**，负责 WXML/WXSS 的解析和视图渲染。**两层不共享内存，也不能直接调用**，所有交互都靠微信客户端（Native）做中间人转发消息，最典型的就是 `setData`——逻辑层把数据序列化后经 Native 送到渲染层，渲染层再 diff 更新视图。
>
> 所以小程序本质上是「**一个被关在沙箱里、只能数据驱动视图的 WebView，外加一层 Native 能力**」。这套设计换来的是安全隔离、跨端一致和可控的性能，代价是**跨线程通信的开销**——这正是小程序性能优化的核心战场。

这段话说完，架构题已经及格了。下面是被追问时的展开。

---

## 二、双线程到底怎么分工

| 维度 | 逻辑层 AppService | 渲染层 WebView |
| --- | --- | --- |
| 运行环境 | iOS：JavaScriptCore；Android：V8 / JSCore；开发者工具：Chromium 内核 | iOS：WKWebView；Android：XWeb（原 X5） |
| 实例数量 | **全局只有一个**，所有页面共用 | **每个页面一个**，页面栈里有几个页面就有几个 WebView |
| 职责 | 执行 JS、发请求、处理事件回调、维护 `data`、调用 `setData` | 解析 WXML/WXSS、生成真实 DOM、绑定事件、执行渲染 |
| 能拿到什么 | `wx.*` API、`App/Page/Component`、`getApp()` | 只能拿到基础库注入的渲染逻辑，业务代码进不来 |
| 拿不到什么 | `window` / `document` / DOM API | 不能直接执行你的业务 JS |

关键点，面试时一定要主动说出来：

1. **逻辑层是单例的**，页面之间共享同一个 JS 运行时，所以页面数据天然容易互相污染（这也是 `globalData` 好用又危险的原因）。
2. **渲染层是多实例的**，页面栈上限 10 层，超过就用 `redirectTo`。
3. **两层物理隔离**，不是同一个进程、不是同一个线程，甚至不是同一种 JS 引擎，因此**只能传可序列化的数据**（JSON 能表达的东西），不能传函数、不能传 DOM 节点、不能传实例。

### 通信链路长什么样

```
逻辑层(this.setData)
   ↓  序列化数据（JSON 化）
Native 桥（WeixinJSBridge：iOS 走 WKWebView messageHandlers，Android 走 evaluateJavascript / JSBridge）
   ↓  反序列化
渲染层（基础库 WAWebview）
   ↓  diff 新旧数据，算出最小更新路径
真实 DOM 更新 / 视图重排
```

一次 `setData` 要经历 **两次序列化 + 一次跨线程转发 + 一次 diff**，这是它比直接操作 DOM 慢的根因。所以官方的说法是：**`setData` 的耗时和传输的数据量成正比**，而不是和页面节点数成正比。

## 三、setData 全链路（架构题的最高频追问）

```js
// 逻辑层
this.setData({ 'list[0].name': 'Tom' })   // 只传路径 + 变化的值
```

四个阶段：

1. **收集差异**：用 `data` 路径语法（`'a.b[0].c'`）可以只传变化的字段，没传的保持原值。
2. **序列化传输**：对象转成 JSON 字符串，经 Native 桥送到渲染层。
3. **渲染层 diff**：基础库把新数据与旧数据比对，生成更新指令，只改受影响的节点。
4. **视图更新**：改真实 DOM 属性 / 触发重排重绘。

**优化手段（能答出这几条，分数直接上一个档）：**

| 手段 | 说明 |
| --- | --- |
| 只传变化路径 | `this.setData({'obj.name': v})` 而非整个 `obj` |
| 减小数据体积 | 不要往 `data` 里塞列表全量数据、图片 base64、长文本 |
| 合并调用 | 同一轮里多次 `setData` 合并成一次，减少通信次数 |
| 避开高频场景 | `onPageScroll`、`touchmove` 里不 `setData`，用 WXS 或纯数据字段 |
| 纯数据字段 | `options: { pureDataPattern: /^_/ }`，`_` 开头的字段不进 `data`、不参与通信 |
| 长列表 | 用 `recycle-view` 或虚拟列表，只渲染可视区 |
| 复杂动画 | 用 CSS 动画 / WXS 响应事件 / Skyline worklet，绕开逻辑层 |

## 四、为什么拿不到 DOM API

这题不能只答「因为不在浏览器里」，那是现象不是原因。分三层讲：

**第一层：环境上就真的没有。**
逻辑层跑的是 JSCore，它是一个纯 JS 引擎，只提供 ECMAScript 标准能力，**没有浏览器宿主环境**，所以 `window`、`document`、`localStorage`、`XMLHttpRequest` 全都不存在。你能用的 `wx.request`、`wx.setStorage`，是微信注入的 Native 能力，不是浏览器 API。

**第二层：设计上故意不给。**
就算渲染层里明明有 DOM，微信也不把引用暴露给逻辑层：

- **安全**：小程序代码来自第三方，如果能操作 DOM，就能注入脚本、读取页面敏感信息、绕过平台管控。沙箱化的前提就是「代码碰不到视图」。
- **可控**：所有更新必须经过 `setData`，平台才能统一做 diff、做渲染调度、做性能监控和错误拦截。
- **跨端**：iOS 的 WKWebView、Android 的 XWeb、以及 Skyline 渲染引擎，底层节点模型都不一样。业务代码只面对「数据 + 模板」，才能一套代码跑多端、并且允许平台随时换渲染引擎（Skyline 就是这么平滑升级的）。

**第三层：那开发者怎么"操作 DOM"？**
答案是**用数据间接操作**，三条正规路径：

- 改数据 → `setData` → 视图跟着变（主流）
- 需要拿到节点信息 → `wx.createSelectorQuery()` 查询尺寸/位置，这是**只读**的
- 需要动 Canvas / 动画 → `Canvas 2D` 接口、`Animation` API、WXS 事件响应、`wx.createIntersectionObserver` 做曝光

一句话收尾：**"小程序把命令式的 DOM 操作换成了声明式的数据驱动，牺牲灵活性换安全和跨端。"**

## 五、小程序原理：从代码到界面

面试问"原理"时，按**编译期 → 启动期 → 运行期**三段讲，比零散罗列有说服力。

**1. 编译期（开发者工具做的）**
- `WXML` → 编译成**生成虚拟节点树的 JS 函数**（不是 HTML 字符串直出，这也是它和模板引擎的区别）
- `WXSS` → 编译成普通 CSS，`rpx` 在运行时按屏幕宽度换算
- `JS` → 语法转换、`ES6+` 兼容处理、按页面/分包拆 bundle
- `JSON` → 页面配置、窗口配置、组件声明

**2. 启动期（用户点开时）**
- 微信客户端下载代码包（有缓存，二次启动走本地包）→ 校验 → 注入逻辑层
- 逻辑层执行 `app.js` 的 `onLaunch` → 渲染层初始化第一个 WebView → 加载基础库 → 首页 `onLoad/onShow/onReady`
- 冷启动 vs 热启动：热启动（5 分钟内被后台回收前再次打开）省掉包加载和初始化，明显更快

**3. 运行期**
- 渲染层用基础库把 WXML 的虚拟节点映射成真实 DOM。注意：**`<view>` 最终就是 `<div>`**，`<text>` 就是 `<span>`，所以小程序 UI 本质还是网页渲染
- 逻辑层负责一切 JS
- 用户点击 → 渲染层捕获事件 → 经 Native 把事件对象序列化后送到逻辑层 → 你的回调执行 → 你可能 `setData` → 回到渲染层更新
- 注意这条回路：**一次点击交互至少要跨两次线程**，所以小程序"点击响应"天然比原生和 H5 多一层开销

> 加分补充：2023 年后微信推出了 **Skyline 渲染引擎**，用自绘渲染替代 WebView，把部分渲染逻辑搬到独立线程，支持 worklet 动画、更好的手势和长列表性能，在 `app.json` 里 `"renderer": "skyline"` 开启。答题时提一句"新架构在收敛这个通信瓶颈"，会显得你跟进过技术演进。

## 六、面试话术（可直接背的口语版）

**问「说说小程序的架构」：**

> 小程序是双线程模型。逻辑层也就是 AppService，跑在 JSCore 里，所有 JS 逻辑、请求、事件回调都在这里执行，全局只有一个；渲染层是 WebView，一个页面一个，负责 WXML 和 WXSS 的渲染。两层不共享内存，靠微信客户端做桥来传消息，`setData` 就是走这条路：逻辑层序列化数据，Native 转发，渲染层 diff 后更新 DOM。
>
> 这么设计的核心原因是安全——小程序跑的是第三方代码，不能让它碰 DOM；顺带也解决了跨端一致性和渲染可控性的问题。代价就是通信开销，所以小程序性能优化基本都围绕"减少 setData 的数据量和频次"来做。

**问「为什么没有 DOM API」：**

> 两个层面。环境层面，逻辑层是 JSCore，只有 JS 引擎没有浏览器宿主，`window`、`document` 压根不存在。设计层面，就算渲染层有 DOM，微信也故意不暴露——一旦能操作 DOM，就能注入脚本、绕过平台管控，沙箱就失效了；而且平台要统一做 diff 和渲染调度，就必须把更新入口收敛到 `setData` 一个口子上。
>
> 实际开发里需要"操作 DOM"的场景，一般用 `createSelectorQuery` 查节点信息，用 Canvas 2D 或 WXS 处理动画，其余全部走数据驱动。

**问「双线程分别做什么」：**

> 逻辑层管"算"，渲染层管"画"。逻辑层执行 JS、维护 data、调接口、跑生命周期；渲染层拿 WXML 模板和 data 生成真实节点、绑事件、做布局和绘制。中间靠 Native 桥做序列化转发，所以传的只能是可 JSON 化的数据，函数和实例过不去。

## 七、追问预判（附答法）

**Q：为什么不把逻辑和渲染放一个线程，像浏览器那样？**
A：放一起就退化成普通 H5 了，JS 长任务会直接卡住渲染。分开之后逻辑层的死循环或长计算不会阻塞渲染层绘制（但会阻塞事件回调），这是小程序"看起来比 H5 稳"的原因之一。

**Q：逻辑层只有一个，多个页面怎么互不影响？**
A：靠页面栈隔离页面实例，但 JS 运行时是共享的，所以全局变量、定时器、事件监听必须自己在 `onUnload` 里清理，否则会出现内存泄漏和串页问题。这也是为什么大项目要用 MobX / 状态管理来约束数据流。

**Q：setData 为什么慢？慢在哪一步？**
A：慢在**跨线程 + 序列化**，不在 diff。数据量越大，序列化和传输越久，超过 1MB 官方会直接告警。所以"减少数据量"比"减少 diff"更有效。

**Q：小程序能直接改样式吗？**
A：可以通过 `setData` 改 `class` 或 `style` 字符串，本质还是数据驱动；也可以 `wx.createSelectorQuery().select().boundingClientRect()` 读位置，但改还是得回到数据。

**Q：小程序页面栈有几层？超了怎么办？**
A：最多 10 层。超了用 `redirectTo` 替换当前页，或 `reLaunch` 重开，避免栈溢出。

**Q：冷启动为什么慢，怎么优化？**
A：慢在代码包下载 + 注入 + 首屏渲染这条链。优化手段：分包 + 分包预下载、`lazyCodeLoading: requiredComponents` 按需注入、控制主包体积、首屏减少同步 API、用骨架屏兜住白屏时间。

**Q：Skyline 和 WebView 渲染的区别？**
A：WebView 是把 WXML 映射成浏览器 DOM 来渲染；Skyline 是自绘渲染引擎，不依赖 WebView，渲染在独立线程，动画可以跑 worklet 不经过逻辑层，长列表和手势更顺。代价是兼容性和部分组件/样式支持有差异。

## 八、易错点 & 加分点

**易错：**
- 说"逻辑层和渲染层是两个线程"——更准确说是**两个运行环境/两个进程内的独立执行环境**，逻辑层内部还有自己的线程池。
- 说"小程序是 H5"——它是 WebView + Native 的混合体，H5 只是渲染层的一部分。
- 说"每个页面有自己的 JS 环境"——错，逻辑层是单例。
- 说"setData 是增量更新所以很快"——`setData` 本身是全量传你给的那部分数据，diff 是渲染层做的，快慢取决于你传多少。

**加分：**
- 主动点出「通信开销是性能优化的靶心」，并给 2～3 条具体手段。
- 提到 Skyline、`lazyCodeLoading`、分包预下载这些较新的官方能力。
- 用一句话点出设计哲学：**"用表达力换安全性和一致性"**。

## 九、一分钟速记卡

```
双线程：逻辑层 JSCore（单例，管算） + 渲染层 WebView（每页一个，管画）
通信：  Native 桥，只能传可序列化数据
setData：序列化 → 跨线程 → diff → 更新 DOM，成本 ∝ 数据量
无 DOM：JSCore 无宿主 + 故意沙箱 + 跨端统一 → 只能数据驱动
原理：  WXML→虚拟节点函数，WXSS→CSS，JS→逻辑层，运行时映射成真实 DOM
优化：  少传、传路径、少频次、纯数据字段、虚拟列表、绕开逻辑层做动画
```
