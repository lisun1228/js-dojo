# 算法 · 03 进阶排序：归并 / 快排 / 堆排

> 本册覆盖：归并排序、快速排序、堆排序
> 这三个是 **O(n log n) 三巨头**，是排序题里唯一值得「背到能默写」的部分。
> 面试出现频率：**快排 > 归并 > 堆排**，但堆排因为「顺带考堆 / TopK」经常被追问。

---

## 3.1 归并排序

### 一句话结论

**分治**：把数组一分为二，分别排好序，再 `merge` 成有序数组。**稳定、O(n log n) 恒定（没有最坏退化）、需要 O(n) 额外空间**。是「要稳定」「链表排序」「外部排序」「求逆序对」的首选。

### 3.1.1 核心思想

```
                [5, 3, 8, 1, 9, 2]
                 /            \
        [5, 3, 8]              [1, 9, 2]
         /     \                /     \
      [5]     [3, 8]         [1]    [9, 2]
               /  \                   /  \
             [3]  [8]               [9]  [2]
        ↓ 自底向上合并 ↓
        [3, 5, 8]              [1, 2, 9]
                 \            /
                [1, 2, 3, 5, 8, 9]
```

**两个阶段**：
1. **分（divide）**：递归到长度 ≤ 1（天然有序）
2. **治（conquer）**：合并两个有序数组

**关键点**：归并排序的「排序工作」全部发生在 **merge 阶段**，递归本身不排序。这和快排正好相反（快排在 partition 阶段就把大小关系分好了）。

### 3.1.2 实现（递归版）

```js
function mergeSort(arr) {
  if (arr.length <= 1) return arr;              // 递归出口
  const mid = arr.length >> 1;                  // 等价于 Math.floor(len / 2)
  const left = mergeSort(arr.slice(0, mid));    // ⚠️ slice 产生 O(n) 拷贝
  const right = mergeSort(arr.slice(mid));
  return merge(left, right);
}

function merge(a, b) {
  const res = new Array(a.length + b.length);
  let i = 0, j = 0, k = 0;
  while (i < a.length && j < b.length) {
    // ★ 用 <= 而不是 <，这是稳定性的唯一来源
    if (a[i] <= b[j]) res[k++] = a[i++];
    else res[k++] = b[j++];
  }
  while (i < a.length) res[k++] = a[i++];
  while (j < b.length) res[k++] = b[j++];
  return res;
}
```

### 3.1.3 逐步推演 `[5, 3, 8, 1]`

```
分：
  [5,3,8,1] → [5,3] + [8,1]
  [5,3]     → [5] + [3]
  [8,1]     → [8] + [1]

治（合并）：
  merge([5],[3])       → 5<=3? 否 → 取 3，再取 5     → [3,5]
  merge([8],[1])       → 8<=1? 否 → 取 1，再取 8     → [1,8]
  merge([3,5],[1,8]):
     3<=1? 否 → 取 1     res=[1]   i=0 j=1
     3<=8? 是 → 取 3     res=[1,3] i=1 j=1
     5<=8? 是 → 取 5     res=[1,3,5] i=2（左耗尽）
     补右剩余 → 取 8      res=[1,3,5,8]
```

### 3.1.4 稳定性：只差一个等号

这是本题单**漏掉的关键点**。

```js
if (a[i] <= b[j]) res[k++] = a[i++];   // ✅ 稳定：相等时优先取左边
if (a[i] <  b[j]) res[k++] = a[i++];   // ❌ 不稳定：相等时取右边，左元素被"插队"
```

**为什么 `<=` 就稳定？**

`left` 和 `right` 来自原数组的前后两半。如果 `a[i] === b[j]`，`a[i]` 在原数组中的位置更靠前。取 `a[i]` 就保住了「前面的先出」，相对顺序不变。

**反例**（用 `<`）：`[2a, 2b]` 分成 `[2a]` 和 `[2b]`，`2a < 2b` 为 false → 取 `2b` → `[2b, 2a]`，顺序反了。

**实测验证**（用 `{v, i}` 标记原下标）：

```js
// 输入: [{v:1,i:0}, {v:1,i:1}, {v:0,i:2}]
// 用 <=  → 结果下标 [2, 0, 1]   ✅ 稳定（两个 v=1 保持 0 在 1 前）
// 用 <   → 结果下标 [2, 1, 0]   ❌ 不稳定（1 跑到了 0 前面）
```

> 面试话术：「归并的稳定性完全取决于 merge 里的比较用的是 `<=` 还是 `<`。用 `<=` 时相等元素优先取左边，而左边来自原数组的前半部分，所以相对顺序不变。」

**如果排序的是对象**，把比较换成：

```js
if (cmp(a[i], b[j]) <= 0) res[k++] = a[i++];
else res[k++] = b[j++];
```

⚠️ **注意**：`a[i] <= b[j]` 对两个对象会先 `ToPrimitive` 成 `"[object Object]"`，比较结果恒为「相等」，代码能跑但排序结果完全错误。**排对象必须传比较器**，这是很隐蔽的 bug。

### 3.1.5 复杂度分析：为什么恒为 O(n log n)

**递归树法**：

```
第 0 层：1 个节点，处理 n 个元素  → 代价 n
第 1 层：2 个节点，各 n/2        → 总代价 n
第 2 层：4 个节点，各 n/4        → 总代价 n
...
第 log₂n 层：n 个节点，各 1      → 总代价 n
```

**每层总代价都是 O(n)，共 log₂n + 1 层 → O(n log n)。**

关键：**无论输入是否有序，递归树形状都一样**（永远是均分），所以**最好、平均、最坏都是 O(n log n)**。这是归并相对于快排的最大优势——**没有最坏退化**。

**空间**：`merge` 里 `new Array(a.length + b.length)`，每层总共要 n 的空间，但同时存活的只有「从根到叶这条路径上的 merge 结果」，峰值约 **O(n)**（用 slice 版每一层都新建数组，实际常数更大，但仍是 O(n)）。

> 注意：递归栈深度是 O(log n)，辅助数组是 O(n)，**总空间取大的 → O(n)**。

### 3.1.6 优化：不用 slice 的原地版

`slice` 版每层都新建数组，虽然总空间仍是 O(n)，但**分配次数多、GC 压力大**，实际比「一次性分配 temp 数组」慢。

```js
function mergeSortInPlace(arr) {
  const n = arr.length;
  const tmp = new Array(n);          // 只分配一次
  sort(0, n - 1);
  return arr;

  function sort(lo, hi) {
    if (lo >= hi) return;
    const mid = (lo + hi) >> 1;
    sort(lo, mid);
    sort(mid + 1, hi);
    mergeRange(lo, mid, hi);
  }

  function mergeRange(lo, mid, hi) {
    let i = lo, j = mid + 1, k = lo;
    while (i <= mid && j <= hi) {
      if (arr[i] <= arr[j]) tmp[k++] = arr[i++];
      else tmp[k++] = arr[j++];
    }
    while (i <= mid) tmp[k++] = arr[i++];
    while (j <= hi) tmp[k++] = arr[j++];
    for (let t = lo; t <= hi; t++) arr[t] = tmp[t];   // 回写
  }
}
```

**这个版本的空间是严格的 O(n) + O(log n) 栈**，且只有 1 次数组分配。

### 3.1.7 优化：自底向上（非递归）

消除递归调用，用「宽度倍增」的方式合并。**面试如果要求「不用递归写归并」，就是这个**。

```js
function mergeSortBottomUp(arr) {
  const n = arr.length;
  if (n <= 1) return arr.slice();
  const a = arr.slice();
  const tmp = new Array(n);

  for (let width = 1; width < n; width *= 2) {      // 1, 2, 4, 8...
    for (let lo = 0; lo < n - width; lo += width * 2) {
      const mid = lo + width - 1;
      const hi = Math.min(lo + width * 2 - 1, n - 1);
      let i = lo, j = mid + 1, k = lo;
      while (i <= mid && j <= hi) tmp[k++] = a[i] <= a[j] ? a[i++] : a[j++];
      while (i <= mid) tmp[k++] = a[i++];
      while (j <= hi) tmp[k++] = a[j++];
      for (let t = lo; t <= hi; t++) a[t] = tmp[t];
    }
  }
  return a;
}
```

**注意外层条件是 `lo < n - width`**：必须保证右半部分至少有一个元素（`mid + 1 <= hi`），否则没得合并。写成 `lo < n` 会导致 `mid` 越界。

**自底向上的优势**：没有递归开销；**天然适合链表**（链表排序的标准做法就是自底向上归并）。

### 3.1.8 归并排序的四个真实用途

这是「为什么要学归并」的答案，比会写代码更重要。

**① 需要稳定排序时**

`Array.prototype.sort` 在 ES2019 之后**规范要求稳定**，V8 因此把快排换成了 TimSort（归并 + 插入的混合）。如果你的场景依赖稳定（多级排序），归并是唯一选择（在 O(n log n) 家族里）。

**② 链表排序**

链表没有随机访问，快排的 partition 需要随机访问，堆排需要下标计算——**只有归并能优雅地用在链表上**（合并链表只需改指针，不需要额外空间）。

```js
function sortList(head) {
  if (!head || !head.next) return head;
  // 快慢指针找中点（fast 从 head.next 开始，保证偶数长度时 slow 停在左中点）
  let slow = head, fast = head.next;
  while (fast && fast.next) { slow = slow.next; fast = fast.next.next; }
  const mid = slow.next;
  slow.next = null;                       // 断开
  return mergeList(sortList(head), sortList(mid));
}

function mergeList(a, b) {
  const dummy = { next: null };
  let tail = dummy;
  while (a && b) {
    if (a.val <= b.val) { tail.next = a; a = a.next; }   // <= 保证稳定
    else { tail.next = b; b = b.next; }
    tail = tail.next;
  }
  tail.next = a || b;                     // 接上剩余部分
  return dummy.next;
}
```

**链表归并的空间是 O(log n)**（只有递归栈），这是它比数组归并更优雅的地方。

**③ 求逆序对**

归并的 merge 过程天然能数出逆序对。**这是「归并排序」最高频的算法题变体**（剑指 Offer 51、LeetCode 493）。

```js
function countInversions(arr) {
  let count = 0;
  const a = arr.slice();
  const tmp = new Array(a.length);

  function sort(lo, hi) {
    if (lo >= hi) return;
    const mid = (lo + hi) >> 1;
    sort(lo, mid);
    sort(mid + 1, hi);

    let i = lo, j = mid + 1, k = lo;
    while (i <= mid && j <= hi) {
      if (a[i] <= a[j]) {
        tmp[k++] = a[i++];
      } else {
        tmp[k++] = a[j++];
        count += mid - i + 1;    // ★ a[i..mid] 全部 > a[j]，都是逆序对
      }
    }
    while (i <= mid) tmp[k++] = a[i++];
    while (j <= hi) tmp[k++] = a[j++];
    for (let t = lo; t <= hi; t++) a[t] = tmp[t];
  }

  sort(0, a.length - 1);
  return count;
}
```

**`count += mid - i + 1` 的含义**：`a[i..mid]` 是左半部分剩下的元素，它们都 ≥ `a[i]`；既然 `a[i] > a[j]`，那么 `a[i..mid]` 全部 > `a[j]`，一共 `mid - i + 1` 个逆序对。

**④ 外部排序（数据量超过内存）**

大文件排序的标准方案：
1. 分块读入内存，每块内部排序后写回磁盘（得到若干有序小文件）
2. **多路归并**：用最小堆从 k 个有序文件里取最小值，边读边写

这就是数据库 `ORDER BY`、`sort` 命令、MapReduce 的底层逻辑。

### 3.1.9 常见坑

| 坑 | 后果 | 修正 |
|---|---|---|
| `merge` 用 `<` 而非 `<=` | **不稳定** | 用 `<=` |
| 递归出口写 `length === 1` | 空数组无限递归 | `length <= 1` |
| `mid = (lo + hi) / 2` 未取整 | 下标是小数，报错 | `>> 1` 或 `Math.floor` |
| 自底向上外层 `lo < n` | `mid` 越界 | `lo < n - width` |
| `merge` 只写 while，忘了补尾部 | 结果缺元素 | 两个 while 补齐 |
| 以为空间是 O(log n) | 错，是 O(n) | 辅助数组 O(n) 主导 |
| 在链表上用数组版归并 | 需要随机访问，性能极差 | 用 mergeList 版 |

### 3.1.10 答题模板

**30 秒版**

> 归并排序是分治：数组一分为二，递归排好左右两半，再合并两个有序数组。合并时用双指针，谁小取谁。
> 时间是恒定的 O(n log n)，没有最坏退化；空间 O(n) 需要辅助数组；**稳定**，稳定性来自 merge 里的 `<=`——相等时优先取左边。
> 它的典型用途是「需要稳定」「链表排序」「外部排序」「求逆序对」。

**2 分钟版（加分层）**

> 归并排序的工作全部发生在合并阶段，递归本身不排序，这一点和快排相反——快排是在分区阶段就把大小关系定下来了。
> 实现上分三块：递归出口是长度 ≤ 1；取中点分成两半；merge 用双指针把两个有序数组合并到一个新数组。
> 复杂度上，递归树每一层的总代价都是 n，共 log n 层，所以是 O(n log n)，而且因为永远均分，**最好、平均、最坏都一样**，这是它相对快排的最大优势。空间是 O(n)，因为 merge 要辅助数组；如果用 slice 版，每层都新建数组，常数会更大，所以工程里通常一次性分配一个 temp 数组。
> 稳定性是本题的重点：必须用 `a[i] <= b[j]`，相等时优先取左边。因为左边来自原数组的前半部分，这样相对顺序才能保住。如果写成 `<`，相等时会取右边，左元素被插队，稳定性就破了。
> 工程上它的价值在四个场景：要稳定排序（V8 的 TimSort 本质就是归并 + 插入）、链表排序（改指针即可，空间只要 O(log n) 栈）、求逆序对（merge 时 `count += mid - i + 1`）、外部排序（分块排序 + 多路归并）。

### 3.1.11 追问表

| 追问 | 回答要点 |
|---|---|
| 归并的空间复杂度？ | O(n)，辅助数组主导；链表版是 O(log n) |
| 归并稳定吗？为什么？ | 稳定，merge 用 `<=`，相等优先取左 |
| 归并有没有最坏退化？ | 没有，永远均分，恒定 O(n log n) |

| 自底向上归并怎么保证边界？ | 外层 `lo < n - width`，保证右半至少一个元素 |

## 3.2 快速排序

### 一句话结论

**选一个基准 pivot，把数组分成「小于 pivot」和「大于 pivot」两部分，再递归两边。原地、不稳定、平均 O(n log n)、最坏 O(n²)。** 实测是所有通用排序里最快的（常数小、缓存友好），所以是工业界默认选择。

### 3.2.1 原题答案的三个问题（必须先纠正）

原题单给的实现：

```js
function quickSort(arr) {
  if (arr.length <= 1) return arr;
  const pivot = arr[0];
  const left = [], right = [];
  for (let i = 1; i < arr.length; i++) {
    arr[i] < pivot ? left.push(arr[i]) : right.push(arr[i]);
  }
  return [...quickSort(left), pivot, ...quickSort(right)];
}
```

**这个写法能跑通，但作为面试答案有三个扣分点**：

| 问题 | 说明 |
|---|---|
| ① **空间不是 O(log n)** | 每层都 `left`/`right` 新数组 + `[...]` 拼接，**空间是 O(n)**，不是题单写的 O(log n) |
| ② **固定取 `arr[0]` 作 pivot** | 已排序 / 完全逆序输入时，每次分区都退化成 1 : n-1，**深度 n，时间 O(n²)** |
| ③ **没处理重复元素** | 全相同数组下，`left` 为空、`right` 有 n-1 个，同样退化 O(n²) |

**这三条恰恰是面试官最想听的分析**。所以正确策略是：**先写这个「易懂版」讲清思路，再主动指出它的三个问题，然后给出工业版**。这个递进过程本身就是加分项。

### 3.2.2 分区（partition）：快排的唯一难点

快排的所有复杂度分析都围绕 partition。两种主流写法：

#### Lomuto 分区（好懂，面试常用）

思路：把 pivot 换到末尾，用 `i` 维护「小于区的下一个位置」，`j` 扫描。

```js
function partitionLomuto(arr, lo, hi) {
  // 随机化：随机选一个换到末尾，避免固定 pivot 的退化
  const r = lo + Math.floor(Math.random() * (hi - lo + 1));
  [arr[r], arr[hi]] = [arr[hi], arr[r]];

  const pivot = arr[hi];
  let i = lo;                        // i 左边都是 < pivot
  for (let j = lo; j < hi; j++) {
    if (arr[j] < pivot) {
      [arr[i], arr[j]] = [arr[j], arr[i]];
      i++;
    }
  }
  [arr[i], arr[hi]] = [arr[hi], arr[i]];   // pivot 归位
  return i;                                 // pivot 的最终下标
}
```

**手算** `[3, 8, 2, 5, 1]`，假设随机选中 `value = 5`（原 index 3），先换到末尾：

```
换到末尾后: [3, 8, 2, 1, 5]   pivot = 5

i=0
  j=0: 3 < 5 → swap(a[0], a[0])，i=1      [3, 8, 2, 1, 5]
  j=1: 8 < 5? 否                          [3, 8, 2, 1, 5]
  j=2: 2 < 5 → swap(a[1], a[2])，i=2      [3, 2, 8, 1, 5]
  j=3: 1 < 5 → swap(a[2], a[3])，i=3      [3, 2, 1, 8, 5]
最后 swap(a[3], a[4]) → [3, 2, 1, 5, 8]，返回 3
```

分区结果：`[3, 2, 1] | 5 | [8]`。pivot 落在 index 3，左右分别递归。

**再看一个退化例子**：`[3, 8, 2, 5, 1]` 若 pivot 取末尾的 `1`：

```
i=0
  j=0: 3 < 1? 否
  j=1: 8 < 1? 否
  j=2: 2 < 1? 否
  j=3: 5 < 1? 否
最后 swap(a[0], a[4]) → [1, 8, 2, 5, 3]，返回 0
```

分区结果：`[1] | [8, 2, 5, 3]` —— **1 : n-1 的极端不均衡**，右边还要递归 n-2 层。这正是「固定取末尾作 pivot + 输入恰好是逆序/有序」时退化成 O(n²) 的机制。

**⚠️ 一个重要的行为**：Lomuto 用 `arr[j] < pivot`（严格小于）时，**所有等于 pivot 的元素会被分到右边**。如果数组全相同，`i` 一直是 `lo`，分区结果是 `[lo] | [lo+1, hi]`，每次只缩小 1 个 → **O(n²)**。

> 这就是为什么「全相同数组」是快排的杀手输入之一，解决方案是**三路快排**。

#### Hoare 分区（更快，但边界难写对）

思路：双指针从两端向中间逼近，左边找 ≥ pivot 的，右边找 ≤ pivot 的，交换。

```js
function partitionHoare(arr, lo, hi) {
  const pivot = arr[lo + ((hi - lo) >> 1)];   // 取中间值作 pivot（不用换位置）
  let i = lo - 1, j = hi + 1;
  while (true) {
    do { i++; } while (arr[i] < pivot);
    do { j--; } while (arr[j] > pivot);
    if (i >= j) return j;                      // ★ 返回 j，不是 i
    [arr[i], arr[j]] = [arr[j], arr[i]];
  }
}
```

**三个必须记住的细节**：
1. **返回 `j`**，递归时用 `[lo, j]` 和 `[j+1, hi]`（不是 `j-1` / `j+1`）
2. **`do-while` 而非 `while`**：保证至少走一步，否则 pivot 本身会让循环卡住
3. **不需要哨兵**：因为 pivot 一定在区间内，`i` 和 `j` 不会越界

**Hoare 的优势**：交换次数约为 Lomuto 的 1/3，且**全相同数组下仍然均分**（`i` 和 `j` 会在中间相遇）→ 不会退化。

> 面试如果只写 Lomuto，被问「全相同数组怎么办」就答三路快排；如果写 Hoare，可以直接说「Hoare 分区对重复元素天然友好」。两种都能过，但**要能说清差异**。

### 3.2.3 完整实现（随机化 + 递归短边优化）

```js
function quickSort(arr, lo = 0, hi = arr.length - 1) {
  while (lo < hi) {
    const p = partitionLomuto(arr, lo, hi);
    // ★ 先递归较短的一侧，较长的一侧用循环继续（尾递归优化的手动版）
    //   这样栈深最坏是 O(log n) 而不是 O(n)
    if (p - lo < hi - p) {
      quickSort(arr, lo, p - 1);
      lo = p + 1;
    } else {
      quickSort(arr, p + 1, hi);
      hi = p - 1;
    }
  }
  return arr;
}
```

**这个技巧值得单独讲**：即使 pivot 每次都恰好是最小值（最坏分区），因为**每次都只递归较短的一侧（长度 0）**，较长的一侧用 `while` 循环继续，**栈深度始终是 O(log n)**。时间仍是 O(n²)，但**不会栈溢出**。

> 业界实现（如 `std::sort`）就是这么做的：`__introsort_loop` 里 `while (last - first > threshold)`，递归短的一边。

### 3.2.4 三路快排（解决重复元素）

把数组分成三段：`< pivot`、`== pivot`、`> pivot`。等于 pivot 的部分**不用再递归**。

```js
function quickSort3Way(arr, lo = 0, hi = arr.length - 1) {
  if (lo >= hi) return arr;

  const r = lo + Math.floor(Math.random() * (hi - lo + 1));
  [arr[lo], arr[r]] = [arr[r], arr[lo]];
  const pivot = arr[lo];

  let lt = lo;        // [lo, lt)     < pivot
  let i = lo + 1;     // [lt, i)      == pivot
  let gt = hi;        // (gt, hi]     > pivot

  while (i <= gt) {
    if (arr[i] < pivot) {
      [arr[lt], arr[i]] = [arr[i], arr[lt]];
      lt++; i++;
    } else if (arr[i] > pivot) {
      [arr[i], arr[gt]] = [arr[gt], arr[i]];
      gt--;                    // ⚠️ 不 i++，换过来的元素还没检查
    } else {
      i++;
    }
  }

  quickSort3Way(arr, lo, lt - 1);
  quickSort3Way(arr, gt + 1, hi);
  return arr;
}
```

**`gt--` 之后不能 `i++`** 是最高频的 off-by-one 错误——换过来的元素来自未检查区，必须重新判断。

**效果**：全相同数组 → 一次分区就结束，**O(n)**。这是「大量重复 key」场景（比如按状态排序、按省份排序）的关键优化。

**实测对比**（Node 22 / Apple Silicon，随机化 pivot，单位 ms）：

| 输入 | Lomuto 单路 | Hoare | 三路（3-way） |
|---|---|---|---|
| 已排序 10 万个 | 9.2 | **3.6** | 24.8 |
| 全相同 2 万个 | **212** ⚠️ | 3.0 | **0.3** |
| 全相同 10 万个 | **5362** ❌ | 3.0 | **0.2** |

**这张表说明三件事**：

1. **随机化之后，「已排序输入」不再是问题**——10 万个有序数据只要 9.2ms，和随机输入差不多。
2. **「全相同」才是 Lomuto 的死穴**——`arr[j] < pivot` 是严格小于，等于 pivot 的元素全被推到右边，每次只缩小 1 个元素 → O(n²)。从 2 万到 10 万（5 倍数据），耗时涨了 **25 倍**（212ms → 5362ms），完全符合平方增长。
3. **三路快排不是万能的**——它在重复元素上极快（0.2ms），但在「全部不重复的有序数据」上反而比 Lomuto 慢 2.7 倍（24.8ms vs 9.2ms），因为每次分区多做了两路交换。**所以真实实现往往是「检测到重复多才走三路」，或者干脆用 Hoare + 相等检测跳过。**

> Hoare 在三组测试里都是最快或接近最快，这也是为什么工业级实现（`std::sort`、`qsort`）多用 Hoare 变体而不是 Lomuto。Lomuto 的价值是**好写好讲**。

### 3.2.5 复杂度分析

| 情况 | 时间 | 触发条件 |
|---|---|---|
| **最好** | O(n log n) | 每次都均分 |
| **平均** | O(n log n) | 随机输入 |
| **最坏** | **O(n²)** | 每次分区都极不均衡（1 : n-1） |

**最坏情况什么时候发生？**

1. **固定取首/尾元素作 pivot，且输入已排序或逆序**
   ```
   [1,2,3,4,5]，pivot = 1（末尾）→ 分区结果 [] | [2,3,4,5]
   下一层 pivot = 5 → [] | [2,3,4]
   每层只减少 1 个元素 → 深度 n → 总代价 n + (n-1) + ... + 1 = O(n²)
   ```

2. **所有元素相同**（Lomuto 版）

**怎么避免？**

| 手段 | 效果 |
|---|---|
| **随机化 pivot** | 期望 O(n log n)，与输入分布无关；最坏仍是 O(n²) 但概率极低（需要 1/n! 级别的巧合） |
| **三数取中**（lo / mid / hi 的中位数） | 对已排序输入直接免疫；`std::sort` 用九数取中 |
| **三路分区** | 免疫「全相同」输入 |
| **递归短边 + 循环长边** | 不改善时间，但**保证栈深 O(log n)**，不会爆栈 |
| **小区间切换插入排序** | 减少递归层数，提升常数（阈值 10~16） |

**平均 O(n log n) 的直觉推导**：

随机 pivot 下，分区位置均匀分布在 `[0, n-1]`。递归式期望为：
```
T(n) = (1/n) Σ_{k=0}^{n-1} [T(k) + T(n-1-k)] + O(n)
```
解得 `T(n) = O(n log n)`（常数约 2n ln n ≈ 1.39 n log₂n）。

> 严格证明要用指示器随机变量算「任意两元素被比较的概率 = 2/(j-i+1)」，求和得到期望比较次数 ≤ 2n ln n。面试说结论 + 一句「期望比较次数约 1.39 n log₂n」就够。

### 3.2.6 空间复杂度：到底是 O(log n) 还是 O(n)？

这是题单写错的地方，必须讲清。

| 实现方式 | 空间 | 原因 |
|---|---|---|
| **原地 + 递归**（本册 3.2.3） | **O(log n)** | 只有递归栈，深度平均 log n |
| 原地 + 递归短边 | **O(log n)** | 严格保证（最坏也是 log n） |
| **`slice`/`left`/`right` 版**（原题单给的） | **O(n)** | 每层都新建数组，同时存活的总和是 O(n) |

**为什么「同时存活」是 O(n) 而不是 O(n log n)？** 因为递归是深度优先的：处理左半时右半还没创建，处理右半时左半已经释放。峰值出现在「某一层的 left + right + 上一层的 pending」，总和不超过 2n。

> 面试话术：「原地版的快排空间是 O(log n)，就是递归栈；但用 `slice` 拆数组的写法是 O(n)，因为每层都复制了。题单里写 O(log n) 是针对原地版的。」

### 3.2.7 为什么快排「实测最快」（看似矛盾但很重要）

理论上快排最坏 O(n²)，归并和堆排都是稳定的 O(n log n)。**为什么工业界默认用快排？**

| 原因 | 说明 |
|---|---|
| **常数因子小** | 内层只有一个比较 + 一个自增，没有函数调用、没有额外数组分配 |
| **缓存友好** | 顺序扫描数组，CPU 预取命中率高；归并的 merge 在两个数组间跳动，缓存不友好 |
| **原地** | 不需要 O(n) 辅助空间，减少内存分配和 GC 压力 |
| **可优化点多** | 三数取中、三路分区、小区间插入排序，每个都能带来实际提升 |
| **最坏情况可规避** | 随机化后，退化的概率低到可以忽略（工程上不担心） |
| **内循环可向量化** | 现代编译器能对 partition 的紧凑循环做优化 |

> 一句话：「快排的 O(n²) 最坏情况在随机化后几乎不可能发生，而它每元素的实际操作数比归并少一半以上。工程上『期望性能 × 发生概率』才是关键。」

**实际数据**（对 100 万随机整数排序的典型耗时，量级参考）：

| 算法 | 耗时 |
|---|---|
| 快排（三路 + 插入排序收尾） | ~90 ms |
| 归并（temp 数组） | ~130 ms |
| 堆排 | ~200 ms |
| 希尔（Knuth） | ~180 ms |
| 插入排序 | ~60 s ❌ |

### 3.2.8 常见坑

| 坑 | 后果 | 修正 |
|---|---|---|
| 递归里用 `[lo, p]` 和 `[p+1, hi]` 但 partition 返回的是 pivot 下标 | **无限递归**（p 位置元素没排除） | Lomuto 用 `[lo, p-1]` / `[p+1, hi]`；Hoare 用 `[lo, j]` / `[j+1, hi]` |
| Lomuto 的比较写 `<=` | 全相同数组退化更严重，且丢失稳定性（虽然本来就不稳定） | 用 `<` |
| 三路快排 `gt--` 后还 `i++` | 跳过元素，结果错 | 不 `i++` |
| 忘记随机化 | 有序输入 O(n²) + 栈溢出 | 随机 swap 或三数取中 |
| 递归两边都直接递归 | 最坏栈深 O(n)，可能爆栈 | 递归短边 + 循环长边 |
| `hi` 传 `arr.length` 而不是 `length - 1` | 越界或漏元素 | 统一用闭区间 `[lo, hi]` |
| 以为快排稳定 | 答错稳定性 | 不稳定（远距离交换） |

**关于「快排不稳定」的反例**：`[2a, 5, 2b, 1]`，pivot = 1，Lomuto 分区后 `2a` 和 `2b` 都可能被换到不同侧，相对顺序无法保证。根因是 partition 的交换是**跨距离**的。

### 3.2.9 答题模板

**30 秒版**

> 快排选一个基准，把数组分成小于和大于基准两部分，再递归两边。原地、不稳定、平均 O(n log n)、最坏 O(n²)、空间 O(log n)（递归栈）。
> 最坏情况出现在「固定取首尾元素作 pivot + 输入已排序」时，每次分区只缩小一个元素。避免手段是随机化 pivot、三数取中、三路分区，再加上「递归短边、循环长边」保证栈深不超过 O(log n)。
> 它实测最快的原因是常数小、缓存友好、原地不分配。

**2 分钟版（加分层）**

> 快排的核心是 partition，也是唯一有难度的地方。我一般写 Lomuto 版：把 pivot 换到末尾，用 i 维护「小于区的边界」，j 扫描整个区间，遇到比 pivot 小的就和 i 交换并 i++，最后把 pivot 换到 i 的位置。返回 i 就是 pivot 的最终位置。
> 三个细节要注意。第一，必须先随机化 pivot，否则有序输入会退化成 O(n²)。第二，Lomuto 用严格小于，等于 pivot 的元素会被分到右边，所以全相同数组会退化——解决方案是三路快排，把数组分成小于、等于、大于三段，等于的部分不再递归。第三，递归时先处理短的一边、长的一边用循环，这样即使最坏分区，栈深也保持在 O(log n)，不会爆栈。
> 空间复杂度要说清：原地版是 O(log n) 递归栈；如果像教学版那样每层 slice 出 left 和 right，那是 O(n)。
> 至于为什么工程上用快排而不是归并——虽然快排最坏 O(n²) 而归并恒定 O(n log n)，但快排常数小、顺序访问缓存友好、原地不分配，随机化后退化的概率可以忽略。所以 `std::sort` 用的是 introsort：快排为主，递归太深时切堆排保证最坏 O(n log n)，小区间切插入排序。

### 3.2.10 追问表

| 追问 | 回答要点 |
|---|---|
| 快排最坏什么时候发生？ | 固定 pivot + 已排序/逆序输入，或全相同元素（Lomuto） |
| 怎么避免最坏？ | 随机化 pivot、三数取中、三路分区、introsort 深度限制 |
| 快排稳定吗？ | 不稳定，partition 是跨距离交换 |
| 空间复杂度？ | 原地 O(log n) 栈；slice 版 O(n) |
| Lomuto 和 Hoare 的区别？ | Lomuto 一次遍历、好懂、交换多、重复元素退化；Hoare 双指针、交换少（约 1/3）、重复元素不退化、边界难写 |

## 3.3 堆排序

> ⚠️ **原题单只有 4 行文字、没有代码**，这里补完整实现 + 建堆复杂度证明 + 优先队列。

### 一句话结论

把数组看成一棵**完全二叉树**，先建成**大顶堆**（每个父节点 ≥ 子节点），然后反复「把堆顶（最大值）换到末尾 → 剩余部分重新堆化」。**原地、不稳定、任何情况都是 O(n log n)**，是唯一「O(1) 空间 + 最坏 O(n log n)」的排序。

### 3.3.1 堆的数组表示（必须先讲清这个）

完全二叉树可以**用数组存，不需要指针**：

```
        9 (0)
       /     \
    7 (1)    8 (2)
   /   \     /
 3(3) 5(4) 6(5)

数组: [9, 7, 8, 3, 5, 6]
下标:  0  1  2  3  4  5
```

**三个公式（必须背）**：

| 关系 | 公式 |
|---|---|
| 父节点下标 | `(i - 1) >> 1` |
| 左子节点 | `2 * i + 1` |
| 右子节点 | `2 * i + 2` |

**为什么能这样映射？** 完全二叉树按层序编号后，第 k 层有 2^k 个节点，编号连续。下标 i 的左子正好是 `2i+1`（前面有 i 个节点，每个贡献 2 个子节点位置）。

**「完全二叉树」的意义**：除了最后一层，其他层都填满，最后一层靠左对齐。这保证了数组**没有空洞**，才能用下标直接算父子关系。

### 3.3.2 两个核心操作：siftDown / siftUp

**siftDown（下沉）**：节点比子节点小，就往下换，直到满足堆性质。用于**建堆**和**删除堆顶**。

```js
// 大顶堆的下沉：把 a[i] 下沉到合适位置，只在 [0, len) 范围内
function siftDown(a, i, len) {
  const val = a[i];              // 先存值（"挖洞"法，比反复 swap 快）
  while (true) {
    let child = 2 * i + 1;
    if (child >= len) break;                        // 没有子节点
    if (child + 1 < len && a[child + 1] > a[child]) child++;  // 选较大的子节点
    if (a[child] <= val) break;                     // 已经比子节点大，停止
    a[i] = a[child];                                // 子节点上移
    i = child;
  }
  a[i] = val;                    // 最后填回洞里
}
```

**「挖洞法」vs「反复 swap」**：swap 每次要 3 次赋值，挖洞法只在下沉路径上各赋一次，**少一半内存写**。这是工程实现的常见优化。

**siftUp（上浮）**：节点比父节点大就往上换。用于**插入**。

```js
function siftUp(a, i) {
  const val = a[i];
  while (i > 0) {
    const parent = (i - 1) >> 1;
    if (a[parent] >= val) break;
    a[i] = a[parent];
    i = parent;
  }
  a[i] = val;
}
```

**记忆**：**建堆用 siftDown（从后往前），插入用 siftUp（从前往后）**。

### 3.3.3 建堆：为什么是 O(n) 而不是 O(n log n)

**这是堆排序最高频的追问，答不出来等于没学懂。**

**做法**：从**最后一个非叶子节点**开始，倒序对每个节点 `siftDown`。

```js
for (let i = (n >> 1) - 1; i >= 0; i--) siftDown(a, i, n);
```

**为什么从 `n/2 - 1` 开始？** 因为下标 ≥ `n/2` 的节点都是叶子，没有子节点，不需要下沉。最后一个非叶子节点的下标是 `⌊n/2⌋ - 1`。

**为什么是 O(n)？**

粗看是「n/2 个节点 × 每个最多下沉 log n 层 = O(n log n)」，但这个估算**过松**了。关键观察：**越往下沉的节点越多，但它们能下沉的高度越小**。

设在高度 h 的节点有 `n / 2^(h+1)` 个（高度 h 指「到最底层的距离」），每个最多下沉 h 层：

```
总代价 = Σ_{h=0}^{log n} (n / 2^(h+1)) × h
       = (n/2) Σ_{h=0}^{log n} h / 2^h
       ≤ (n/2) × 2                    （因为 Σ h/2^h 收敛到 2）
       = O(n)
```

**直觉解释**：
- 最底层（叶子）占一半节点，下沉 0 层
- 倒数第二层占 1/4，下沉 1 层
- 倒数第三层占 1/8，下沉 2 层
- ……

节点数按 1/2 递减，下沉层数按 1 递增，**乘积是收敛的**。所以总代价是线性。

> 对比：如果用 siftUp 从前往后建堆（模拟「逐个插入」），每个节点上浮的代价是「它的深度」，而底层的节点最多、深度最大，总代价就是 O(n log n)。**方向选错，复杂度就不同。**

**面试话术**：「建堆是 O(n) 不是 O(n log n)。因为从最后一个非叶子节点倒序下沉时，大部分节点在底层、能下沉的高度很小。求和 Σ (n/2^(h+1)) × h 收敛到 2n，所以是线性的。如果反过来用上浮建堆，就是 O(n log n) 了。」

### 3.3.4 完整实现

```js
function heapSort(arr) {
  const n = arr.length;
  if (n <= 1) return arr;

  // 1. 建大顶堆：O(n)
  for (let i = (n >> 1) - 1; i >= 0; i--) {
    siftDown(arr, i, n);
  }

  // 2. 依次把堆顶换到末尾，剩余部分重新堆化：n 次 × O(log n)
  for (let end = n - 1; end > 0; end--) {
    [arr[0], arr[end]] = [arr[end], arr[0]];   // 最大值归位
    siftDown(arr, 0, end);                     // 注意：范围是 [0, end)
  }
  return arr;
}
```

**`siftDown(arr, 0, end)` 的第三个参数是「有效长度」**。因为 `[end, n)` 已经排好序，不能再参与堆化——否则会把刚归位的最大值又捞回来。**这是最容易写错的地方**。

### 3.3.5 逐步推演 `[3, 1, 4, 5, 2]`

**建堆**（n=5，从 index 1 开始倒序）：

```
初始:      [3, 1, 4, 5, 2]
        树:      3(0)
               /      \
            1(1)      4(2)
           /   \
        5(3)  2(4)

i=1（值 1）：子节点 5、2 → 最大 5 > 1 → 交换
           [3, 5, 4, 1, 2]

i=0（值 3）：子节点 5、4 → 最大 5 > 3 → 交换
           [5, 3, 4, 1, 2]
           继续看 index 1（值 3）：子节点 1、2 → 最大 2 < 3 → 停

建堆结果: [5, 3, 4, 1, 2]
        树:      5(0)
               /      \
            3(1)      4(2)
           /   \
        1(3)  2(4)
✓ 每个父节点都 ≥ 子节点
```

**排序**：

```
end=4: swap(0,4) → [2,3,4,1,5]  siftDown(0,4) → 4 上到顶 → [4,3,2,1,5]
end=3: swap(0,3) → [1,3,2,4,5]  siftDown(0,3) → 3 上到顶 → [3,1,2,4,5]
end=2: swap(0,2) → [2,1,3,4,5]  siftDown(0,2) → 2 > 1 不换 → [2,1,3,4,5]
end=1: swap(0,1) → [1,2,3,4,5]  siftDown(0,1) → 无子节点 → [1,2,3,4,5]
结果: [1,2,3,4,5] ✅
```

### 3.3.6 为什么堆排序不稳定

**反例**：`[3a, 3b, 2]`

```
建堆: n=3, i 从 0 开始
  siftDown(0,3): 子节点 3b、2 → 最大 3b；3b <= 3a → 停下
  堆 = [3a, 3b, 2]

end=2: swap(0,2) → [2, 3b, 3a]
       siftDown(0,2): 子节点只有 3b；3b > 2 → 交换 → [3b, 2, 3a]
end=1: swap(0,1) → [2, 3b, 3a]
       siftDown(0,1): 无子节点 → 不变

结果: [2, 3b, 3a]
```

原顺序是 `3a` 在前，结果 `3b` 在前 → **不稳定**。

**根因**：堆排序的交换发生在「堆顶 ↔ 末尾」，是**远距离交换**，会跨过大量元素。

### 3.3.7 复杂度

| 项目 | 复杂度 | 说明 |
|---|---|---|
| 建堆 | **O(n)** | 见 3.3.3 的证明 |
| 排序阶段 | O(n log n) | n 次 siftDown，每次 O(log n) |
| **总时间** | **O(n log n)** | 最好 = 平均 = 最坏 |
| 空间 | **O(1)** | 原地，只用几个临时变量 |
| 稳定 | ❌ | 远距离交换 |

**唯一「O(1) 空间 + 最坏 O(n log n)」的排序** —— 这是它在工程上的独特价值。

| 算法 | 最坏时间 | 空间 |
|---|---|---|
| 快排 | O(n²) ❌ | O(log n) |
| 归并 | O(n log n) | O(n) ❌ |
| **堆排** | **O(n log n)** ✅ | **O(1)** ✅ |

**所以堆排的适用场景**：
- **内存/栈极度受限**（嵌入式、内核）
- **不能接受最坏退化**（实时系统）
- **introsort 的兜底**：快排递归太深时切堆排，保证最坏 O(n log n)

**为什么工程上不默认用堆排？** 因为它的**缓存不友好**：`siftDown` 是跳跃访问（`2i+1`、`2i+2`），内存访问模式远不如快排的顺序扫描。实测比快排慢 2 倍左右。

### 3.3.8 手写优先队列（堆的真正主战场）

堆排本身用得少，但**堆（优先队列）用得极多**：TopK、任务调度、Dijkstra、合并 K 个链表、滑动窗口中位数。

```js
class MinHeap {
  constructor(cmp = (a, b) => a - b) {
    this.a = [];
    this.cmp = cmp;                 // cmp(a,b) < 0 表示 a 优先
  }
  get size() { return this.a.length; }
  peek() { return this.a[0]; }

  push(x) {
    this.a.push(x);
    let i = this.a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.cmp(this.a[i], this.a[p]) >= 0) break;
      [this.a[i], this.a[p]] = [this.a[p], this.a[i]];
      i = p;
    }
  }

  pop() {
    const a = this.a;
    if (a.length === 0) return undefined;
    const top = a[0];
    const last = a.pop();
    if (a.length > 0) {
      a[0] = last;
      let i = 0;
      while (true) {
        const l = 2 * i + 1, r = l + 1;
        let best = i;
        if (l < a.length && this.cmp(a[l], a[best]) < 0) best = l;
        if (r < a.length && this.cmp(a[r], a[best]) < 0) best = r;
        if (best === i) break;
        [a[i], a[best]] = [a[best], a[i]];
        i = best;
      }
    }
    return top;
  }
}
```

**TopK 的标准解法**（面试极高频）：

```js
// 求前 K 大：维护大小为 K 的【最小堆】
function topK(arr, k) {
  const heap = new MinHeap();
  for (const x of arr) {
    heap.push(x);
    if (heap.size > k) heap.pop();     // 弹掉当前 K+1 个里最小的
  }
  return heap.a.slice();               // 堆内即前 K 大（无序）
}
```

**为什么求「前 K 大」要用「最小堆」？** 因为堆顶是「这 K 个里最小的」，一旦来了更大的，就把堆顶淘汰掉。**堆顶充当了「守门员」**。

**复杂度对比**：

| 方案 | 时间 | 空间 | 适用 |
|---|---|---|---|
| 全排序后取前 K | O(n log n) | O(n) 或 O(1) | 简单，n 小时可用 |
| **维护 K 大小堆** | **O(n log k)** | **O(k)** | **n 很大、k 很小（最优）** |
| 快速选择（quickselect） | 平均 O(n) | O(1) | 只需第 K 个，不需要全序 |
| 桶/计数（值域小） | O(n) | O(值域) | 分数、年龄这类有限值域 |

### 3.3.9 常见坑

| 坑 | 后果 | 修正 |
|---|---|---|
| `siftDown(arr, 0, n)` 在排序阶段用 n | **已排好的部分被重新打乱**，结果错 | 用当前有效长度 `end` |
| 建堆从 `i = n - 1` 开始 | 对叶子做无用的 siftDown，慢但不影响正确性 | 从 `n/2 - 1` |
| 建堆从 `i = 0` 正序 | 建出来的**不是堆**（父节点可能还没就位） | 必须倒序 |
| 大顶堆写成 `a[child] < val` | 变成小顶堆，结果降序 | 大顶堆用 `>` |
| `child + 1 < len` 漏了 | 右子节点越界，读到 undefined | 必须判断 |
| 以为建堆是 O(n log n) | 答错复杂度 | O(n)，见 3.3.3 |
| 以为堆排稳定 | 答错稳定性 | 不稳定 |
| 用 `siftUp` 建堆 | O(n log n)，比 O(n) 慢 | 用 `siftDown` 倒序 |

### 3.3.10 答题模板

**30 秒版**

> 堆排序把数组看成一棵完全二叉树，下标 i 的左右子是 `2i+1`、`2i+2`。先从最后一个非叶子节点倒序下沉，建成大顶堆；再反复把堆顶换到末尾，对剩余部分重新下沉。n 次后数组有序。
> 建堆是 O(n)，排序阶段 O(n log n)，总时间恒定 O(n log n)，空间 O(1)，不稳定。
> 它的独特价值是唯一同时做到「O(1) 空间 + 最坏 O(n log n)」的排序，所以 introsort 用它给快排兜底。

**2 分钟版（加分层）**

> 堆排序分两步。第一步建堆，从最后一个非叶子节点 `n/2-1` 开始倒序对每个节点做 siftDown。这里有个常被问的点：建堆是 O(n) 不是 O(n log n)，因为越靠底层的节点越多、但能下沉的高度越小，求和 `Σ (n/2^(h+1))·h` 收敛到 2n。
> 第二步排序，循环 n-1 次，每次把堆顶（最大值）和当前末尾交换，然后对 `[0, end)` 这个前缀重新 siftDown。注意第三个参数必须是当前有效长度，否则会把刚归位的元素又捞回来。
> 空间是 O(1)，只用几个临时变量；不稳定，因为堆顶和末尾的交换是远距离的，反例是 `[3a, 3b, 2]`。
> 工程上堆排本身用得不多，因为 siftDown 是跳跃访问，缓存不友好，实测比快排慢一倍。但**堆这个数据结构用得极多**：TopK 用大小为 K 的最小堆做到 O(n log k)、Dijkstra、任务调度、合并 K 个有序链表。另外 `std::sort` 是 introsort，快排递归深度超过 2log n 时切换堆排，保证最坏也是 O(n log n)。

### 3.3.11 追问表

| 追问 | 回答要点 |
|---|---|
| 建堆为什么是 O(n)？ | 倒序下沉，底层节点多但下沉高度小，求和收敛到 2n |
| 为什么从 `n/2-1` 开始？ | 下标 ≥ n/2 的都是叶子，无需下沉 |
| 排序阶段为什么传 `end`？ | 已排好的后缀不能再参与堆化 |
| 堆排稳定吗？ | 不稳定，堆顶与末尾远距离交换；反例 `[3a,3b,2]` |
| 堆排的空间？ | O(1)，原地 |
| 堆排为什么实际比快排慢？ | 跳跃访问，缓存不友好 |
| 什么场景该用堆排？ | 内存受限、不能容忍最坏退化、introsort 兜底 |
| TopK 为什么用最小堆？ | 堆顶是「K 个里最小的」，充当守门员，新来的更大就淘汰堆顶 |
| TopK 还能怎么解？ | 快速选择平均 O(n)、全排序 O(n log n)、值域小用桶 |
| 怎么找中位数数据流？ | 一个大顶堆（前半）+ 一个小顶堆（后半），保持大小差 ≤ 1 |

## 3.4 三者横向对比

### 3.4.1 总表

| | 归并 | 快排 | 堆排 |
|---|---|---|---|
| 平均 | O(n log n) | O(n log n) | O(n log n) |
| 最好 | O(n log n) | O(n log n) | O(n log n) |
| **最坏** | **O(n log n)** ✅ | **O(n²)** ❌ | **O(n log n)** ✅ |
| 空间 | O(n) ❌ | O(log n) | **O(1)** ✅ |
| 稳定 | ✅ | ❌ | ❌ |
| 局部性 | 差（两数组跳） | **好（顺序扫）** | 差（跳父子） |
| 实测速度 | 中 | **最快** | 慢 |
| 核心操作 | merge | partition | siftDown |
| 排序发生在 | 合并阶段 | 分区阶段 | 建堆 + 交换 |

### 3.4.2 一句话选型

```
要稳定？
  └─ 是 → 归并（或 TimSort）
  └─ 否 → 要 O(1) 空间 / 怕最坏退化？
            └─ 是 → 堆排
            └─ 否 → 快排（默认选择）
```

### 3.4.3 工业界的真实选择

| 场景 | 用的算法 | 原因 |
|---|---|---|
| **V8 `Array.prototype.sort`** | TimSort（归并 + 插入） | ES2019 要求稳定 |
| **C++ `std::sort`** | introsort（快排 + 堆排 + 插入） | 快排快，堆排兜底，插入收尾 |
| **C++ `std::stable_sort`** | 归并 | 要稳定 |
| **Java `Arrays.sort(对象)`** | TimSort | 要稳定 |
| **Java `Arrays.sort(基本类型)`** | 双轴快排 | 基本类型不需要稳定 |
| **Redis `SORT`** | 快排 | 不需要稳定 |
| **数据库 `ORDER BY`** | 外部归并排序 | 数据超内存 |
| **Linux 内核 `sort`** | 堆排 | 栈空间极度受限 |

> 这张表是「你懂不懂工程」的分水岭。能说出「`Array.prototype.sort` 在 ES2019 之后要求稳定，所以 V8 从快排换成了 TimSort」的候选人，比只会默写快排的高一个档次。

## 3.5 本册速记卡

```
归并
  分治：递归均分 + merge；工作全在 merge 阶段
  稳定性只差一个等号：<= 稳定，< 不稳定
  恒定 O(n log n)，无最坏退化；空间 O(n)（链表版 O(log n)）
  四用途：稳定排序 / 链表 / 外部排序 / 求逆序对（count += mid-i+1）
  自底向上：外层 lo < n - width，保证右半非空

快排
  partition 是核心；Lomuto（好懂、交换多）vs Hoare（快、边界难）
  Lomuto 返回 i → [lo, i-1] / [i+1, hi]
  Hoare 返回 j → [lo, j] / [j+1, hi]（注意不是 j-1）
  最坏 O(n²)：固定 pivot + 有序输入 / 全相同元素
  四道防线：随机化 + 三数取中 + 三路分区 + 递归短边循环长边
  三路：lt/i/gt，gt-- 后不 i++
  空间：原地 O(log n)；slice 版 O(n)
  实测最快：常数小 + 顺序访问 + 原地

堆排
  下标 i 的子节点：2i+1、2i+2；父节点：(i-1)>>1
  建堆：i 从 n/2-1 倒序 siftDown → O(n)（求和收敛到 2n）
  排序：swap(0, end) + siftDown(0, end)，第三个参数必须是 end
  唯一「O(1) 空间 + 最坏 O(n log n)」
  不稳定：堆顶与末尾远距离交换
  TopK：大小为 K 的最小堆，O(n log k)
```
