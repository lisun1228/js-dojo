## 0.3 工程化的六层模型（先建立框架，再背细节）

工程化面试最大的陷阱是**被问成一地问号**。你需要一个框架，能把任意问题挂上去：

```
第 6 层  监控与度量     Sentry / 埋点 / 性能监控 / 告警
第 5 层  部署与交付     CI/CD / Docker / Nginx / CDN / 灰度
第 4 层  测试与质量     单元测试 / E2E / 覆盖率 / 质量门禁
第 3 层  规范与约束     ESLint / Prettier / commitlint / husky / TS
第 2 层  构建与编译     Webpack / Vite / Babel / Tree Shaking / 产物优化
第 1 层  开发与协作     目录规范 / Git 工作流 / 脚手架 / Monorepo / 包管理
```

**这张图的用法**：

面试官问「你对工程化的理解」，你不要背定义，而是说：

> 「我把前端工程化拆成六层：**最底层是开发协作**（目录规范、Git 流、脚手架），**往上是构建编译**（Webpack/Vite/Babel），**然后是规范约束**（ESLint、提交规范），**再上是测试质量**，**然后是部署交付**（CI/CD、Docker），**最上面是监控度量**。每一层解决的问题不同——底层解决「多人协作不打架」，中层解决「代码能不能跑在目标环境」，上层解决「改完怎么安全上线、出问题怎么发现」。」

**这一段的杀伤力**：它证明你有全局视角，而不是背了 34 个孤立概念。后面的每一个具体问题，你都可以说「这属于第 N 层」。

## 0.4 工程化题和前面的题不一样：它考「决策」不考「实现」

对比一下：

| 题型 | 考什么 | 答法 |
|---|---|---|
| JS 手写题 | **能不能写对** | 写代码 + 补边界 |
| 网络原理题 | **记不记得机制** | 讲清流程 + 关键细节 |
| **工程化题** | **能不能做技术决策** | **讲清取舍 + 说出踩过的坑** |

**所以工程化题最忌讳的是「背定义」**。看两个回答：

❌ 背定义式：

> 「Tree shaking 就是删除未使用的代码，基于 ES Module 静态分析，CommonJS 不支持。」

✅ 决策式：

> 「Tree shaking 本质是**用『模块副作用是否可判定』换取体积**。它依赖 ESM 的静态结构，所以有三个前提：**必须是 ESM、必须标记 sideEffects、必须经过压缩器真正删除**。我实测过，只开 `usedExports` 的话 webpack 只是加一行 `/* unused harmony export */` 注释，代码还在——真正删除是 Terser 干的。所以如果项目关掉了压缩（比如为了调试），tree shaking 等于没生效。」

第二个回答里有三个东西：**机制 + 边界 + 实测**。这就是工程化题的高分答案。

## 0.5 工程化题的三段式答法

### 第一段：先说「解决什么问题」（15 秒）

不要上来讲实现。先说这个技术**存在的原因**：

> 「Tree shaking 解决的是**打包产物体积**问题。在它之前，我们只能靠『按需引入』这种人工约定，容易漏。它把这件事自动化了。」

### 第二段：讲机制 + 关键前提（60 秒）

> 「机制是：ESM 的 import/export 是**静态声明**，打包器在编译期就能画出完整的依赖图，标出「谁被用了、谁没被用」。但**标记不等于删除**……」

### 第三段：说取舍 + 踩过的坑（30 秒）

> 「它的代价是：① 要求代码必须是 ESM，CommonJS 的动态 `require` 分析不了；② 需要库作者正确标记 `sideEffects`，标错了会误删有副作用的代码（比如 `import './polyfill'` 被删掉）；③ 依赖压缩器做最终删除。」

**这三段的比例是 1:3:1。** 第三段是区分度所在——只有真做过项目的人才说得出「标错 sideEffects 会误删」。

## 0.7 本册的实测数据（可以先记结论）

所有数据都是用 webpack 5.112 / @babel/core 8.0 / esbuild 0.28 / tapable 2.3 实跑出来的：

### Tree Shaking 的四个阶段（同一份源码，逐级开配置）

| 配置 | 产物体积 | unusedFn | unusedGreet | square |
|---|---|---|---|---|
| 全部关闭 | **3573 B** | 残留 | 残留 | 残留 |
| + `usedExports` | **3003 B** | 残留 | 残留 | 残留 |
| + `sideEffects` + `concatenateModules` | **413 B** | 残留 | 残留 | 残留 |
| + `minimize`（Terser） | **62 B** | **已删除** | **已删除** | **已删除** |

**关键发现**：`usedExports` 只是加了一行注释：

```js
/* unused harmony exports unusedFn, square */
/* unused harmony export unusedGreet */
```

**真正删除代码的是 Terser，不是 webpack。** 所以 `minimize: false` 时 tree shaking 等于没生效。

最终产物（62 字节）：

```js
(()=>{"use strict";console.log(3),console.log("HI world")})();
```

注意 `console.log(3)` —— Terser 还顺手做了**常量折叠**（`1 + 2` 在编译期算掉了）。

### Babel vs esbuild 速度（200 个模块 / 84.4 KB）

| 工具 | 耗时 | 倍数 |
|---|---|---|
| Babel（preset-env → IE11） | **1956 ms** | 1× |
| esbuild（transform → ES2015） | **100 ms** | **19.6×** |
| esbuild（完整 bundle + minify） | **15 ms** | 130× |

> 130× 这个数字要打折：esbuild 那次做了 tree shaking，产物只有 1.2 KB，工作量不一样。**但 19.6× 这个同口径的对比是可信的。**

### tapable 九种钩子的语义差异

```
SyncHook         → 依次执行，不传返回值，call() 返回 undefined
SyncWaterfallHook→ 1 → A(+10) → 11 → B(*2) → 22 → C → 最终 22
SyncBailHook     → A(undefined) → B(返回"STOP") → 中断，C 不执行，call 返回 "STOP"
SyncLoopHook     → A 返回非 undefined 就重头再来（实测 A 执行 3 次后 B 才执行）
AsyncSeriesHook  → 串行 62ms（40+20）
AsyncParallelHook→ 并行 42ms（max(40,20)）
```

### loader 链的执行顺序（洋葱模型）

配置 `use: [l1, l2, l3]`，实测输出：

```
l1 pitch（最先执行）
l2 pitch
l3 pitch（最后执行）
l3 normal（最先执行）
l2 normal
l1 normal（最后执行）
```

产物里的追加顺序：`l3 → l2 → l1`

**pitch 是「左到右」，normal 是「右到左」——整个链条是一个洋葱。**

### git merge vs rebase（同一个分叉）

**merge**：

```
*   14045c8 merge feature into main
|\
| * 2d3e657 C: feature 2
| * e64fdec B: feature 1
* | 24a4394 E: main 2
* | d31174f D: main 1
|/
* c380f79 A: base
```
→ 6 个 commit，有分叉，多一个 merge commit

**rebase**：

```
* 81c9f59 (feature) C: feature 2
* 4d4a95c B: feature 1
* 0223a44 (main) E: main 2
* d7d1fa1 D: main 1
* 742846f A: base
```
→ 5 个 commit，完全线性

**但重点在 hash**：`B` 从 `e64fdec` 变成了 `4d4a95c`，`C` 从 `2d3e657` 变成了 `81c9f59`。

> **rebase 是「重新创建提交」，不是「移动提交」。** 这就是「不要 rebase 公共分支」的根本原因——别人的本地分支会指向一堆已经不存在的 commit。

### rebase 冲突现场的关键认知

```
line1
<<<<<<< HEAD
MAIN          ← 这里是 main（目标分支）
=======
FEATURE       ← 这里是你正在被 rebase 的提交
>>>>>>> 07a0edf (B: 改成 FEATURE)
line3
```

**`HEAD` 指向的是「目标分支」，不是你的分支。** 这跟 merge 冲突时完全相反（merge 时 `HEAD` 是当前分支），是 rebase 最反直觉的一点。

## 0.11 一句话速记

> **工程化面试考的不是「你知道多少工具」，而是「你能不能在多个方案里做出有理由的选择」。**
>
