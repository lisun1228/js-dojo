# 网络 · 09 HTTPS 与 TLS（题 13、17、30、34、39、47、48、59、66）

> 本册覆盖：HTTPS 加密过程（原题 13、34）、为什么需要 HTTPS（题 30）、为什么安全（题 39、47、66）、HTTP 与 HTTPS 区别（题 17、48、59）
> 题单只写了「混合加密：非对称协商密钥，对称传数据，证书验证身份」。**这句话是对的，但只够及格**。
> 真正拉开差距的是三件事：**为什么不能用非对称传数据（要给出量级）**、**证书链怎么验证**、**什么是前向安全**。

---

## 9.1 一句话结论

HTTPS = **HTTP + TLS**。TLS 解决 HTTP 的三个致命问题：**明文可窃听、内容可篡改、身份可冒充**。
手段是**混合加密**——**非对称加密只用来「协商密钥 + 验证身份」，数据全程用对称加密**（因为非对称慢 3~4 个数量级），**证书链**保证你连的是真服务器。

**一句话记忆：非对称解决「怎么安全地把钥匙给你」，对称解决「怎么快速传数据」，证书解决「钥匙给了谁」。**

## 9.2 HTTP 的三个致命问题（题 30 的答案）

HTTP 是**纯文本、明文传输**，链路上任何一个节点都能：

| 攻击 | 手段 | 后果 |
|---|---|---|
| **窃听（Eavesdropping）** | 抓包（WiFi 热点、运营商、代理） | 密码、Cookie、身份证号全暴露 |
| **篡改（Tampering）** | 中间人修改响应 | 注入广告、注入恶意 JS、改支付账号 |
| **冒充（Spoofing）** | DNS 劫持、ARP 欺骗、伪造服务器 | 你访问 `bank.com`，实际连到了假服务器 |

**一个具体的攻击场景**（公共 WiFi）：

```
你在咖啡厅连 WiFi，访问 http://bank.com
    ↓
攻击者开一个同名热点，做 DNS 劫持
    ↓
你的请求到了攻击者的服务器
    ↓
攻击者反向代理到真正的 bank.com，把页面原样返回给你
    ↓
你输入账号密码 → 攻击者全都看得到
    ↓
攻击者还可以篡改响应：把「转账给 A」改成「转账给 B」
    ↓
你完全无感
```

**HTTPS 就是来解决这三件事的**。

## 9.3 TLS 解决的三件事

| 安全目标 | 手段 | 具体算法 |
|---|---|---|
| **机密性（Confidentiality）** | **对称加密** | AES-128-GCM / AES-256-GCM / ChaCha20-Poly1305 |
| **完整性（Integrity）** | **消息认证码（MAC）** | 现代用 AEAD（GCM 自带 MAC） |
| **身份认证（Authentication）** | **数字证书 + 非对称签名** | RSA / ECDSA |

**注意完整性是独立的**：光加密不够——攻击者虽然看不懂内容，但可以**随机翻转几个字节**，让解密后的内容变成垃圾（或者精心构造出有意义的内容）。所以需要 MAC 来校验「有没有被改过」。

**现代 TLS 1.3 用 AEAD（Authenticated Encryption with Associated Data）**，把加密和完整性**合成一个算法**（比如 AES-GCM），一次运算同时保证两件事。这比「先加密再 HMAC」更快也更安全。

## 9.4 为什么必须是混合加密（必问，要说数量级）

### 9.4.1 两种加密的特性对比

| | 对称加密 | 非对称加密 |
|---|---|---|
| **密钥** | 加解密用**同一把** | **公钥加密、私钥解密**（或私钥签名、公钥验签） |
| **算法** | AES、ChaCha20、DES | RSA、ECC（ECDSA/ECDHE）、DH |
| **速度** | **快**（AES-NI 硬件加速下可达 GB/s 级） | **慢**（比 AES 慢 3~4 个数量级） |
| **密钥分发** | ❌ **难题**：怎么把密钥安全地给对方 | ✅ 公钥可以公开传输 |
| **能做什么** | 只加密 | 加密 + **签名（身份认证）** |

### 9.4.2 只用对称：密钥怎么给？

```
客户端                          服务端
   │  请把对称密钥给我            │
   │ ──────────────────────────> │
   │  好的，密钥是 K              │  ← 这个 K 在明文链路上传输
   │ <────────────────────────── │
   │                              │
   ↑ 攻击者抓到这个包就拿到 K 了，后面全程可解密
```

**死锁**：要安全传密钥，得先有安全通道；要有安全通道，得先有密钥。

### 9.4.3 只用非对称：慢到不可用

**量级对比**（RSA-2048 vs AES-128-GCM，同一台机器）：

| 操作 | 大致吞吐量 |
|---|---|
| AES-128-GCM（有 AES-NI） | **GB/s 级**（比如 2~5 GB/s） |
| RSA-2048 加密 | **几万次/秒**（每次只能加密 245 字节） |
| RSA-2048 解密 | **几千次/秒** |

**结论**：用 RSA 传 1 MB 数据，需要分 4000 多块、做 4000 多次非对称运算，**慢上千倍**。而且 RSA 一次只能加密「密钥长度减去 padding」的字节数（2048 位 = 256 字节，实际只能加密 245 字节）。

### 9.4.4 混合加密：各取所长

```
① 用非对称（或密钥交换）安全地协商出一个「会话密钥」
   （这个密钥只用于本次会话，用完即弃）

② 之后所有数据都用这个会话密钥做对称加密
```

**所以 HTTPS 的实际数据流是**：

```
握手阶段（非对称）：
  验证证书（确认服务器身份）→ ECDHE 协商出 pre-master → 算出会话密钥
    ↓
传输阶段（对称）：
  HTTP 明文 → 用会话密钥 AES-GCM 加密 → 传输 → 解密
```

> **面试话术**：「只用对称解决不了密钥分发——密钥本身怎么安全地传过去？只用非对称慢到不可用——RSA 比 AES 慢三到四个数量级，而且一次只能加密几百字节。所以是混合：**非对称只用来协商一个临时的会话密钥（这一步数据量极小），后续所有数据用对称加密**。这样既有非对称的「能安全协商」，又有对称的「快」。」

### 9.4.5 一个常见误区

| 错误说法 | 正确说法 |
|---|---|
| 「HTTPS 用非对称加密传输数据」 | 数据用**对称**加密；非对称只用于协商和签名 |
| 「非对称加密比对称安全」 | 安全性都够，**差别在性能和密钥分发** |
| 「HTTPS 加密了 URL 和域名」 | ❌ **域名（SNI）和 IP 在 TLS 握手前就是明文**（ECH 可以加密 SNI，但还没普及）；URL 路径在加密的请求里，是安全的 |

## 9.5 TLS 1.2 完整握手（题 13、34 的详细版）

> 面试说「HTTPS 加密过程」时，**能把 TLS 1.2 的握手讲清就已经很好了**。TLS 1.3 是加分项。

### 9.5.1 完整时序（ECDHE + RSA 签名）

```
客户端                                              服务端
  │                                                   │
  │ ① ClientHello                                     │
  │    · 支持的 TLS 版本（1.2/1.3）                     │
  │    · 密码套件列表（cipher suites）                   │
  │    · client_random（32 字节随机数）                 │
  │    · SNI（要访问的域名，明文！）                     │
  │    · ALPN（应用层协议协商：h2 / http/1.1）           │
  │ ─────────────────────────────────────────────────>│
  │                                                   │
  │ ② ServerHello                                     │
  │    · 选定的 TLS 版本和密码套件                       │
  │    · server_random（32 字节随机数）                 │
  │                                                   │
  │ ③ Certificate                                     │
  │    · 服务器证书链（服务器证书 + 中间 CA）             │
  │                                                   │
  │ ④ ServerKeyExchange                               │
  │    · ECDHE 参数（椭圆曲线、服务器临时公钥）           │
  │    · 用【证书私钥】对上述参数签名  ← 证明「我真的是服务器」│
  │                                                   │
  │ ⑤ ServerHelloDone                                 │
  │ <─────────────────────────────────────────────────│
  │                                                   │
  │ ★ 客户端此时做三件事：                              │
  │   1. 验证证书链（域名、有效期、签名、吊销）           │
  │   2. 用 ECDHE 算出 pre-master secret              │
  │   3. 用 client_random + server_random + pre-master │
  │      算出 master secret → 再导出会话密钥            │
  │      （这一步叫 PRF，伪随机函数）                    │
  │                                                   │
  │ ⑥ ClientKeyExchange                               │
  │    · 客户端临时公钥（ECDHE）                        │
  │                                                   │
  │ ⑦ ChangeCipherSpec + Finished                     │
  │    · 「我这边切换成加密了」                          │
  │    · Finished = 之前所有握手报文的摘要（加密后发）    │
  │ ─────────────────────────────────────────────────>│
  │                                                   │
  │ ⑧ ChangeCipherSpec + Finished                     │
  │ <─────────────────────────────────────────────────│
  │                                                   │
  │ ══════════ 之后全部用会话密钥对称加密 ══════════      │
```

### 9.5.2 四个关键设计（为什么这么设计）

#### ① 为什么需要 `client_random` 和 `server_random`

**防重放攻击**。如果会话密钥只由 ECDHE 决定，那么**同样的 ECDHE 参数**会产生**同样的密钥**。攻击者录下整个会话，将来重放就能解密。

加了两个随机数后，**每次会话的密钥都不同**，重放无效。

#### ② 为什么 ECDHE 参数要「用证书私钥签名」

**这是「身份认证」的关键一步。**

```
攻击者可以自己生成一对 ECDHE 密钥，然后跟客户端协商
    ↓
但攻击者没有 example.com 的【证书私钥】
    ↓
所以它无法对 ECDHE 参数签名，或者签名验证不过
    ↓
客户端发现签名不对 → 中断连接
```

**注意区分两对密钥**：

| 密钥 | 用途 | 生命周期 |
|---|---|---|
| **证书里的公私钥**（RSA/ECDSA） | **只用于签名**（证明身份），**不用于加密数据** | 长期（几个月到几年） |
| **ECDHE 临时密钥对** | **只用于协商会话密钥** | **一次会话**，用完即弃（这就是「前向安全」的来源） |

#### ③ 为什么 `Finished` 要包含「之前所有报文的摘要」

**防止握手过程被篡改**。如果攻击者在握手期间偷偷改掉了密码套件列表（比如降级到弱算法），`Finished` 的摘要就对不上，双方会立刻发现并中断。

这个机制叫 **transcript hash**，是防**降级攻击（downgrade attack）**的核心。

#### ④ 为什么需要 `ChangeCipherSpec`

因为握手前半段是**明文**的，需要一个明确的信号告诉对方「**从下一条消息开始，我说的话是加密的**」。

## 9.6 TLS 1.3 的改进

### 9.6.1 三个核心变化

| 变化 | 内容 |
|---|---|
| **① 握手从 2-RTT 降到 1-RTT** | 把密钥协商和证书发送**合并到第一轮**；客户端在 `ClientHello` 里就带上 ECDHE 公钥（`key_share`），不用等服务器 |
| **② 只保留安全算法** | 删掉了 RSA 密钥交换、CBC 模式、RC4、SHA-1、MD5。只保留 **(EC)DHE + AEAD + SHA-256 以上** |
| **③ 强制前向安全** | 因为只允许 (EC)DHE，**所有 TLS 1.3 连接都有前向安全** |

### 9.6.2 1-RTT 怎么做到的

```
TLS 1.2（2-RTT）：
  ClientHello ──→                    （第 1 个 RTT）
                ←── ServerHello + 证书 + ECDHE 参数
  ClientKeyExchange + Finished ──→    （第 2 个 RTT）
                ←── Finished
  ══ 开始传数据 ══

TLS 1.3（1-RTT）：
  ClientHello + key_share ──→         （第 1 个 RTT，客户端猜一个曲线，直接给公钥）
                ←── ServerHello + key_share + 证书 + Finished
  Finished ──→
  ══ 开始传数据 ══
```

**关键**：客户端在 `ClientHello` 里**主动提供 ECDHE 公钥**（`key_share` 扩展，通常会猜几个常见曲线）。服务器如果接受，第一轮就能算出共享密钥，**省掉一整个 RTT**。

### 9.6.3 0-RTT 怎么做到的（以及它的代价）

**原理**：用上次会话的 **PSK（Pre-Shared Key，session ticket）**。客户端在第一个包里就带上加密的应用数据。

```
首次连接：1-RTT（正常握手）
    ↓ 服务器发一个 session ticket（加密的会话状态）
下次连接：ClientHello + PSK + 【加密的 HTTP 请求】
    ↓ 服务器直接用 PSK 解密
0-RTT！直接开始传数据
```

**0-RTT 的两个严重问题**：

| 问题 | 说明 |
|---|---|
| **没有前向安全** | 0-RTT 的数据用 PSK 加密，而 PSK 是长期存在的。如果 PSK 泄露，这段数据就能被解 |
| **可被重放攻击** | 攻击者录下 0-RTT 的数据包，可以**原样重放**。服务器会以为是新请求 |

**所以 0-RTT 只能用于「幂等请求」**——通常是 `GET`。**绝不能用于 `POST /transfer`**（重放会导致重复转账）。

> 面试话术：「TLS 1.3 的 0-RTT 用上次会话的 PSK，第一个包就带加密数据，省掉整个握手。但它没有前向安全，而且可被重放——攻击者录下 0-RTT 包原样重发就能生效。所以只能用于 GET 这种幂等请求，不能用于支付这类操作。」

## 9.7 证书与证书链验证（最能体现深度的一块）

### 9.7.1 证书里有什么

一张 X.509 证书包含：

| 字段 | 内容 | 作用 |
|---|---|---|
| **Subject** | 证书持有者（`CN=example.com`） | 标识身份 |
| **SAN（Subject Alternative Name）** | **实际生效的域名列表** | **✅ 现代浏览器只看 SAN，不看 CN** |
| **Issuer** | 签发者（哪个 CA） | 找上级验证 |
| **Validity** | 有效期（`Not Before` / `Not After`） | 防过期 |
| **Public Key** | **服务器的公钥** | 验签、协商 |
| **Signature** | **CA 用自己私钥对上面内容的签名** | 证明「CA 认证过这个证书」 |
| **Key Usage / EKU** | 用途（serverAuth / clientAuth） | 防止「签名证书」被用于服务器 |
| **Serial Number** | 序列号 | 吊销查询 |
| **SCT** | 证书透明度日志的证明 | 防误签 |

### 9.7.2 三级证书链

```
┌─────────────────────────────────────────┐
│  根证书（Root CA）                        │
│  · 自签名（Issuer == Subject）             │
│  · 【预装在操作系统/浏览器的信任库】          │
│  · 私钥在 CA 的离线 HSM 里，绝不出网         │
└────────────────┬────────────────────────┘
                 │ 用根 CA 私钥签名
                 ▼
┌─────────────────────────────────────────┐
│  中间证书（Intermediate CA）              │
│  · 由根 CA 签发                           │
│  · 【必须由服务器一起下发】                  │
└────────────────┬────────────────────────┘
                 │ 用中间 CA 私钥签名
                 ▼
┌─────────────────────────────────────────┐
│  服务器证书（Leaf / End-entity）           │
│  · 由中间 CA 签发                         │
│  · 里面是 example.com 的公钥               │
└─────────────────────────────────────────┘
```

**为什么要有中间 CA**：根 CA 的私钥极度重要，必须离线保存（放在保险柜/HSM 里）。日常签发证书用中间 CA，**即使中间 CA 私钥泄露，只需吊销中间证书，根 CA 不受影响**。

### 9.7.3 验证流程（六步）

浏览器拿到服务器证书后：

```
① 域名匹配
   证书的 SAN 列表里是否包含当前域名？
   （支持通配符 *.example.com，但不支持 *.a.example.com 这种多级）

② 有效期
   now 是否在 Not Before ~ Not After 之间？

③ 用途正确
   EKU 是否包含 serverAuth？

④ 逐级验签
   用「中间 CA 的公钥」验证「服务器证书的签名」
   → 用「根 CA 的公钥」验证「中间证书的签名」
   → 根 CA 到达信任库 → ✅

⑤ 吊销检查
   证书是否被 CA 吊销？
   方式：CRL（下载列表）/ OCSP（在线查询）/ OCSP Stapling（服务器代查）/ CRLite

⑥ 证书透明度
   SCT（Signed Certificate Timestamp）是否存在于公开的 CT 日志？
   → 防止 CA 偷偷签发
```

**任何一步失败，浏览器都会报错并中断连接**：

| 错误 | 原因 |
|---|---|
| `NET::ERR_CERT_DATE_INVALID` | 过期 |
| `NET::ERR_CERT_COMMON_NAME_INVALID` | 域名不匹配 |
| `NET::ERR_CERT_AUTHORITY_INVALID` | 证书链不完整，或根 CA 不受信任 |
| `NET::ERR_CERT_REVOKED` | 被吊销 |
| `NET::ERR_CERT_SELF_SIGNED` | 自签名证书 |

### 9.7.4 为什么证书能防中间人（核心逻辑）

**中间人攻击的困境**：

```
攻击者想冒充 example.com
    ↓
它需要一张「example.com 的证书」
    ↓
证书必须有【受信任的 CA】的签名
    ↓
攻击者拿不到这个签名（CA 会验证域名所有权才签发）
    ↓
攻击者只能：
  ① 用自签名证书 → 浏览器报「不受信任」
  ② 用自己域名的证书 → 域名不匹配，报错
  ③ 偷/骗一张证书 → 需要攻破 CA 或做域名验证绕过（历史上有过，所以有了 CT 日志）
```

**这就是「信任链」的本质**：**你信任的不是证书本身，而是「证书背后的 CA」**。而 CA 的信任是预装在操作系统里的。

**为什么需要 CA 而不是「自己签名」**：因为「自己签名」等于「自己说自己是好人」，没有任何第三方背书。CA 的作用是**做域名所有权的第三方验证**。

### 9.7.5 一个真实的运维坑：中间证书没配

**现象**：Chrome 能打开，但**安卓 App / 老版本 Java 客户端报证书错误**。

**根因**：服务器只下发了「服务器证书」，**没下发「中间证书」**。Chrome 会自动去网上找缺失的中间证书（AIA Fetching），所以能打开；但很多客户端不会，于是链断了。

**检查方法**：

```bash
openssl s_client -connect example.com:443 -showcerts
# 看输出里有几张证书。正常应该有 2~3 张（服务器证书 + 中间证书）
```

**修复**：把「服务器证书 + 中间证书」拼成一个文件配置到 Nginx：

```nginx
ssl_certificate     /path/fullchain.pem;   # 服务器证书 + 中间证书
ssl_certificate_key /path/privkey.pem;
```

> **这个案例答出来非常加分**——它证明你真的配过 HTTPS，不只是背过理论。

## 9.8 前向安全（Forward Secrecy）

### 9.8.1 定义

**即使服务器的长期私钥将来泄露了，攻击者也无法解密过去录下的流量。**

### 9.8.2 为什么需要

**没有前向安全的情况**（TLS 1.2 用 RSA 密钥交换）：

```
客户端用【服务器证书的公钥】加密 pre-master secret
    ↓
服务器用【证书私钥】解密
    ↓
会话密钥由 pre-master 派生
    ↓
★ 攻击者录下所有流量，等哪天偷到了服务器私钥
    ↓
用私钥解开当年录下的 pre-master → 算出会话密钥 → 解密全部历史流量
```

**这就是「先录后解」（harvest now, decrypt later）** —— 也是各国情报机构的常规操作。

**有前向安全的情况**（ECDHE）：

```
双方各自生成【临时】ECDHE 密钥对，交换公钥，各自算出共享密钥
    ↓
临时私钥用完立刻销毁（不落盘）
    ↓
★ 服务器证书私钥泄露也没用——它只用于签名，不参与密钥计算
    ↓
攻击者无法恢复会话密钥
```

### 9.8.3 现状

| 版本 | 前向安全 |
|---|---|
| TLS 1.2 + RSA 密钥交换 | ❌ 没有 |
| TLS 1.2 + ECDHE | ✅ 有（现在的主流配置） |
| **TLS 1.3** | ✅ **强制有**（只允许 (EC)DHE） |

> **面试话术**：「前向安全是指即使服务器私钥将来泄露，历史流量也解不开。原理是会话密钥由**临时**的 ECDHE 密钥算出，用完就销毁，证书私钥只用于签名、不参与密钥计算。TLS 1.2 如果用 RSA 密钥交换就没有前向安全——攻击者可以『先录流量，等偷到私钥再解』。所以现在都要配 ECDHE，TLS 1.3 更是强制只允许 ECDHE。」

## 9.9 HSTS：防止 SSL 剥离

### 9.9.1 什么是 SSL Stripping

```
用户输入 example.com（浏览器补全成 http://）
    ↓
攻击者在链路上拦截这个 http 请求
    ↓
攻击者自己跟服务器建立 HTTPS（攻击者能验证证书）
    ↓
攻击者把内容用【明文 HTTP】返回给用户
    ↓
用户看到的是 http:// 但内容正常 → 毫无察觉
    ↓
之后所有「敏感操作」都在明文下进行
```

**问题根源**：用户第一次访问时用的是 `http://`，第一跳是明文的。

### 9.9.2 HSTS 的解法

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

| 指令 | 作用 |
|---|---|
| `max-age=31536000` | 浏览器记住「这个域名**只走 HTTPS**」，有效期一年 |
| `includeSubDomains` | 所有子域名也适用 |
| `preload` | 申请加入**浏览器内置的 HSTS 预加载列表**（首次访问也强制 HTTPS） |

**生效后**：

```
用户输入 http://example.com
    ↓
浏览器内部直接改成 https://example.com（307 Internal Redirect）
    ↓
http 请求根本不会发出去
    ↓
SSL Stripping 失效
```

### 9.9.3 `preload` 的坑（谨慎使用）

**一旦进入 Chrome 的 HSTS preload 列表，移除需要几个月**（要等所有用户的浏览器更新）。

**如果配错了**（比如某个子域名只有 HTTP 服务），会导致**该子域名永久无法访问**。

> 建议：先上 `max-age` 短一点（比如 300 秒）验证，稳定后再加长，最后再考虑 `preload`。

## 9.10 HTTPS 的性能成本与优化

### 9.10.1 成本在哪

| 成本 | 量级 | 优化 |
|---|---|---|
| **握手多 1~2 RTT** | 40~120 ms | **TLS 1.3**（1-RTT）、**会话复用**（0-RTT） |
| **证书验证** | 可能要多一次 OCSP 查询（几十~几百 ms） | **OCSP Stapling**（服务器代查并缓存） |
| **加解密计算** | 现代 CPU 有 AES-NI，**几乎可忽略**（< 1%） | 硬件加速、ChaCha20（移动端无 AES-NI 时更快） |
| **首次连接无缓存** | 无法避免 | `preconnect`、CDN 边缘节点就近握手 |

### 9.10.2 四个优化手段

```nginx
# Nginx 生产配置模板
ssl_protocols TLSv1.2 TLSv1.3;                    # 只留 1.2/1.3
ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:...';  # 只留 AEAD + ECDHE
ssl_prefer_server_ciphers off;                    # TLS1.3 下建议 off，让客户端选

ssl_session_cache shared:SSL:10m;                 # 会话缓存（1万左右会话）
ssl_session_timeout 1d;
ssl_session_tickets on;                           # session ticket（0-RTT 基础）

ssl_stapling on;                                  # OCSP Stapling
ssl_stapling_verify on;
resolver 8.8.8.8 valid=300s;
```

| 手段 | 效果 |
|---|---|
| **TLS 1.3** | 握手从 2-RTT → 1-RTT |
| **会话复用**（session id / ticket） | 二次连接 0-RTT 或 1-RTT |
| **OCSP Stapling** | 省掉客户端查吊销列表的往返 |
| **ECDSA 证书** | 签名运算比 RSA 快很多，证书也更小 |

## 9.11 HTTP 与 HTTPS 的区别（题 17、48、59）

| 维度 | HTTP | HTTPS |
|---|---|---|
| **协议** | 应用层直接跑在 TCP 上 | HTTP over **TLS** over TCP |
| **默认端口** | 80 | **443** |
| **加密** | ❌ 明文 | ✅ 加密 |
| **完整性** | ❌ 可被篡改 | ✅ AEAD 校验 |
| **身份认证** | ❌ 无法确认服务器身份 | ✅ 证书链 |
| **证书** | 不需要 | **需要（且要受信任的 CA 签发）** |
| **握手** | TCP 1 RTT | TCP 1 RTT + TLS 1~2 RTT |
| **性能** | 略快 | 略慢（可优化到接近） |
| **SEO** | 无加成 | **Google 有排名加成** |
| **浏览器标记** | **「不安全」警告** | 显示锁图标 |
| **HTTP/2、Service Worker 等新 API** | ❌ **不支持**（需要 Secure Context） | ✅ 支持 |

**最后一行很重要**：很多现代 Web API（Service Worker、Geolocation、Camera、Clipboard、`crypto.subtle`）**只在 Secure Context（HTTPS 或 localhost）下可用**。所以 **HTTPS 不只是安全，还是「能不能用新能力」的门槛**。

## 9.12 常见坑

| 坑 | 正确说法 |
|---|---|
| 说「HTTPS 用非对称加密传数据」 | 数据用**对称**；非对称只用于协商和签名 |
| 说「HTTPS 加密了所有内容，包括域名」 | **SNI（域名）在握手前是明文的**；IP 也是明文 |
| 说「证书验证只看域名和有效期」 | 还有**签名链**、**用途（EKU）**、**吊销状态**、**CT 日志** |
| 说「证书的 CN 字段是域名」 | 现代浏览器**只看 SAN**，CN 已废弃 |
| 说「自签名证书也能用」 | 浏览器会报「不受信任」；只能内网/开发用（需手动导入根证书） |
| 说「TLS 1.3 一定更快」 | 首次 1-RTT 更快；但 0-RTT 有安全代价，不能滥用 |
| 说「0-RTT 可以用于所有请求」 | 只能用于**幂等请求**（GET），因为可被重放 |
| 说「HTTPS 就没有中间人了」 | 如果**客户端信任了攻击者的根证书**（比如装了抓包工具的证书），照样能中间人 |
| 说「HTTPS 一定安全」 | 只保证**传输安全**；XSS、SQL 注入、越权它都防不了 |
| 只配服务器证书，不配中间证书 | 部分客户端（安卓 App、老 Java）会报证书链错误 |
| 说「HTTPS 性能差很多」 | 现代硬件下加解密开销 < 1%，主要成本在握手 RTT |
| 说「HSTS 可以随时撤销」 | 一旦进 preload 列表，移除要等几个月 |

## 9.13 答题模板

### 30 秒版（题 13 原题）

> HTTPS 是在 HTTP 和 TCP 之间加了一层 TLS。它用**混合加密**：握手阶段用**非对称加密**（严格说是 ECDHE 密钥交换）协商出一个临时的会话密钥，同时用**证书**验证服务器身份；之后所有数据用这个会话密钥做**对称加密**传输。
> 之所以混合，是因为非对称太慢（比对称慢三四个数量级），只适合传少量密钥；对称快，适合传大量数据。
> 证书由受信任的 CA 签发，浏览器通过验证证书链、域名、有效期来确认「我连的是真服务器，不是中间人」。

### 30 秒版（题 17 原题：HTTP vs HTTPS）

> 五个区别：HTTPS 在 HTTP 和 TCP 之间加了 TLS，端口从 80 变 443，加密、保证完整性、用证书认证身份，代价是握手多 1~2 个 RTT。
> 还有一点常被忽略：**很多现代 API（Service Worker、摄像头、地理位置）只在 HTTPS 下可用**，所以 HTTPS 不只是安全，还是能力门槛。
> 另外 HTTP 站会被浏览器标「不安全」，Google 搜索也有排名加成。

### 2 分钟版（完整版，推荐）

> 我分四块讲：为什么需要、怎么加密、证书怎么验证、有什么代价。
>
> **为什么需要**：HTTP 是明文，链路上任何人都能窃听、篡改、冒充。最典型的是公共 WiFi 下的 SSL Stripping——攻击者劫持你的 http 请求，自己跟服务器建 HTTPS，再用明文返回给你，你完全无感。
>
> **怎么加密**：核心是混合加密。只用对称解决不了密钥分发——密钥本身怎么安全传过去？只用非对称又慢到不可用——RSA 比 AES 慢三到四个数量级，一次只能加密几百字节。所以是：**非对称只用来协商一个临时的会话密钥，之后所有数据用对称加密**。
>
> 具体到 TLS 1.2 的握手：客户端发 ClientHello，带支持的套件、client_random 和 SNI；服务器回 ServerHello、server_random、证书链，还有 ECDHE 参数——**关键是用证书私钥对这些参数签名**，这一步就是身份认证；客户端验证证书后，用 ECDHE 算出 pre-master，再结合两个随机数派生出会话密钥，回 Finished；服务器也回 Finished，之后全部走对称加密。
>
> 这里有两个设计值得说。**两个 random 是为了防重放**——否则同样的 ECDHE 参数会产生同样的密钥，录下来重放就能解。**Finished 里包含之前所有握手报文的摘要**，是为了防止中间人偷偷降级算法。
>
> **证书怎么验证**：证书是三级链——根 CA 预装在系统里、中间 CA 由根签发、服务器证书由中间签发。浏览器做六件事：域名匹配（**现代只看 SAN，不看 CN**）、有效期、用途 EKU、逐级验签直到根 CA、吊销检查、CT 日志。任何一步失败就报错。**中间人拿不到受信任 CA 的签名**，所以伪造不了。
>
> 这里有个真实运维坑：只下发服务器证书、忘了下发中间证书，Chrome 会自动去补所以能打开，但安卓 App 和老 Java 客户端会报证书链错误。
>
> **代价与优化**：主要成本是握手多 1~2 个 RTT，加解密在现代 CPU 上因为 AES-NI 几乎可以忽略。优化手段是 **TLS 1.3**（1-RTT）、**会话复用**（0-RTT）、**OCSP Stapling**（省掉查吊销的往返）、**ECDSA 证书**。
>
> 最后补一个概念：**前向安全**。TLS 1.2 如果用 RSA 密钥交换，攻击者可以「先录流量、等偷到服务器私钥再解」。用 ECDHE 就有前向安全，因为会话密钥由临时密钥算出、用完销毁，证书私钥只签名不参与。TLS 1.3 强制只允许 ECDHE，所以一定有前向安全。

### 追问表

| 追问 | 回答要点 |
|---|---|
| 为什么用混合加密 | 对称解决不了密钥分发；非对称慢 3~4 个数量级且只能加密几百字节 |

## 9.14 速记卡

```
HTTPS = HTTP + TLS，端口 443

解决三件事
  机密性 → 对称加密（AES-GCM / ChaCha20）
  完整性 → AEAD 的 MAC
  身份认证 → 证书 + 非对称签名

为什么混合
  只用对称：密钥没法安全分发
  只用非对称：慢 3~4 个数量级，RSA 一次只能加密 245 字节
  → 非对称只协商密钥，数据全程对称

TLS 1.2 握手（2-RTT）
  ClientHello（套件 + client_random + SNI）
  ServerHello（套件 + server_random）+ Certificate + ServerKeyExchange（ECDHE 参数 + 用证书私钥签名）
  ClientKeyExchange（ECDHE 公钥）→ 双方算 pre-master → master → 会话密钥
  ChangeCipherSpec + Finished（含 transcript hash，防降级）
  ★ 两个 random 防重放；ECDHE 签名做身份认证

TLS 1.3（1-RTT / 0-RTT）
  握手合并 + key_share 提前给 → 1-RTT
  PSK（session ticket）→ 0-RTT（但无前向安全、可重放，只能 GET）
  删掉 RSA 密钥交换 / CBC / RC4 / SHA-1，强制 (EC)DHE

证书链
  根 CA（预装在系统）→ 中间 CA（必须下发）→ 服务器证书
  验证六步：域名(SAN) / 有效期 / EKU / 逐级验签 / 吊销(OCSP) / CT 日志
  ★ 只看 SAN 不看 CN
  ★ 忘下发中间证书 → 安卓 App 和老 Java 报错（Chrome 会 AIA 自动补）

前向安全
  会话密钥来自临时 ECDHE，用完销毁；证书私钥只签名
  TLS1.2+RSA 密钥交换 ❌；TLS1.2+ECDHE ✅；TLS1.3 强制 ✅

HSTS
  Strict-Transport-Security: max-age=31536000; includeSubDomains
  防 SSL Stripping；preload 一旦进入很难移除

性能
  加解密 < 1%（AES-NI）；成本在握手 RTT
  优化：TLS1.3 / 会话复用 / OCSP Stapling / ECDSA 证书

HTTP vs HTTPS
  80 vs 443 / 明文 vs 加密 / 无证书 vs 有证书 / 握手多 1~2 RTT
  ★ HTTPS 还是 Secure Context 门槛（SW、摄像头、地理位置）
```
