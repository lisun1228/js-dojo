## 5.1 一句话结论

**TCP 是可靠的字节流管道**：先建连，字节按序到达，有流量控制和拥塞控制，代价是建连延迟与头部开销。
**UDP 是不可靠的数据报**：不建连，不保证送达和顺序，保留消息边界，可靠性由应用层自己实现。

选型只回答一个问题：数据必须到齐，还是延迟必须够低。

## 5.2 全维度对比表（这张表必须背下来）

| 维度 | TCP | UDP |
|---|---|---|
| **连接** | 面向连接（三次握手/四次挥手） | 无连接，直接发 |
| **可靠性** | 可靠：确认 + 重传 + 校验，保证送达 | 不可靠：发了就不管，可能丢、可能重复 |
| **有序性** | 保证按序（序号 + 重排） | 不保证顺序 |
| **消息边界** | **不保留**（字节流）→ 有「粘包」问题 | **保留**（数据报）→ 一次发一次收 |
| **流量控制** | 有（滑动窗口 rwnd） | 无 |
| **拥塞控制** | 有（慢启动、拥塞避免…） | 无（发了就猛发，可能加剧拥塞） |
| **传输方式** | 单播（一对一） | 单播 / **广播** / **组播** |
| **头部大小** | **20 字节**起（含选项最多 60） | **8 字节**（固定） |
| **首包延迟** | 1 RTT 握手（HTTPS 再加 TLS） | **0 RTT**，直接发 |
| **状态** | 有状态（连接、序号、窗口、定时器） | 无状态（服务端不用记客户端） |
| **服务端并发** | 每连接一个 socket（fd 消耗大） | 一个 socket 收所有（可扛百万级） |
| **适用数据量** | 大量、连续（文件、网页） | 少量、离散（一次一个包） |
| **典型协议** | HTTP/1.1、HTTP/2、FTP、SMTP、SSH、MySQL | DNS、DHCP、NTP、SNMP、QUIC、视频流、游戏 |

## 5.3 头部结构对比（理解「开销差在哪」）

### 5.3.1 TCP 头部 20 字节（最小）

| 字段 | 长度（bit） | 作用 |
|---|---|---|
| 源端口 / 目的端口 | 16 + 16 | 寻址 |
| 序号 seq | 32 | 按字节编号，用于排序与去重 |
| 确认号 ack | 32 | 累计确认，表示下一个期望收到的字节 |
| 首部长度 + 保留 + 9 个标志位 + 窗口 | 4 + 3 + 9 + 16 | 标志位含 SYN/ACK/FIN/RST/PSH/URG；窗口用于流量控制 |
| 校验和 | 16 | 校验首部与数据 |
| 紧急指针 | 16 | 指向带外数据 |
| 选项（可选） | 0–40 字节 | MSS、窗口扩大因子、SACK、时间戳 |

### 5.3.2 UDP 头部 8 字节（固定）

| 字段 | 长度（bit） | 作用 |
|---|---|---|
| 源端口 / 目的端口 | 16 + 16 | 寻址 |
| 长度 | 16 | 首部 + 数据的总长度 |
| 校验和 | 16 | 校验首部与数据 |

**开销**：

- TCP 最小 20 字节、UDP 固定 8 字节，比例 2.5 : 1；传 1 字节数据时，IP 之上分别是 21 与 9 字节
- TCP 头部固定有 8 字节是序号和确认号，这是可靠传输的固定成本
- UDP 头部只有寻址、长度、校验，没有任何与「送达」相关的字段

## 5.4 五个最常被追问的差异

### 5.4.1 「可靠」到底意味着什么

TCP 的「可靠」是四件事的组合（见 04 册）：

1. **不丢**：确认 + 超时重传 + 快速重传
2. **不重**：序号去重
3. **不乱**：序号重排
4. **不错**：校验和

UDP 这四件都不做，但「不做」不等于「一定丢」：丢不丢由链路决定，UDP 只是不检测、不重传、不排序。

### 5.4.2 「消息边界」为什么重要

本地用 node 的 `net` 与 `dgram` 各跑一组（回环地址）：

```text
TCP  client.write('hello') 后紧接 client.write('world')
     服务端 data 事件：["helloworld"]        ← 两次写并成一次读
     client.write(1 MiB)
     服务端 data 事件：17 次，前 5 次各 65536 B，合计 1048576 B   ← 一次写被拆开
UDP  send('hello') 与 send('world')
     服务端 message 事件：["hello", "world"]  ← 两条独立报文
     send(1024 B)
     服务端 message 事件：1 次 1024 B
```

- TCP 只保证字节顺序，不保留「写了几次」：两次写可能合并，一次写可能拆分，接收方必须按长度前缀或分隔符自己切分
- UDP 在不丢包的前提下，一次 `send` 对应一次 `receive`，报文边界由协议保留
- 「粘包」不是 TCP 的缺陷：TCP 没有包的概念，边界是应用层该定义的事（详见 04 册 4.5）

### 5.4.3 为什么 UDP 能一对多

| 方式 | 含义 | TCP | UDP |
|---|---|---|---|
| **单播（unicast）** | 一对一 | ✅ | ✅ |
| **广播（broadcast）** | 一对同子网所有主机 | ❌ | ✅ |
| **组播（multicast）** | 一对一组 | ❌ | ✅ |

TCP 要维护每条连接的序号、窗口和定时器，一对多时无法为每个接收方维护独立状态，所以只能单播。

广播的典型用途：DHCP 客户端还没有 IP，只能发 `255.255.255.255`；ARP 用广播询问同网段主机的 MAC；mDNS 做局域网服务发现。

> 任播（anycast）由 IP 路由选路决定，与传输层选 TCP 还是 UDP 无关；DNS 根服务器常用 UDP anycast。

### 5.4.4 为什么 UDP 服务端能扛百万连接

```text
TCP：每连接一个 socket fd
  100 万连接 → 100 万个 fd，受 ulimit -n 限制（常见默认 1024，需调到百万级）
  每连接还要维护序号、窗口、定时器、收发缓冲区 → 内核内存随连接数线性增长

UDP：一个 socket 收所有
  100 万客户端 → 1 个 fd，内核无连接状态
  连接状态要自己搬到用户态
```

QUIC 的设计动机之一就是用 UDP 绕开「每连接一个 fd + 内核态状态」，把连接管理搬到用户态，便于水平扩展。

### 5.4.5 延迟差多少（具体数字）

| 维度 | TCP | UDP |
|---|---|---|
| **丢包恢复** | 等 RTO 或 3 个重复 ACK | 应用自己决定，可以不等 |
| **队头阻塞** | 有：丢一个段，后到的段也不能交付 | 无：丢一个包不影响其他包 |

按 RTT = 40 ms 折算（算术示例，非实测）：TCP 建连 1 RTT + TLS 1.2 握手 2 RTT ≈ 120 ms 才能发首字节；UDP 首包 0 RTT。

UDP 省下的不是带宽，而是「等握手」和「等重传」这两段等待。

## 5.5 应用场景（要求）

### 5.5.1 TCP 的场景：不能容忍数据缺失

| 场景 | 为什么必须 TCP |
|---|---|
| **网页（HTTP/1.1、HTTP/2）** | HTML/CSS/JS 少一个字节就解析错，必须完整有序 |
| **文件传输（FTP、S3）** | 文件损坏比慢严重得多 |
| **邮件（SMTP/IMAP）** | 内容必须完整 |
| **远程登录（SSH、Telnet）** | 字符顺序错了命令就完全变了 |
| **数据库连接（MySQL、PostgreSQL）** | SQL 语句顺序错一个字节就语法错 |
| **RPC（gRPC、Thrift）** | 参数必须完整 |
| **金融交易** | 丢一笔就是钱 |

**共同点**：数据的完整性优先于及时性。

### 5.5.2 UDP 的场景：不能容忍延迟

| 场景 | 为什么用 UDP | 丢了怎么办 |
|---|---|---|
| **视频直播 / 音视频通话（WebRTC）** | 卡 200ms 比丢一帧难受得多 | 丢帧就丢帧，继续播下一帧 |
| **在线游戏（FPS、MOBA）** | 位置包过期了就没意义 | 用最新位置覆盖，不等旧的 |
| **DNS 查询** | 一个包一问一答，不值得建连 | 超时重发 |
| **DHCP** | 客户端还没 IP，只能广播 | 重发 |
| **NTP 时间同步** | 一次请求一个响应 | 重发 |
| **SNMP 监控** | 周期性采集，偶尔丢一次无所谓 | 下次再采 |
| **日志/埋点上报** | 量大、可丢 | 丢了就算了 |
| **QUIC（HTTP/3）** | 绕开 TCP 队头阻塞 | QUIC 自己在应用层做可靠传输 |

**共同点**：及时性优先于完整性，或者单次数据量小到不值得建连。

### 5.5.3 一个常被搞错的点：视频「流媒体」用哪个？

| 类型 | 协议 | 传输层 |
|---|---|---|
| **点播（YouTube、B 站）** | HLS / DASH over **HTTP** | **TCP** |
| **直播（低延迟）** | WebRTC（UDP）/ RTMP（TCP） | 看方案 |
| **视频会议** | WebRTC | **UDP** |
| **IPTV（运营商）** | 组播 RTP | **UDP** |

- 点播可以缓冲：缓冲几秒就能容忍重传，画质优先，所以走 TCP
- 会议不能缓冲：宁可丢帧也不能卡，所以走 UDP

所以「视频一律用 UDP」是错的，先看点播还是实时。

## 5.6 怎么选（答法）

### 5.6.1 决策树

```text
数据丢了会怎样？
├─ 会出严重问题（文件损坏、SQL 错乱、界面崩）
│    └─→ TCP
└─ 丢了就丢了（下一帧、下一次采样）
     └─ 需要「可靠但又要低延迟」吗？
          ├─ 需要 → 在 UDP 上自己实现可靠性（QUIC / KCP / WebRTC 的 SCTP）
          └─ 不需要 → UDP

另外三个判断：
  ① 要不要一对多（广播/组播）？→ 只能 UDP
  ② 单次数据是不是小到不值得建连？→ UDP 更划算（DNS、NTP）
  ③ 服务端要不要扛百万并发且无状态？→ UDP 更省资源
```

### 5.6.2 决策树之外的工程约束

- 企业网/运营商常对 UDP 限速或封禁（历史上被 P2P、DDoS 滥用），此时只能退回 TCP；WebRTC 在 UDP 不通时会降级到 TCP（TURN over TCP）
- 需要「可靠 + 低延迟」时用成熟的 UDP 可靠性实现（QUIC、KCP），不要从零写重传、拥塞控制

## 5.7 一个反直觉的问题：为什么 HTTP/3 掉头用 UDP

### 5.7.1 先说 HTTP/2 的问题

HTTP/2 用一个 TCP 连接跑所有请求（多路复用），问题出在 TCP 层：

```text
一条 TCP 连接上有 5 个 stream
  → 底层丢了一个 TCP 段
  → TCP 要求按序交付，后到的段即使收到也不能交给应用
  → 5 个 stream 全部卡住，等那一个段重传
  → TCP 层队头阻塞
```

HTTP/2 解决了 HTTP 层的队头阻塞，却把队头阻塞下沉到 TCP 层：HTTP/1.1 开 6 个连接，丢包只卡 1 个；HTTP/2 只有 1 个连接，丢包卡全部。

### 5.7.2 HTTP/3 的解法：把可靠传输搬到 UDP 上

```text
HTTP/1.1:  HTTP → TCP
HTTP/2:    HTTP → TCP（多路复用，共享一个 TCP 的队头阻塞）
HTTP/3:    HTTP → QUIC（基于 UDP，每个 stream 独立可靠）
```

QUIC 在 UDP 之上自己实现：

| 能力 | 说明 |
|---|---|
| **可靠传输** | 自己的序号 + ACK + 重传 |
| **按 stream 独立** | 每个 stream 有独立序号空间，丢包只影响所在 stream |
| **拥塞控制** | 用户态实现，换算法不用等内核升级 |
| **TLS 1.3 内置** | 传输握手与加密握手合并，首次 1-RTT，复用 0-RTT |
| **连接迁移** | 用 Connection ID 而非四元组标识连接，切 WiFi/4G 不断连 |
| **无队头阻塞** | 每个 stream 独立重传，这是它存在的根本原因 |

不改 TCP 而换 UDP 的原因：

| 原因 | 说明 |
|---|---|
| **TCP 在内核里，升级太慢** | 改 TCP 要等操作系统升级，全球设备基数大 |
| **中间设备会干扰** | 防火墙/NAT 对 TCP 的「异常行为」会重置连接（OSSification） |
| **UDP 是「白纸」** | 在用户态实现，浏览器升级就能生效 |

## 5.8 常见坑

| 坑 | 正确说法 |
|---|---|
| 「TCP 比 UDP 安全」 | 都不加密，HTTP 走 HTTPS 才安全；HTTP/3 的 QUIC 内置 TLS 1.3 |
| 「UDP 没有校验和」 | 有 16 位，但可选（IPv4 下可为 0 表示不校验） |
| 「UDP 不分片」 | 也会被 IP 分片，而且没有 MSS 协商，更容易超过 MTU |
| 「QUIC 就是 UDP 版的 TCP」 | QUIC 还带 TLS 1.3、连接迁移、stream 独立，是传输层与加密层的合并 |
| 「TCP 一定比 UDP 慢」 | 大文件、链路稳定时 TCP 的拥塞控制能把链路跑满，裸 UDP 猛发反而丢包 |
| 「选 UDP 就不用管可靠性」 | 业务需要可靠性时，要在应用层自己实现序号、ACK、重传、去重 |

## 5.9 答题模板

### 30 秒版（区别）

- **连接与延迟**：TCP 三次握手，首包 1 个 RTT；UDP 0 RTT，直接发
- **可靠性**：TCP 不丢、不重、不乱、不错；UDP 四件都不做
- **消息边界**：TCP 是字节流，要应用层切分；UDP 是数据报，一次发一次收
- **控制与拓扑**：TCP 有流量控制和拥塞控制，只能单播；UDP 都没有，支持广播和组播
- **开销**：TCP 头部 20 字节起，UDP 固定 8 字节

### 30 秒版（场景与选择）

- 判断标准：数据丢了会出严重问题 → TCP；丢了无所谓或过期就没意义 → UDP
- 既要可靠又要低延迟 → 在 UDP 上做应用层可靠传输（QUIC、KCP、WebRTC 的 SCTP）
- 硬约束：广播/组播只能 UDP；企业网封 UDP 时退回 TCP

### 2 分钟版（完整版）

- **连接与延迟**：TCP 首包要等建连（1 RTT），TLS 再加 1–2 个 RTT；UDP 0 RTT
- **可靠性**：TCP 靠序号、确认、超时重传、快速重传、校验和做到四项保证；UDP 不做，但不代表一定丢
- **消息边界**：TCP 两次写会合并、一次写会拆分（本地 `net` 实测），所以要自己切分；UDP 一次 `send` 对应一次 `receive`
- **控制与拓扑**：TCP 有滑动窗口和拥塞控制，只能单播；UDP 都没有，支持广播和组播
- **选型**：按「数据丢了会怎样」判断；HTTP/3 改用 QUIC 是为了绕开 TCP 层队头阻塞，不只是为了快

### 追问表

| 追问 | 回答要点 |
|---|---|
| TCP 一定可靠吗 | 只保证字节不丢不重不乱不错，不保证对方应用处理了；应用层还要幂等 |
| 为什么 UDP 适合实时 | 没有握手等待、没有队头阻塞、过期数据可以直接丢 |
| 怎么在 UDP 上做可靠传输 | 序号 + ACK + 重传 + 拥塞控制（QUIC/KCP） |
| 同一端口能同时跑 TCP 和 UDP 吗 | 能，TCP 和 UDP 是两个独立的端口空间 |

## 5.10 速记卡

```text
一句话
  TCP 保证你不丢，UDP 保证你不等

六个核心差异
  连接：三次握手 1 RTT / 0 RTT
  可靠：不丢不重不乱不错 / 四件都不管
  边界：字节流要自己切分 / 一次 send 一次 receive
  控制：滑动窗口 + 拥塞控制 / 都没有
  拓扑：只能单播 / 支持广播 + 组播
  头部：20B 起 / 8B 固定

场景
  TCP：网页、文件、邮件、SSH、数据库、gRPC、金融
  UDP：直播会议、游戏、DNS、DHCP、NTP、SNMP、日志、QUIC
  ★ 视频点播（HLS/DASH）走 TCP，别答错

选型
  丢了会出严重问题 → TCP
  丢了无所谓/过期无意义 → UDP
  两者都要 → UDP + 应用层可靠（QUIC/KCP/WebRTC）
  要广播组播 → 只能 UDP
  企业网封 UDP → 退回 TCP

HTTP/3 为什么用 UDP
  HTTP/2 多路复用共享一个 TCP → 丢一个段卡所有 stream（TCP 队头阻塞）
  QUIC 在 UDP 上：stream 独立重传 + TLS 1.3 内置 + 1-RTT/0-RTT + Connection ID 连接迁移
  不改 TCP 的原因：内核升级太慢 + 中间设备干扰（OSSification）
```
