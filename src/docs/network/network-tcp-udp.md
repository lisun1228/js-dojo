## 5.1 一句话结论

**TCP 是「可靠的字节流管道」**：先建连、保证每个字节按序到达、有流量和拥塞控制，代价是延迟和开销。
**UDP 是「不可靠的数据报」**：不建连、不保证送达、不保证顺序、保留了消息边界，代价是可靠性要应用层自己兜。

**选型的本质问题是：你要的是「数据一定到齐」还是「延迟一定够低」。**

## 5.2 全维度对比表（这张表必须背下来）

| 维度 | TCP | UDP |
|---|---|---|
| **连接** | 面向连接（三次握手/四次挥手） | 无连接，直接发 |
| **可靠性** | 可靠：确认 + 重传 + 校验，保证送达 | 不可靠：发了就不管，可能丢、可能重复 |
| **有序性** | 保证按序（序号 + 重排） | 不保证顺序 |
| **消息边界** | **不保留**（字节流）→ 有「粘包」问题 | **保留**（数据报）→ 一次发一次收 |
| **流量控制** | 有（滑动窗口 rwnd） | 无 |
| **拥塞控制** | 有（慢启动、拥塞避免…） | 无（发了就猛发，可能加剧拥塞） |
| **传输方式** | 单播（一对一） | 单播 / **广播** / **组播** |
| **头部大小** | **20 字节**起（含选项最多 60） | **8 字节**（固定） |
| **首包延迟** | 1 RTT 握手（HTTPS 再加 TLS） | **0 RTT**，直接发 |
| **状态** | 有状态（连接、序号、窗口、定时器） | 无状态（服务端不用记客户端） |
| **服务端并发** | 每连接一个 socket（fd 消耗大） | 一个 socket 收所有（可扛百万级） |
| **适用数据量** | 大量、连续（文件、网页） | 少量、离散（一次一个包） |
| **典型协议** | HTTP/1.1、HTTP/2、FTP、SMTP、SSH、MySQL | DNS、DHCP、NTP、SNMP、QUIC、视频流、游戏 |

## 5.3 头部结构对比（理解「开销差在哪」）

### 5.3.1 TCP 头部 20 字节（最小）

```
 0                   1                   2                   3
┌───────────────┬───────────────┬───────────────────────────────┐
│   源端口 (16)  │  目的端口 (16) │                               │
├───────────────┴───────────────┤                               │
│         序号 seq (32)          │                               │
├───────────────────────────────┤                               │
│        确认号 ack (32)         │        ← 20 字节里，一半是序号和确认号
├──────┬───────┬─┬─┬─┬─┬─┬─┬───┤                               │
│首部长度│ 保留  │U│A│P│R│S│F│窗口 (16)│                          │
├──────┴───────┴─┴─┴─┴─┴─┴─┴───┤                               │
│        校验和 (16)             │      紧急指针 (16)             │
└───────────────────────────────┴───────────────────────────────┘
```

### 5.3.2 UDP 头部 8 字节（固定）

```
┌───────────────┬───────────────┐
│   源端口 (16)  │  目的端口 (16) │
├───────────────┼───────────────┤
│   长度 (16)    │  校验和 (16)   │
└───────────────┴───────────────┘
```

**结论**：
- **TCP 头部是 UDP 的 2.5 倍**。传 1 字节数据，TCP 要 21 字节，UDP 只要 9 字节
- TCP 的头部里一半是「序号 + 确认号」——**这就是可靠性的成本**
- UDP 的头部**只有寻址和校验**，没有任何「保证送达」的字段

## 5.4 五个最常被追问的差异

### 5.4.1 「可靠」到底意味着什么

TCP 的「可靠」是**四件事的组合**（见 04 册）：

1. **不丢**：确认 + 超时重传 + 快速重传
2. **不重**：序号去重
3. **不乱**：序号重排
4. **不错**：校验和

**UDP 这四件都不做**，但**不代表 UDP 一定丢**——只是「丢了它不管」。

> **一个关键认知**：UDP 在网络质量好的时候（局域网、同机房）丢包率几乎为 0，**实际体验和 TCP 差不多，但延迟低一半**。这就是为什么游戏、直播、RPC 大量用 UDP。

### 5.4.2 「消息边界」为什么重要

**这是最容易被忽略、但工程上最要命的一条。**

```
TCP：字节流
  send("hello") + send("world")
  → 接收方可能收到 "helloworld" 或 "hello" + "world" 或 "hel" + "loworld"
  → 必须自己做边界（长度前缀 / 分隔符）

UDP：数据报
  sendto("hello") + sendto("world")
  → 接收方一定收到两个独立的报文：["hello", "world"]
  → 天然有边界
```

**这就是「TCP 有粘包，UDP 没有」的根本原因**（详见 04 册 4.5）。

### 5.4.3 为什么 UDP 能一对多

| 方式 | 含义 | TCP | UDP |
|---|---|---|---|
| **单播（unicast）** | 一对一 | ✅ | ✅ |
| **广播（broadcast）** | 一对所有（同子网） | ❌ | ✅ |
| **组播（multicast）** | 一对一组 | ❌ | ✅ |
| **任播（anycast）** | 一对「最近的一个」 | ❌ | ✅（DNS 根服务器就用这个） |

**为什么 TCP 不能广播**：TCP 要维护「连接状态」（序号、窗口），**一对多时无法为每个接收方维护独立状态**。

**UDP 广播/组播的用途**：
- DHCP：客户端还不知道自己 IP，只能广播 `255.255.255.255` 找 DHCP 服务器
- ARP：广播问「谁是 192.168.1.1」
- 局域网服务发现（mDNS/Bonjour）
- 视频会议（一份流发给一组人，省带宽）

### 5.4.4 为什么 UDP 服务端能扛百万连接

```
TCP：每连接一个 socket fd
  100 万连接 → 100 万个 fd → 超过默认 ulimit（1024），要调到百万级
  且每连接要维护：序号、窗口、定时器、收发缓冲区 → 内核内存爆炸

UDP：一个 socket 收所有
  100 万客户端 → 1 个 fd → 无连接状态
  但要把「连接状态」自己搬到用户态（QUIC 就是这么干的）
```

**这就是 QUIC 的设计动机之一**：用 UDP 绕开内核的「每连接一个 fd + 内核态状态」，把连接管理搬到**用户态**，实现更灵活、更容易水平扩展。

### 5.4.5 延迟差多少（具体数字）

| 场景 | TCP | UDP |
|---|---|---|
| 首次发数据 | **1 RTT**（握手）+ 1 RTT（TLS 1.2 是 2） | **0 RTT** |
| 丢包恢复 | 等 RTO（几百 ms）或 3 dup ACK | 应用自己决定（可以不等，继续用新数据） |
| 队头阻塞 | 有（丢一个段，后面全卡） | 无（丢一个包，后面的照收） |
| 头部开销 | 20 B / 包 | 8 B / 包 |

**按 RTT = 40ms 算**：
- TCP + TLS 1.2：握手 1 + TLS 2 = **120ms 才开始发数据**
- UDP：**0ms 就开始发**

**这就是实时场景（游戏、VoIP、直播）用 UDP 的核心原因**——不是「UDP 更快」，而是「**UDP 没有等待**」。

## 5.5 应用场景（要求）

### 5.5.1 TCP 的场景：不能容忍数据缺失

| 场景 | 为什么必须 TCP |
|---|---|
| **网页（HTTP/1.1、HTTP/2）** | HTML/CSS/JS 少一个字节就解析错，必须完整有序 |
| **文件传输（FTP、S3）** | 文件损坏比慢严重得多 |
| **邮件（SMTP/IMAP）** | 内容必须完整 |
| **远程登录（SSH、Telnet）** | 字符顺序错了命令就完全变了 |
| **数据库连接（MySQL、PostgreSQL）** | SQL 语句顺序错一个字节就语法错 |
| **RPC（gRPC、Thrift）** | 参数必须完整 |
| **金融交易** | 丢一笔就是钱 |

**共同点**：**数据的「完整性」优先于「及时性」**。

### 5.5.2 UDP 的场景：不能容忍延迟

| 场景 | 为什么用 UDP | 丢了怎么办 |
|---|---|---|
| **视频直播 / 音视频通话（WebRTC）** | 卡 200ms 比丢一帧难受得多 | 丢帧就丢帧，继续播下一帧 |
| **在线游戏（FPS、MOBA）** | 位置包过期了就没意义 | 用最新位置覆盖，不等旧的 |
| **DNS 查询** | 一个包一问一答，不值得建连 | 超时重发 |
| **DHCP** | 客户端还没 IP，只能广播 | 重发 |
| **NTP 时间同步** | 一次请求一个响应 | 重发 |
| **SNMP 监控** | 周期性采集，偶尔丢一次无所谓 | 下次再采 |
| **日志/埋点上报** | 量大、可丢 | 丢了就算了 |
| **QUIC（HTTP/3）** | 绕开 TCP 队头阻塞 | QUIC 自己在应用层做可靠传输 |

**共同点**：**数据的「及时性」优先于「完整性」**，或者「单次数据量小到不值得建连」。

> **一个精辟的总结**：
> **「TCP 保证你不丢，UDP 保证你不等。」**

### 5.5.3 一个常被搞错的点：视频「流媒体」用哪个？

| 类型 | 协议 | 传输层 |
|---|---|---|
| **点播（YouTube、B 站）** | HLS / DASH over **HTTP** | **TCP** |
| **直播（低延迟）** | WebRTC / RTMP（RTMP 基于 TCP，WebRTC 基于 UDP） | 看方案 |
| **视频会议** | WebRTC | **UDP** |
| **IPTV（运营商）** | 组播 RTP | **UDP** |

**为什么点播用 TCP**：点播可以缓冲（buffer），缓冲几秒就能容忍重传，画质优先。
**为什么会议用 UDP**：不能缓冲（要实时对话），宁可丢帧也不能卡。

**这个区分答出来很加分**——很多人一听「视频」就说 UDP，是错的。

## 5.6 怎么选（答法）

### 5.6.1 决策树

```
数据丢了会怎样？
├─ 会出严重问题（文件损坏、SQL 错乱、界面崩） 
│    └─→ TCP
└─ 丢了就丢了（下一帧、下一次采样）
     └─ 需要「可靠但又要低延迟」吗？
          ├─ 需要 → 在 UDP 上自己实现可靠性（QUIC / KCP / WebRTC 的 SCTP）
          └─ 不需要 → UDP

另外三个判断：
  ① 要不要一对多（广播/组播）？→ 只能 UDP
  ② 单次数据是不是小到不值得建连？→ UDP 更划算（DNS、NTP）
  ③ 服务端要不要扛百万并发且无状态？→ UDP 更省资源
```

### 5.6.2 一句话选型

| 需求 | 选择 |
|---|---|
| 数据必须完整 | TCP |
| 延迟必须低 | UDP |
| 又要完整又要低延迟 | **UDP + 应用层可靠传输**（QUIC/KCP） |
| 一对多 | UDP |
| 穿过严格防火墙 | **TCP（或 UDP 443）** ← 很多企业网封 UDP |

> **最后一个点很重要**：UDP 在很多企业网络/运营商网络里被**限速或封禁**（因为历史上被 P2P、DDoS 滥用）。所以 WebRTC 在 UDP 不通时会**降级到 TCP**（TURN over TCP）。这是工程现实。

## 5.7 一个反直觉的问题：为什么 HTTP/3 掉头用 UDP

**这是本题最高频、也最能体现实力的追问。**

### 5.7.1 先说 HTTP/2 的问题

HTTP/2 用**一个 TCP 连接**跑所有请求（多路复用）。看起来很美，但：

```
一个 TCP 连接上有 5 个 stream（5 个请求的响应）
    ↓
底层丢了一个 TCP 段
    ↓
TCP 的累计确认导致：后面的段即使收到了，也不能交给应用（因为有序性要求）
    ↓
5 个 stream 全部卡住，等那一个段重传
    ↓
这就是【TCP 层队头阻塞】
```

**HTTP/2 解决了「HTTP 层的队头阻塞」**（不用排队等前一个响应），**但把队头阻塞下沉到了 TCP 层，而且更严重了**——HTTP/1.1 时代开 6 个连接，丢包只卡 1 个；HTTP/2 只有 1 个连接，丢包卡全部。

### 5.7.2 HTTP/3 的解法：把可靠传输搬到 UDP 上

```
HTTP/1.1:  HTTP  →  TCP
HTTP/2:    HTTP  →  TCP（多路复用，但共享一个 TCP 的队头阻塞）
HTTP/3:    HTTP  →  QUIC（基于 UDP）  ← 每个 stream 独立可靠
```

**QUIC 在 UDP 之上自己实现了**：

| 能力 | 说明 |
|---|---|
| **可靠传输** | 自己的序号 + ACK + 重传 |
| **按 stream 独立** | 每个 stream 有自己的序号空间，**丢包只影响那一个 stream** |
| **拥塞控制** | 在用户态实现（可以用 BBR 等新算法，不用等内核升级） |
| **TLS 1.3 内置** | 传输握手和加密握手合并，**首次 1-RTT，复用 0-RTT** |
| **连接迁移** | 用 **Connection ID** 标识连接，而不是四元组 → **切 WiFi/4G 不断连** |
| **无需队头阻塞** | 这是它存在的根本原因 |

**为什么不用「改 TCP」而是「换 UDP」？**

| 原因 | 说明 |
|---|---|
| **TCP 在内核里，升级太慢** | 改 TCP 要等操作系统升级，全球几十亿设备，十年都推不完 |
| **中间设备会干扰** | 防火墙/NAT 对 TCP 的「异常行为」会重置连接（OSSification） |
| **UDP 是「白纸」** | 在用户态实现，浏览器升级就能生效 |

> **面试话术**：「HTTP/3 用 UDP 不是为了快，是为了**绕开 TCP 的队头阻塞**。HTTP/2 的多路复用共享一个 TCP 连接，丢一个段就卡住所有 stream，比 HTTP/1.1 开 6 个连接还糟。QUIC 在 UDP 之上自己实现可靠传输，每个 stream 独立重传，还顺带拿到了 1-RTT 握手和连接迁移。之所以不直接改 TCP，是因为 TCP 在内核里，升级要等操作系统，而 UDP 上做用户态实现，浏览器更新就生效。」

## 5.8 常见坑

| 坑 | 正确说法 |
|---|---|
| 「UDP 一定丢包」 | UDP 只是**不保证**，网络好时几乎不丢 |
| 「视频都用 UDP」 | 点播（HLS/DASH）走 HTTP over **TCP**；只有实时会议/直播用 UDP |
| 「TCP 比 UDP 安全」 | 都不加密。**HTTPS 才安全**，HTTP/3 的 QUIC 内置 TLS 1.3 |
| 「UDP 没有校验和」 | 有（16 位），但**可选**（IPv4 下可以为 0 表示不校验） |
| 「TCP 有粘包缺陷」 | TCP 是字节流，没有「包」的概念；**是应用层没做边界** |
| 「UDP 不分片」 | UDP 也会被 IP 分片，而且**没有 MSS 协商**，更容易分片 |
| 「QUIC 就是 UDP 版的 TCP」 | QUIC 还带 TLS 1.3、连接迁移、stream 独立，是「传输层 + 加密层」的合并 |
| 「TCP 一定比 UDP 慢」 | 在「大文件、网络稳定」场景，TCP 的拥塞控制反而能跑满带宽，比裸 UDP 更高效 |
| 「选 UDP 就不用管可靠性」 | 业务需要可靠性时，要在**应用层自己实现**（重传、序号、去重） |

## 5.9 答题模板

### 30 秒版（区别）

> TCP 面向连接、可靠、有序、有流量和拥塞控制，头部 20 字节，首包要 1 个 RTT 握手；UDP 无连接、不保证送达和顺序、没有流控，头部只有 8 字节，直接发。
> 还有一个常被忽略的差异：**TCP 是字节流不保留消息边界，所以有粘包问题；UDP 是数据报，天然有边界**。
> 另外 UDP 支持广播和组播，TCP 只能单播。

### 30 秒版（场景与选择）

> 判断标准是「**数据丢了会怎样**」。丢了会出严重问题（文件、SQL、网页）就用 TCP；丢了无所谓或者过期就没意义（游戏位置、音视频帧、日志）就用 UDP。
> 如果既要可靠又要低延迟，就在 UDP 上自己做可靠传输，QUIC、KCP、WebRTC 都是这个思路。
> 另外两个硬约束：需要广播/组播只能 UDP；企业网封 UDP 时只能退回 TCP。

### 2 分钟版（完整版）

> 我从五个维度对比，然后说选型。
>
> **第一，连接和延迟。** TCP 要三次握手，首包数据要等 1 个 RTT，HTTPS 再加 TLS，TLS 1.2 是 2 个 RTT，所以一个全新的 HTTPS 请求要 3 到 4 个 RTT 才开始传数据。UDP 是 0 RTT，直接发。
>
> **第二，可靠性。** TCP 靠序号加确认、超时重传、快速重传、校验和做到「不丢、不重、不乱、不错」。UDP 这四件都不做，但不代表一定丢——只是丢了它不管。所以 UDP 在网络好的时候体验和 TCP 差不多，但延迟低一半。
>
> **第三，消息边界。** 这条最容易被忽略但工程上最要命。TCP 是字节流，两次 send 可能被合并成一次收，也可能被拆开，所以有「粘包」——本质是应用层没做边界处理，要用长度前缀或分隔符。UDP 是数据报，一次发一次收，天然有边界。
>
> **第四，控制机制。** TCP 有滑动窗口做流量控制、有拥塞控制四阶段；UDP 都没有。所以 UDP 如果猛发会把网络打爆，需要应用层自己限速（比如 WebRTC 的 GCC、QUIC 的拥塞控制）。
>
> **第五，拓扑和开销。** UDP 支持广播和组播，TCP 只能单播——因为 TCP 要为每个连接维护状态，一对多没法做。头部开销 TCP 20 字节、UDP 8 字节。
>
> 选型上，判断标准是「数据丢了会怎样」。网页、文件、邮件、数据库、SSH 必须 TCP；游戏、音视频会议、DNS、DHCP、NTP、日志上报用 UDP。这里有个常见误区：**视频点播（HLS/DASH）其实走 HTTP over TCP**，因为可以缓冲；只有实时会议才用 UDP。
>
> 如果既要可靠又要低延迟，就在 UDP 上自己实现可靠传输——QUIC 就是这么做的。顺带说，这也是 HTTP/3 用 UDP 的原因：HTTP/2 的多路复用共享一个 TCP 连接，丢一个段就卡住所有 stream，比 HTTP/1.1 开 6 个连接还糟。QUIC 在 UDP 上让每个 stream 独立重传，还顺带拿到 1-RTT 握手和连接迁移。

### 追问表

| 追问 | 回答要点 |
|---|---|
| TCP 一定可靠吗 | 保证「不丢不重不乱不错」，但不保证「对方应用处理了」；应用层还要幂等 |
| UDP 一定丢包吗 | 不保证送达，但网络好时几乎不丢 |
| 为什么 UDP 适合实时 | 没有握手等待、没有队头阻塞、过期数据可以直接丢 |
| HTTP/3 为什么用 UDP | 绕开 TCP 层队头阻塞；内核 TCP 升级太慢 |
| 视频点播为什么用 TCP | 可以缓冲，容忍重传，画质优先 |
| TCP 能广播吗 | 不能，一对多无法为每个接收方维护状态 |
| UDP 有校验和吗 | 有 16 位，IPv4 下可选 |
| UDP 会分片吗 | 会，且没有 MSS 协商，更容易分片 |
| 怎么在 UDP 上做可靠传输 | 序号 + ACK + 重传 + 拥塞控制（QUIC/KCP） |
| 什么情况 UDP 会被封 | 企业网/运营商限速（历史 P2P 滥用），WebRTC 会降级到 TCP |
| 同一端口能同时跑 TCP 和 UDP 吗 | 能，TCP 和 UDP 是两个独立的端口空间 |

## 5.10 速记卡

```
一句话
  TCP 保证你不丢，UDP 保证你不等

五个核心差异
  连接：三次握手 1 RTT / 0 RTT
  可靠：不丢不重不乱不错 / 四件都不管
  边界：字节流（粘包）/ 数据报（有边界）
  控制：滑动窗口 + 拥塞控制 / 都没有
  拓扑：只能单播 / 支持广播 + 组播
  头部：20B / 8B

场景
  TCP：网页、文件、邮件、SSH、数据库、gRPC、金融
  UDP：直播会议、游戏、DNS、DHCP、NTP、SNMP、日志、QUIC
  ★ 视频点播（HLS/DASH）走 TCP，别答错

选型
  丢了会出严重问题 → TCP
  丢了无所谓/过期无意义 → UDP
  两者都要 → UDP + 应用层可靠（QUIC/KCP/WebRTC）
  要广播组播 → 只能 UDP
  企业网封 UDP → 退回 TCP

HTTP/3 为什么用 UDP
  HTTP/2 多路复用共享一个 TCP → 丢一个段卡所有 stream（TCP 队头阻塞）
  QUIC 在 UDP 上：stream 独立重传 + TLS1.3 内置 + 1-RTT/0-RTT + Connection ID 连接迁移
  不改 TCP 的原因：内核升级太慢 + 中间设备干扰（OSSification）
```
