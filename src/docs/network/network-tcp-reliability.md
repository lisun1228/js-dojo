## 4.1 一句话结论

TCP 的可靠性由**四件事**共同保证：**序号 + 确认、超时重传、快速重传、校验和**。
在此之上有两套「限速」机制：**流量控制**防止压垮**接收方**（靠 `rwnd`），**拥塞控制**防止压垮**网络**（靠 `cwnd`，分慢启动、拥塞避免、快重传、快恢复四个阶段）。

**一句话区分：流量控制是「别把接收方淹了」，拥塞控制是「别把路堵死」。**

## 4.2 可靠传输的四个机制

### 4.2.1 序号 + 确认（累计确认）

- 每个**字节**都有编号（不是每个报文），初始序号是握手里的 ISN
- 接收方回 ACK，`ack = 期望收到的下一个字节编号`
- **累计确认**：`ack=1001` 表示「1000 及之前的所有字节我都收到了」

**累计确认的好处**：丢一个 ACK 不要紧，后面的 ACK 会覆盖它（幂等）。
**累计确认的坏处**：如果中间丢了一个段，后面的段即使收到了，ACK 也只能停在缺口处（**这就是 TCP 层队头阻塞的根源**）。

```
发送：seg1(1-1000) seg2(1001-2000) seg3(2001-3000)
seg2 在网络中丢了

接收方：
  收到 seg1 → 回 ACK 1001
  收到 seg3 → 回 ACK 1001（还是 1001，因为 1001-2000 缺失）
  收到 seg3 的重复数据……又发一个 ACK 1001
```

### 4.2.2 超时重传 + RTO 怎么算

**RTO（Retransmission Timeout）**：发出去多久没收到 ACK 就重传。

**RTO 不能拍脑袋定**：
- 太小 → 网络只是慢了一点就重传，**加剧拥塞**
- 太大 → 真丢包了要等很久，**体验差**

**RFC 6298 的算法（Jacobson / Karels）**：

```
第一次测量：SRTT = R,  RTTVAR = R/2
之后每次测量 R'：
  RTTVAR = (1 - β) × RTTVAR + β × |SRTT - R'|      β = 1/4
  SRTT   = (1 - α) × SRTT   + α × R'               α = 1/8
  RTO    = SRTT + 4 × RTTVAR
```

**为什么用「平滑 + 方差」而不是「平均值」**：网络 RTT 波动大时，平均值会低估抖动，导致误重传。**加上 4 倍方差，就是「平均值 + 波动余量」**。

**Karn 算法**：**重传过的报文不能用来算 RTT**。因为你分不清收到的 ACK 是对第一次发的还是重传的（ACK 歧义），用它算会把 RTT 算小，导致 RTO 越来越小、重传越来越多（雪崩）。

**重传的退避**：每次重传失败，RTO **翻倍**（指数退避），直到达到上限或重传次数用完。

### 4.2.3 快速重传（不用等超时）

**问题**：等 RTO 太久了（可能几百毫秒到几秒）。有没有更快的办法？

**答案**：如果接收方连续发来**多个相同的 ACK**，说明「有个段丢了，后面的一直在到」。

```
发送：seg1 seg2 seg3 seg4 seg5
seg2 丢了

接收方：
  收 seg1 → ACK 1001
  收 seg3 → ACK 1001   ← 第 1 个重复 ACK（dup ACK #1）
  收 seg4 → ACK 1001   ← 第 2 个（dup ACK #2）
  收 seg5 → ACK 1001   ← 第 3 个（dup ACK #3）
                          ★ 发送方收到 3 个重复 ACK，立刻重传 seg2，不等 RTO
```

**触发条件**：收到 **3 个重复 ACK**（`dupthresh = 3`）。

**为什么是 3 而不是 1**：因为**乱序**也会产生重复 ACK。如果只收到 1~2 个就重传，会把「正常乱序」误判成丢包，做无用重传。3 是个经验值，在「快速发现」和「避免误判」之间取平衡。

**SACK（选择性确认）**：现代 TCP 支持在 ACK 里告诉发送方「我收到了哪些区间」，这样发送方可以精确重传缺失的段，而不是重传缺口之后的全部。（`net.ipv4.tcp_sack`）

### 4.2.4 校验和

TCP 头里有 16 位校验和，覆盖「TCP 头 + 数据 + 伪首部（源 IP、目的 IP、协议号、TCP 长度）」。

**为什么要包含 IP 地址（伪首部）**：防止「报文被错误路由到别的主机」这种情况被当成有效数据。

**注意**：TCP 校验和只能**发现**错误，不能纠正。发现错误就丢弃，等对方重传。

## 4.3 滑动窗口与流量控制

### 4.3.1 为什么需要窗口

如果「发一个段 → 等 ACK → 再发下一个」（停等协议），吞吐量会被 RTT 卡死：

```
吞吐量 = 窗口大小 / RTT
窗口 = 1 个段（1460 B），RTT = 40 ms
→ 吞吐量 = 1460 / 0.04 ≈ 36 KB/s   ← 太慢了
```

**用窗口**：一次可以发多个段，不用等每个都确认。

```
窗口 = 65535 B（老式最大值），RTT = 40 ms
→ 吞吐量 = 65535 / 0.04 ≈ 1.6 MB/s
```

**这就是「带宽时延积（BDP）」的概念**：

```
BDP = 带宽 × RTT
例：100 Mbps × 40 ms = 4 Mbit = 500 KB
```

**要让链路跑满，窗口必须 ≥ BDP**。所以高带宽高延迟的链路（跨国）需要**窗口缩放（Window Scaling）**——把 16 位窗口字段左移最多 14 位，最大到 1 GB。

### 4.3.2 发送窗口的四个区间

```
已发已确认   已发未确认      可发未发        不可发
[=========][///////////][           ]|[          ]
           ↑           ↑           ↑
        ack 位置    已发送边界    窗口右边界
           └──── 发送窗口 ────────┘
```

- 收到 ACK → 窗口左边界右移（**窗口滑动**）
- 应用写入数据 → 可发数据增加
- 接收方通告新窗口 → 窗口右边界可能变

### 4.3.3 流量控制：接收方说「我还能收多少」

接收方在每个 ACK 里带 `window` 字段 = **「我的接收缓冲区还剩多少空间」**。

发送方必须保证：

```
已发未确认的数据量 ≤ min(rwnd, cwnd)
                       ↑      ↑
                    接收方   网络
                    通告窗口  拥塞窗口
```

**取两者较小值**——这是理解两套限速机制关系的关键。

**零窗口（Zero Window）**：

```
接收方缓冲区满 → 通告 window = 0
    ↓
发送方停止发送，但启动「零窗口探测（Zero Window Probe）」
    ↓ 定期（指数退避）发 1 字节的探测包
接收方缓过来 → 通告 window > 0
    ↓
发送方恢复
```

**为什么需要探测**：如果「窗口更新」的 ACK 丢了，双方会**永久死锁**——发送方以为窗口是 0，接收方以为发送方知道窗口开了。

### 4.3.4 糊涂窗口综合征（SWS）与 Nagle / 延迟 ACK

**SWS（Silly Window Syndrome）**：窗口只剩几十字节时就通告出去，导致发送方发一堆极小的段，头部开销远大于数据。

**两个方向的解法**：

| 方向 | 解法 |
|---|---|
| **接收方**（不要通告小窗口） | 窗口小于 `min(MSS, 缓冲区一半)` 时，通告 0，等空间够了再通告 |
| **发送方**（不要发小包） | **Nagle 算法** |

**Nagle 算法**：

```
规则：如果还有「已发未确认」的小包，就把新的小数据攒着，等 ACK 回来再一起发
      （只有「满 MSS 的包」或「所有数据都确认了」才立即发）
```

**延迟 ACK**：接收方不立即回 ACK，等 40~200ms，看能不能「捎带」在反向数据里，或者一次确认多个段。

**⚠️ 经典坑：Nagle + 延迟 ACK 互相拖累**

```
发送方（开了 Nagle）：有个小包没被 ACK，所以新数据攒着不发
接收方（开了延迟 ACK）：收到数据不立即 ACK，等 200ms 看有没有更多
    ↓
发送方等 ACK 才能发 → 接收方等数据才发 ACK
    ↓
死锁 200ms，然后才解开
```

**表现**：某些「请求-响应」型小包应用（比如实时游戏、SSH、某些 RPC）出现**固定 40~200ms 的延迟**。

**解法**：`TCP_NODELAY` 关掉 Nagle。

```js
// Node.js
socket.setNoDelay(true);

// 浏览器 fetch 默认已开启 NODELAY（无法关闭）
```

> **面试话术**：「Nagle 是为了减少小包，延迟 ACK 是为了减少 ACK 包，本意都是好的，但两者一起用会互相等——发送方等 ACK 才发下一个，接收方等数据才回 ACK。表现就是某些小包交互出现固定 200ms 延迟。解法是 `TCP_NODELAY`。」

## 4.4 拥塞控制（核心）

### 4.4.1 为什么需要拥塞控制

**流量控制只管两端**，但**中间的网络也会堵**。

```
发送方 1 Gbps ──→ [ 路由器 100 Mbps ] ──→ 接收方
                    ↑
              这里是瓶颈，发送方不知道
```

如果发送方一直按接收方的窗口猛发，**路由器缓冲区会溢出 → 大量丢包 → 全网雪崩**（1986 年互联网真的发生过「拥塞崩溃」，吞吐量掉了 1000 倍，这才有了拥塞控制）。

**拥塞控制的核心思想**：**发送方自己维护一个「拥塞窗口 cwnd」，通过「丢包」来探测网络容量，动态调整发送速率。**

### 4.4.2 三个关键变量

| 变量 | 谁维护 | 含义 |
|---|---|---|
| **cwnd**（拥塞窗口） | **发送方** | 我估计网络能承受多少（**动态探测**） |
| **ssthresh**（慢启动阈值） | 发送方 | 慢启动和拥塞避免的分界点 |
| **rwnd**（接收窗口） | 接收方（通告） | 接收方缓冲区还剩多少 |

**实际发送窗口 = min(cwnd, rwnd)**。

### 4.4.3 四个阶段（必须能画图讲）

```
cwnd
  ↑
  │                                      ╱│
  │                                   ╱   │  ← 拥塞避免（线性增长）
  │                                ╱      │
  │                          ╱────────────┤ ssthresh
  │                    ╱   ╱              │
  │              ╱  ╱                     │
  │        ╱ ╱                            │  ← 慢启动（指数增长）
  │  ╱ ╱                                  │
  └──────────────────────────────────────→ 时间
    ↑
  cwnd 从 1 个 MSS 开始，每 RTT 翻倍
```

#### ① 慢启动（Slow Start）

**名字有误导性——它一点都不慢，是「指数增长」。**

```
cwnd 初始 = 1 MSS（RFC 5681 允许 2~4，RFC 6928 建议 10）
每收到 1 个 ACK，cwnd += 1 MSS
→ 效果：每经过 1 个 RTT，cwnd 翻倍：1 → 2 → 4 → 8 → 16 ...
```

**为什么叫「慢启动」**：相对于「一开始就发满窗口」而言，它是「慢慢开始」的——**从 1 个 MSS 起步**。

**什么时候结束**：`cwnd >= ssthresh` 时，转入拥塞避免。

**初始 ssthresh 很大**（比如 65535 或更大），所以慢启动会持续好几个 RTT。

#### ② 拥塞避免（Congestion Avoidance）

```
每经过 1 个 RTT，cwnd += 1 MSS（线性增长）
实现上：每收到 1 个 ACK，cwnd += MSS × MSS / cwnd  （即每个 ACK 加一点点）
```

**为什么从指数改线性**：已经接近估计的容量了，要谨慎试探。

#### ③ 快重传（Fast Retransmit）

**触发条件**：收到 **3 个重复 ACK**（不是超时）。

**动作**：立即重传丢失的段，**不等 RTO**。

#### ④ 快恢复（Fast Recovery）

**关键区别：`cwnd` 要不要回到 1？**

| 触发方式 | ssthresh | cwnd | 后续阶段 |
|---|---|---|---|
| **超时重传**（严重拥塞） | `cwnd / 2` | **回到 1 MSS** | **回到慢启动** |
| **3 个重复 ACK**（轻微拥塞） | `cwnd / 2` | **降到 ssthresh**（不回到 1） | **直接进拥塞避免** |

**为什么区别对待**：
- **超时**说明「严重到连 ACK 都回不来了」，网络可能严重拥塞 → 保守，从头慢慢来
- **3 个重复 ACK** 说明「后面的包还能到，只是丢了一个」→ 网络没那么糟 → 不用回到 1，直接减半继续

**这就是「快恢复」的含义：不用回到慢启动，快速恢复发送速率。**

### 4.4.4 完整推演（这道题会算就赢一半）

假设初始 `cwnd = 1 MSS`，`ssthresh = 8 MSS`：

```
轮次   事件                        cwnd       阶段
─────────────────────────────────────────────────────
RTT1   发 1 个，收 1 个 ACK          2        慢启动（指数）
RTT2   发 2 个，收 2 个 ACK          4        慢启动
RTT3   发 4 个，收 4 个 ACK          8        慢启动 → 达到 ssthresh
RTT4   发 8 个，收 8 个 ACK          9        拥塞避免（线性 +1）
RTT5                                 10       拥塞避免
RTT6                                 11       拥塞避免
...
RTT10                                15       拥塞避免
        ┌── 此时发生【超时】
        │   ssthresh = 15/2 = 7（向下取整）
        │   cwnd = 1
        └→ 回到慢启动
RTT11                                2        慢启动
RTT12                                4        慢启动
RTT13                                7        慢启动 → 达到 ssthresh（7）
RTT14                                8        拥塞避免
...

另一种分支：RTT10 时收到 3 个重复 ACK（而不是超时）
        ssthresh = 15/2 = 7
        cwnd = 7（= ssthresh，不回到 1）
        → 直接进拥塞避免
RTT11                                8        拥塞避免
```

**记住这张表的三个关键数字**：
1. 超时：`ssthresh = cwnd/2`，`cwnd = 1`
2. 三个重复 ACK：`ssthresh = cwnd/2`，`cwnd = ssthresh`
3. 慢启动每 RTT **×2**，拥塞避免每 RTT **+1**

### 4.4.5 四代算法的演进（加分项）

| 算法 | 年份 | 核心改进 | 问题 |
|---|---|---|---|
| **Tahoe** | 1988 | 提出慢启动 + 拥塞避免 + 快重传 | 丢包一律回到 cwnd=1，太保守 |
| **Reno** | 1990 | 加入**快恢复**（3 dup ACK 时不回 1） | 一个窗口多个丢包时，每个丢包都减半，减得太多 |
| **NewReno** | 1995 | 改进快恢复，一个窗口多丢包只减一次 | 仍基于丢包 |
| **CUBIC** | 2008 | 用三次函数增长，**与 RTT 无关**（更公平） | Linux 默认至今 |
| **BBR** | 2016 | **不把丢包当拥塞信号**，直接测量带宽和最小 RTT | Google 提出，在弱网/长肥管道上优势明显 |

**BBR 的思路（值得单独说）**：

传统算法（Reno/CUBIC）的逻辑是「**丢包 = 拥塞 → 降速**」。但在**有一定丢包率的链路**（比如跨国、卫星、WiFi）上，丢包不等于拥塞，降速反而浪费带宽。

BBR 改为**主动测量**：
```
瓶颈带宽（BtlBw）= 一段时间内观测到的最大发送速率
最小 RTT（RTprop）= 一段时间内观测到的最小 RTT
BDP = BtlBw × RTprop
发送速率控制在 BDP 附近
```

**效果**：在高丢包链路上吞吐量能比 CUBIC 高几倍，且**缓冲区占用更低**（不会把路由器队列塞满，降低延迟）。

**前端能感知到的**：YouTube / Google 系服务用 BBR，所以在弱网下视频起播更快。

### 4.4.6 流量控制 vs 拥塞控制（必问对比）

| 维度 | 流量控制 | 拥塞控制 |
|---|---|---|
| **保护谁** | 接收方（别把它缓冲区打爆） | 网络（别把链路堵死） |
| **控制变量** | `rwnd`（接收方通告） | `cwnd`（发送方自己算） |
| **谁知道** | 接收方知道自己的缓冲区 | 发送方只能**猜**网络容量 |
| **信号** | 接收方的窗口字段 | 丢包 / RTT 变大 |
| **作用范围** | 端到端 | 全局（涉及所有经过的路由器） |
| **实际窗口** | `min(rwnd, cwnd)` | 同左 |
| **出问题的表现** | 接收方处理不过来（应用读得慢） | 全网丢包、延迟飙升 |

> **一句话记忆**：「**流量控制是接收方说『我吃不下』，拥塞控制是发送方猜『路堵了』。**」

## 4.5 粘包：TCP 是字节流，没有消息边界

### 4.5.1 为什么会「粘包」

**TCP 是面向字节流的协议**，它**只保证字节顺序，不保留应用层的消息边界**。

```
应用层 write("hello") → write("world")
    ↓
TCP 可能合并成一个段发出："helloworld"
    ↓
接收方 read() 一次读到 "helloworld"  ← 看起来像「粘」在一起了
```

**三个成因**：

| 成因 | 说明 |
|---|---|
| **TCP 本身是字节流** | 根本没有「消息」这个概念 |
| **Nagle 算法** | 把多个小包攒起来一次发，直接合并 |
| **接收方缓冲区** | 一次 `read` 可能读到多个消息，也可能只读到半个 |

**注意**：「粘包」这个词本身是**不准确的**——TCP 没有「包」的概念，谈不上「粘」。准确说法是「**应用层没有做消息边界处理**」。

### 4.5.2 三种解决方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 固定长度** | 每条消息固定 N 字节，不够补齐 | 实现最简单 | 浪费空间、长度不可变 |
| **② 分隔符** | 用特殊字符分隔（如 `\r\n`、`\0`） | 可读性好 | 消息内容里不能出现分隔符（要转义） |
| **③ 长度前缀（最常用）** | 先发 4 字节的长度，再发内容 | 精确、无转义问题 | 需要处理「长度本身也可能被拆开」 |

**长度前缀的实现（最容易写错的地方）**：

```js
// 服务端：发送
function sendMessage(socket, str) {
  const body = Buffer.from(str, 'utf8');
  const header = Buffer.alloc(4);
  header.writeUInt32BE(body.length, 0);       // 4 字节大端长度
  socket.write(Buffer.concat([header, body]));
}

// 服务端：接收（★ 必须处理「半包」，不能假设一次 data 就是一个完整消息）
let buffer = Buffer.alloc(0);

socket.on('data', (chunk) => {
  buffer = Buffer.concat([buffer, chunk]);

  while (true) {
    if (buffer.length < 4) return;                 // 长度头还没收全
    const len = buffer.readUInt32BE(0);
    if (buffer.length < 4 + len) return;           // 消息体还没收全
    const body = buffer.subarray(4, 4 + len);
    buffer = buffer.subarray(4 + len);             // 剩余部分留着下次用
    handleMessage(body.toString('utf8'));
  }
});
```

**三个必须理解的细节**：
1. **`buffer` 必须跨 `data` 事件累积**，不能每次清空
2. **`while` 循环而不是 `if`**：一次 `data` 可能包含多条消息
3. **`subarray` 而不是 `slice`**：`subarray` 是零拷贝视图（Buffer 专用），性能更好

### 4.5.3 为什么 UDP / WebSocket 没有粘包

| 协议 | 为什么没有 |
|---|---|
| **UDP** | 面向**报文**，一个 `sendto` 对应一个 `recvfrom`，**保留消息边界** |
| **WebSocket** | 有自己的**帧协议**，每帧有长度字段和 FIN 标志，天然分隔消息 |
| **HTTP/1.1** | 有 `Content-Length` 或 `Transfer-Encoding: chunked` 来定界 |
| **HTTP/2** | 有 **frame**（9 字节头含长度）+ stream id |

> **面试话术**：「粘包不是 TCP 的缺陷，是应用层没做边界处理。因为 TCP 是字节流，只保证顺序不保证边界。解决方式三种：定长、分隔符、长度前缀，工程上用长度前缀最多。UDP 和 WebSocket 没这个问题，因为前者面向报文、后者有帧协议。」

## 4.6 常见坑

| 坑 | 正确说法 |
|---|---|
| 把「快重传」的触发说成「超时」 | 快重传是**收到 3 个重复 ACK**；超时触发的是**慢启动** |
| 以为超时和快重传对 cwnd 处理一样 | 超时 `cwnd=1`（回慢启动）；快重传 `cwnd=ssthresh`（直接拥塞避免） |
| 把 ssthresh 说成「固定值」 | 它是**动态的**，每次拥塞时设为 `cwnd/2` |
| 把流量控制和拥塞控制混为一谈 | 前者保护接收方（rwnd），后者保护网络（cwnd），**取 min** |
| 说「接收窗口就是 65535 上限」 | 有**窗口缩放**，最大可到 1 GB |
| 说「Nagle 是好的，应该一直开」 | 实时小包场景要 `TCP_NODELAY`，否则和延迟 ACK 互锁 200ms |
| 说「粘包是 TCP 的问题」 | 是**应用层没做边界处理**；UDP/WebSocket 都没有这个问题 |
| 以为 RTT 用平均值算 RTO | 是 `SRTT + 4×RTTVAR`，要加**方差** |
| 用重传过的报文算 RTT | Karn 算法禁止，会导致 ACK 歧义和 RTO 雪崩 |
| 说「丢包一定代表拥塞」 | 无线链路丢包常见，BBR 正是为了不把丢包当拥塞信号 |

## 4.7 答题模板

### 30 秒版（拥塞控制，题 61 的原题）

> TCP 拥塞控制有四个阶段：慢启动、拥塞避免、快重传、快恢复。
> 慢启动时拥塞窗口从 1 个 MSS 开始，每收到一个 ACK 加 1，效果是每 RTT 翻倍；到达 ssthresh 后进入拥塞避免，改成每 RTT 加 1，线性增长。
> 发生**超时**时，ssthresh 减半、cwnd 回到 1，重回慢启动；如果只是收到 **3 个重复 ACK**，说明网络没那么糟，就只把 ssthresh 和 cwnd 都减半，**不进慢启动**，直接进拥塞避免——这就是快重传加快恢复。

### 2 分钟版（完整版）

> 先说为什么需要它。流量控制只管接收方的缓冲区，但中间的路由器也会堵。1986 年互联网真的发生过「拥塞崩溃」，吞吐量掉了三个数量级，所以 TCP 加了拥塞控制。
>
> 核心是发送方维护一个**拥塞窗口 cwnd**，用它来「猜」网络容量。实际发送窗口取 `min(cwnd, rwnd)`——cwnd 是我的估计，rwnd 是接收方通告的。
>
> 四个阶段。**慢启动**从 1 个 MSS 开始，每收到一个 ACK 加 1 个 MSS，效果是每 RTT 翻倍，指数增长。**拥塞避免**在 cwnd 达到 ssthresh 后启动，改成每 RTT 加 1，线性增长。
>
> 然后是两个「出错」分支，这里最容易答错。**如果超时**，说明严重到连 ACK 都回不来，就把 ssthresh 设为 cwnd 的一半、cwnd 回到 1，重新慢启动。**如果收到 3 个重复 ACK**，说明后面的包还能到、只是丢了一个，网络没那么糟，这时触发**快重传**立即重传丢失的段，同时把 ssthresh 和 cwnd 都设成 cwnd 的一半——**不回到 1**，直接进拥塞避免，这就是**快恢复**。
>
> 为什么是 3 个重复 ACK？因为乱序也会产生重复 ACK，1 到 2 个不够区分，3 个是「快速发现」和「避免误判」的平衡。
>
> 再补两点。第一，**RTO 不能拍脑袋定**，要用 `SRTT + 4×RTTVAR`，也就是平均值加四倍方差，而且重传过的报文不能用来算 RTT（Karn 算法），否则会产生 ACK 歧义、RTO 越来越小导致雪崩。第二，现代算法已经不只是 Reno/CUBIC 了，**BBR 不把丢包当拥塞信号**，直接测量瓶颈带宽和最小 RTT，在高丢包链路上吞吐量能高好几倍，YouTube 就用它。

### 追问表

| 追问 | 回答要点 |

## 4.8 速记卡

```
可靠传输四机制
  序号 + 累计确认（ack = 期望的下一个字节）
  超时重传（RTO = SRTT + 4×RTTVAR；Karn：重传报文不算 RTT）
  快速重传（3 个重复 ACK，不等 RTO）
  校验和（含伪首部的 IP 地址）

滑动窗口
  吞吐量 = 窗口 / RTT；要跑满链路需窗口 ≥ BDP = 带宽 × RTT
  窗口缩放：16 位左移最多 14 位 → 最大 1 GB
  实际发送窗口 = min(cwnd, rwnd)
  零窗口 → 零窗口探测（防窗口更新丢失导致死锁）

拥塞控制
  三个变量：cwnd（发送方估）/ ssthresh（阈值）/ rwnd（接收方通告）
  ① 慢启动：cwnd 从 1 起，每 ACK +1 → 每 RTT 翻倍
  ② 拥塞避免：cwnd ≥ ssthresh 后，每 RTT +1（线性）
  ③ 快重传：3 个重复 ACK 立即重传
  ④ 快恢复：ssthresh = cwnd/2，cwnd = ssthresh（不回 1）
  ★ 超时：ssthresh = cwnd/2，cwnd = 1，回慢启动
  ★ 3 dup ACK：ssthresh = cwnd/2，cwnd = ssthresh，进拥塞避免

流量控制 vs 拥塞控制
  流量控制：保护接收方，rwnd，接收方知道
  拥塞控制：保护网络，cwnd，发送方只能猜
  实际窗口 = min(两者)

算法演进
  Tahoe → Reno（加快恢复）→ NewReno → CUBIC（Linux 默认，与 RTT 无关）
  → BBR（不看丢包，测带宽 + 最小 RTT，YouTube 在用）

粘包
  TCP 是字节流，没有消息边界 → 不是「粘」，是应用层没做边界
  三种解法：定长 / 分隔符 / 长度前缀（最常用）
  接收端必须：累积 buffer + while 循环 + subarray
  UDP 面向报文、WebSocket 有帧 → 没这个问题

Nagle × 延迟 ACK
  Nagle 等 ACK 才发小包，延迟 ACK 等数据才回 ACK → 互锁 200ms
  解法：TCP_NODELAY
```
