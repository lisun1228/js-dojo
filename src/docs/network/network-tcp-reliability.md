## 4.1 一句话结论

TCP 的可靠性由四件事保证：**序号 + 确认、超时重传、快速重传、校验和**。在此之上有两套限速机制：**流量控制**防止压垮接收方（`rwnd`），**拥塞控制**防止压垮网络（`cwnd`，含慢启动、拥塞避免、快重传、快恢复四个阶段）。

## 4.2 可靠传输的四个机制

### 4.2.1 序号 + 确认（累计确认）

- 每个**字节**都有编号（不是每个报文），初始序号是握手里的 ISN
- 接收方回 ACK，`ack = 期望收到的下一个字节编号`
- **累计确认**：`ack=1001` 表示 1000 及之前的所有字节都已收到

好处：单个 ACK 丢失不影响确认进度，后续 ACK 会覆盖它。
代价：中间丢一个段时，后面收到的段也只能确认到缺口处——这是 **TCP 层队头阻塞**的根源。

```
发送：seg1(1-1000) seg2(1001-2000) seg3(2001-3000)，seg2 丢失
接收方：收 seg1 → ACK 1001；收 seg3 → ACK 1001（1001-2000 仍缺失）
```

### 4.2.2 超时重传 + RTO 怎么算

**RTO**：发出数据后多久没收到 ACK 就重传。太小会误重传、加剧拥塞；太大则丢包后等待过久。

**RFC 6298（Jacobson / Karels）**：

```
第一次测量：SRTT = R, RTTVAR = R/2
之后每次测量 R'（α = 1/8，β = 1/4）：
  RTTVAR = (1 - β) × RTTVAR + β × |SRTT - R'|
  SRTT   = (1 - α) × SRTT   + α × R'
  RTO    = SRTT + max(G, 4 × RTTVAR)      G = 时钟粒度
```

**为什么要加方差**：RTT 波动大时平均值会低估抖动，导致误重传；`4 × RTTVAR` 就是波动余量。

**Karn 算法**：重传过的报文不参与 RTT 采样。否则分不清 ACK 对应首传还是重传（ACK 歧义），会把 RTT 算小、RTO 越调越小，重传越来越多。

**退避**：每次重传失败，RTO 翻倍，直到上限。

### 4.2.3 快速重传（不用等超时）

接收方连续回多个相同的 ACK，说明缺口前的段已到达、某个段丢了。RFC 5681 对重复 ACK 的定义：发送方有未确认数据、ACK 不携带新数据、SYN/FIN 为 0、ACK 号与通告窗口都不变（或携带新的 SACK 信息）。

```
发送：seg1 seg2 seg3 seg4 seg5，seg2 丢失
接收方：收 seg1 → ACK 1001
        收 seg3 → ACK 1001   ← 第 1 个重复 ACK
        收 seg4 → ACK 1001   ← 第 2 个
        收 seg5 → ACK 1001   ← 第 3 个 → 发送方立即重传 seg2，不等 RTO
```

**触发条件**：收到 **3 个重复 ACK**（`dupthresh = 3`）。

**为什么不是 1 个**：乱序也会产生重复 ACK；1~2 个不足以区分丢包和乱序，3 是「快速发现」与「避免误判」的折中。

**SACK（选择性确认）**：ACK 里携带已收到的区间，发送方只重传缺失段，而不是缺口之后的全部。Linux 开关为 `net.ipv4.tcp_sack`。

### 4.2.4 校验和

TCP 头有 16 位校验和，覆盖 TCP 头、数据和伪首部（源/目的 IP、协议号、TCP 长度）。伪首部让被错误路由到其他主机的报文无法通过校验。

校验和只能发现错误，不能纠正：出错即丢弃，等对端重传。

## 4.3 滑动窗口与流量控制

### 4.3.1 为什么需要窗口

停等协议（发一个段、等一个 ACK）的吞吐量被 RTT 卡死：

```
吞吐量 = 窗口大小 / RTT
窗口 = 1 MSS（1460 B），RTT = 40 ms → 1460 / 0.04 ≈ 36 KB/s
窗口 = 65535 B，       RTT = 40 ms → 65535 / 0.04 ≈ 1.6 MB/s
```

**带宽时延积（BDP）= 带宽 × RTT**，例如 100 Mbps × 40 ms = 4 Mbit = 500 KB。要让链路跑满，窗口必须 ≥ BDP；高带宽高延迟链路因此需要**窗口缩放**：16 位窗口字段左移最多 14 位，上限约 1 GB。

### 4.3.2 发送窗口的四个区间

```
已发已确认   已发未确认      可发未发        不可发
[=========][///////////][           ]|[          ]
           ↑           ↑           ↑
        ack 位置    已发送边界    窗口右边界
           └──── 发送窗口 ────────┘
```

- 收到 ACK → 左边界右移（窗口滑动）
- 应用写入数据 → 可发数据增加
- 接收方通告新窗口 → 右边界可能变化

### 4.3.3 流量控制：接收方说「我还能收多少」

接收方在每个 ACK 的 `window` 字段通告接收缓冲区剩余空间。发送方必须保证：

```
已发未确认的数据量 ≤ min(rwnd, cwnd)
```

`rwnd` 由接收方通告，`cwnd` 由发送方维护——两套限速机制共同决定实际发送窗口。

**零窗口**：缓冲区满 → 通告 `window = 0` → 发送方停止发送并启动**零窗口探测**（指数退避，每次 1 字节）→ 接收方恢复后通告非零窗口 → 发送方继续。

探测的必要性：若「窗口更新」的 ACK 丢失，发送方以为窗口仍是 0、接收方以为对方已知窗口打开，双方永久死锁。

### 4.3.4 糊涂窗口综合征（SWS）与 Nagle / 延迟 ACK

**SWS**：窗口只剩几十字节就通告，发送方随之发大量小段，头部开销远大于数据。

| 方向 | 解法 |
|---|---|
| 接收方（不通告小窗口） | 窗口小于 `min(MSS, 缓冲区一半)` 时通告 0，等空间够了再通告 |
| 发送方（不发小包） | Nagle 算法 |

**Nagle**：还有已发未确认的小包时，把新的小数据攒着，等 ACK 回来一起发；只有满 MSS 的包或所有数据都被确认时才立即发。

**延迟 ACK**：接收方不立即回 ACK，等一个短周期，以便捎带反向数据或合并确认。RFC 1122 要求延迟小于 0.5 s，且满长段流中至少每两个段确认一次；具体等待时间由实现决定。

**Nagle + 延迟 ACK 互相拖累**：

```
发送方（Nagle）：有小包未确认，新数据攒着
接收方（延迟 ACK）：收到数据不立即 ACK，等更多数据
    ↓ 发送方等 ACK 才能发，接收方等数据才回 ACK
    ↓ 每次交互多等一个延迟 ACK 周期
```

请求-响应型小包应用（实时游戏、SSH、部分 RPC）因此出现额外延迟。解法是关掉 Nagle：

```js
socket.setNoDelay(true);   // Node.js；浏览器的 TCP 栈由浏览器控制，JS 无法设置
```

## 4.4 拥塞控制（核心）

### 4.4.1 为什么需要拥塞控制

流量控制只管两端，中间的路由器也会堵：

```
发送方 1 Gbps ──→ [ 路由器 100 Mbps ] ──→ 接收方
                    ↑ 瓶颈，发送方不知道
```

发送方若一直按接收窗口发送，路由器缓冲区溢出 → 大量丢包 → 全网吞吐崩塌。1986 年互联网出现过这种「拥塞崩溃」，吞吐量下降约三个数量级（Jacobson, SIGCOMM '88）。

**核心思想**：发送方维护拥塞窗口 `cwnd`，以丢包为信号探测网络容量，动态调整发送速率。

### 4.4.2 三个关键变量

| 变量 | 谁维护 | 含义 |
|---|---|---|
| **cwnd** | 发送方 | 估计网络能承受的发送量（动态探测） |
| **ssthresh** | 发送方 | 慢启动与拥塞避免的分界点 |
| **rwnd** | 接收方（通告） | 接收缓冲区剩余空间 |

实际发送窗口 = `min(cwnd, rwnd)`。

### 4.4.3 四个阶段

```
cwnd
  ↑                                      ╱│
  │                                   ╱   │  拥塞避免（线性）
  │                                ╱      │
  │                          ╱────────────┤ ssthresh
  │                    ╱   ╱              │
  │              ╱  ╱                     │
  │        ╱ ╱                            │  慢启动（指数）
  │  ╱ ╱                                  │
  └──────────────────────────────────────→ 时间
```

#### ① 慢启动（Slow Start）

```
初始 cwnd = 1 MSS（教材推演值；RFC 5681 的 IW 为 2~4 MSS，RFC 6928 建议 10 MSS）
每收到 1 个 ACK，cwnd += 1 MSS
→ 每经过 1 个 RTT，cwnd 翻倍：1 → 2 → 4 → 8 ...
```

名字里的「慢」是相对于「一开始就发满窗口」：从很小的窗口起步，实际增长是指数的。

`ssthresh` 初始值设得任意大（RFC 5681），所以慢启动会持续若干 RTT；`cwnd >= ssthresh` 时转入拥塞避免。

#### ② 拥塞避免（Congestion Avoidance）

```
每经过 1 个 RTT，cwnd += 1 MSS（线性）
实现：每收到 1 个 ACK，cwnd += MSS × MSS / cwnd
```

已接近估计容量，改为谨慎试探。

#### ③ 快重传（Fast Retransmit）

触发条件见 4.2.3：收到 3 个重复 ACK。动作是立即重传丢失段，不等 RTO；随后按 ④ 调整窗口。

#### ④ 快恢复（Fast Recovery）

| 触发方式 | ssthresh | cwnd | 后续阶段 |
|---|---|---|---|
| 超时重传 | `max(FlightSize/2, 2·MSS)` | **1 MSS** | 慢启动 |
| 3 个重复 ACK | `max(FlightSize/2, 2·MSS)` | **ssthresh + 3·MSS** | 快恢复 → 拥塞避免 |

`FlightSize` 是已发送未确认的数据量，通常近似当时的 `cwnd`。快恢复期间每多收到一个重复 ACK，`cwnd` 再 +1 MSS（膨胀）；收到确认新数据的 ACK 后，`cwnd` 回落到 `ssthresh`（deflate）。

区别对待的原因：超时说明连 ACK 都回不来，拥塞更严重，从头慢启动；3 个重复 ACK 说明后续段仍能到达，只是丢了一个，减半后继续即可。

「快恢复」即：不回到慢启动，直接把发送速率降到减半后的水平继续。

### 4.4.4 完整推演

初始 `cwnd = 1 MSS`，`ssthresh = 8 MSS`。下表按教材简化：拥塞避免每 RTT +1 MSS，快恢复直接记 `cwnd = ssthresh`。

```
轮次   事件                     cwnd   阶段
──────────────────────────────────────────────
RTT1   发 1 收 1 ACK             2     慢启动
RTT2   发 2 收 2 ACK             4     慢启动
RTT3   发 4 收 4 ACK             8     慢启动 → 达到 ssthresh
RTT4   发 8 收 8 ACK             9     拥塞避免（每 RTT +1）
RTT5..RTT10                      15    拥塞避免
        ┌ 超时：ssthresh = 15/2 = 7（向下取整），cwnd = 1
        └→ 回慢启动
RTT11                            2     慢启动
RTT12                            4     慢启动
RTT13                            7     慢启动 → 达到 ssthresh（7）
RTT14                            8     拥塞避免

另一分支：RTT10 收到 3 个重复 ACK
        ssthresh = 15/2 = 7，cwnd = 7（不回 1）→ 直接拥塞避免
RTT11                            8     拥塞避免
```

### 4.4.5 四代算法的演进

| 算法 | 年份 | 核心改进 | 局限 |
|---|---|---|---|
| **Tahoe** | 1988 | 提出慢启动、拥塞避免、快重传 | 丢包一律回到 `cwnd = 1` |
| **Reno** | 1990 | 加入快恢复：3 个重复 ACK 时不回 1 | 一个窗口多个丢包时，每个丢包都减半 |
| **NewReno** | 1995 提出，RFC 6582 | 用部分 ACK 处理一个窗口多丢包，只减一次 | 仍以丢包为信号 |
| **CUBIC** | 2008 论文，RFC 8312 | 三次函数增长，与 RTT 无关 | 仍以丢包为信号；Linux 默认 |
| **BBR** | 2016 | 测量瓶颈带宽与最小 RTT，不以丢包为唯一信号 | — |

BBR 与 Reno/CUBIC 的分歧：后者把丢包当拥塞信号，在跨国、卫星、WiFi 等有随机丢包的链路上会误降速。BBR 改为主动测量：

```
瓶颈带宽 BtlBw = 一段时间内观测到的最大发送速率
最小 RTT RTprop = 一段时间内观测到的最小 RTT
BDP = BtlBw × RTprop
```

发送速率控制在 BDP 附近，不靠填满路由器队列来探测容量，因此排队延迟更低。BBR 由 Google 提出。

### 4.4.6 流量控制 vs 拥塞控制（必问对比）

| 维度 | 流量控制 | 拥塞控制 |
|---|---|---|
| **保护谁** | 接收方（别把缓冲区打爆） | 网络（别把链路堵死） |
| **控制变量** | `rwnd`（接收方通告） | `cwnd`（发送方自己算） |
| **谁知道** | 接收方知道自己的缓冲区 | 发送方只能探测网络容量 |
| **信号** | 接收方的窗口字段 | 丢包 / RTT 变大 |
| **作用范围** | 端到端 | 全路径（涉及所有经过的路由器） |
| **出问题的表现** | 接收方处理不过来（应用读得慢） | 全网丢包、延迟飙升 |

## 4.5 粘包：TCP 是字节流，没有消息边界

### 4.5.1 为什么会「粘包」

TCP 只保证字节顺序，不保留应用层消息边界。

```
应用层 write("hello") → write("world")
TCP 可能合并成一个段发出："helloworld"
接收方一次 read 读到 "helloworld"
```

| 成因 | 说明 |
|---|---|
| TCP 本身是字节流 | 没有「消息」这个概念 |
| Nagle 算法 | 把多个小包攒起来一次发，直接合并 |
| 接收方缓冲区 | 一次 `read` 可能读到多个消息，也可能只读到半个 |

「粘包」本身不是准确说法：TCP 没有「包」的概念，问题是应用层没做消息边界处理。

### 4.5.2 三种解决方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 固定长度** | 每条消息固定 N 字节，不够补齐 | 实现最简单 | 浪费空间、长度不可变 |
| **② 分隔符** | 用特殊字符分隔（如 `\r\n`、`\0`） | 可读性好 | 消息内容里不能出现分隔符（要转义） |
| **③ 长度前缀（最常用）** | 先发 4 字节的长度，再发内容 | 精确、无转义问题 | 需要处理「长度本身也可能被拆开」 |

```js
// 发送
function sendMessage(socket, str) {
  const body = Buffer.from(str, 'utf8');
  const header = Buffer.alloc(4);
  header.writeUInt32BE(body.length, 0);       // 4 字节大端长度
  socket.write(Buffer.concat([header, body]));
}

// 接收：必须处理半包，不能假设一次 data 就是一个完整消息
let buffer = Buffer.alloc(0);

socket.on('data', (chunk) => {
  buffer = Buffer.concat([buffer, chunk]);

  while (true) {
    if (buffer.length < 4) return;                 // 长度头还没收全
    const len = buffer.readUInt32BE(0);
    if (buffer.length < 4 + len) return;           // 消息体还没收全
    const body = buffer.subarray(4, 4 + len);
    buffer = buffer.subarray(4 + len);             // 剩余部分留着下次用
    handleMessage(body.toString('utf8'));
  }
});
```

三个要点：`buffer` 必须跨 `data` 事件累积；用 `while` 而不是 `if`，因为一次 `data` 可能包含多条消息；`subarray` 返回共享内存的视图（零拷贝），`slice` 已废弃。

### 4.5.3 为什么 UDP / WebSocket 没有粘包

| 协议 | 为什么没有 |
|---|---|
| **UDP** | 面向**报文**，一个 `sendto` 对应一个 `recvfrom`，保留消息边界 |
| **WebSocket** | 有自己的**帧协议**，每帧有长度字段和 FIN 标志，天然分隔消息 |
| **HTTP/1.1** | 有 `Content-Length` 或 `Transfer-Encoding: chunked` 来定界 |
| **HTTP/2** | 有 **frame**（9 字节头含长度）+ stream id |

## 4.6 常见坑

| 坑 | 正确说法 |
|---|---|
| 快重传由「超时」触发 | 由 **3 个重复 ACK** 触发；超时走慢启动 |
| 超时和快重传对 cwnd 处理相同 | 超时 `cwnd = 1`；快重传 `cwnd = ssthresh + 3·MSS`，随后回落到 `ssthresh` |
| 把 ssthresh 说成「固定值」 | 它是**动态的**，每次拥塞设为 `max(FlightSize/2, 2·MSS)` |
| 把流量控制和拥塞控制混为一谈 | 前者保护接收方（`rwnd`），后者保护网络（`cwnd`），实际窗口取 min |
| 说「接收窗口就是 65535 上限」 | 有**窗口缩放**，上限约 1 GB |
| 以为 RTT 用平均值算 RTO | 是 `SRTT + max(G, 4×RTTVAR)`，要加**方差** |
| 用重传过的报文算 RTT | Karn 算法禁止，会造成 ACK 歧义与 RTO 雪崩 |
| 说「丢包一定代表拥塞」 | 无线链路随机丢包常见；BBR 不以丢包为唯一信号 |

## 4.7 答题模板

### 30 秒版（拥塞控制四阶段）

- 四个阶段：慢启动、拥塞避免、快重传、快恢复。
- 慢启动：`cwnd` 从 1 MSS 起，每 ACK +1，每 RTT 翻倍；到达 `ssthresh` 后转入拥塞避免。
- 拥塞避免：每 RTT +1，线性增长。
- 超时：`ssthresh = max(FlightSize/2, 2·MSS)`、`cwnd` 回到 1，重回慢启动。
- 3 个重复 ACK：触发快重传；同样设置 `ssthresh`，`cwnd` 设为 `ssthresh + 3·MSS`，收到新 ACK 后回落到 `ssthresh`，即快恢复。

### 2 分钟版

- 动机：流量控制只保护接收方，中间路由器也会堵；拥塞控制用 `cwnd` 估计网络容量，实际窗口取 `min(cwnd, rwnd)`。
- 增长与分界：慢启动指数增长，`ssthresh` 是转入线性增长（拥塞避免）的分界点，具体数值见 4.4.3。
- 丢包响应：超时按严重拥塞处理（`cwnd = 1`，回慢启动）；3 个重复 ACK 按轻微拥塞处理，触发快重传 + 快恢复。
- RTT/RTO：`RTO = SRTT + max(G, 4·RTTVAR)`；重传过的报文不参与 RTT 采样（Karn）。
- 算法演进：Reno → NewReno → CUBIC（Linux 默认，增长与 RTT 无关）→ BBR（测瓶颈带宽与最小 RTT，不以丢包为唯一信号）。

## 4.8 速记卡

```
可靠传输
  序号 + 累计确认（ack = 期望的下一个字节）
  超时重传：RTO = SRTT + max(G, 4×RTTVAR)；Karn：重传报文不采样
  快速重传：3 个重复 ACK，不等 RTO
  校验和：含伪首部的 IP 地址

窗口
  吞吐量 = 窗口 / RTT；跑满链路需窗口 ≥ BDP = 带宽 × RTT
  窗口缩放：16 位左移最多 14 位，上限约 1 GB
  实际窗口 = min(cwnd, rwnd)；零窗口 → 零窗口探测

拥塞控制
  变量：cwnd（发送方估）/ ssthresh（阈值）/ rwnd（接收方通告）
  慢启动：1 MSS 起，每 ACK +1，每 RTT 翻倍，到 ssthresh 转拥塞避免
  拥塞避免：每 RTT +1（线性）
  快重传：3 个重复 ACK
  快恢复：ssthresh = max(FlightSize/2, 2·MSS)，cwnd = ssthresh + 3·MSS → 新 ACK 后回落
  超时：同上 ssthresh，cwnd = 1，回慢启动

算法演进
  Tahoe → Reno（快恢复）→ NewReno（一个窗口多次丢包只减一次）
  → CUBIC（Linux 默认，与 RTT 无关）→ BBR（测带宽 + 最小 RTT）

粘包
  TCP 是字节流，没有消息边界 → 应用层定界
  定长 / 分隔符 / 长度前缀（最常用）；接收端累积 buffer + while + subarray
  UDP 面向报文、WebSocket 有帧 → 无此问题

Nagle × 延迟 ACK
  Nagle 等 ACK 才发小包，延迟 ACK 等数据才回 ACK → 互相等待一个 ACK 周期
  解法：TCP_NODELAY
```
