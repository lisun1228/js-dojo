# 网络 · 07 HTTP 版本演进：HTTP/1.0 → 1.1 → 2 → 3

> 本册覆盖：HTTP 各版本区别、HTTP/1.1 怎么解决 HTTP/1.0 的问题
> 题单只给了四个版本的四个关键词。**这道题真正的考点是「队头阻塞」**——它有三层含义，分别对应三个版本，**能把这三层讲清，这题就满分**。

---

## 7.1 一句话结论

**HTTP/1.0 每次请求建一个 TCP 连接 → HTTP/1.1 用持久连接 + 管线化（但管线化有队头阻塞，实际没人用）→ HTTP/2 用二进制分帧 + 多路复用解决了 HTTP 层的队头阻塞，但把问题下沉成了 TCP 层队头阻塞 → HTTP/3 干脆换掉 TCP，用 QUIC（基于 UDP）让每个 stream 独立可靠。**

一句话主线：**「所有版本演进都在解决同一个问题——如何在一个连接上高效并发地传多个资源。」**

---

## 7.2 演进总表（必背）

| 维度 | HTTP/1.0（1996） | HTTP/1.1（1997） | HTTP/2（2015） | HTTP/3（2022） |
|---|---|---|---|---|
| **传输层** | TCP | TCP | TCP | **UDP（QUIC）** |
| **连接** | 每请求一个连接 | **持久连接（keep-alive）默认开** | 单连接多路复用 | 单连接多路复用 |
| **并发方式** | 多开连接（浏览器 6 个/域名） | 多开连接 + 管线化（理论） | **一个连接上的多 stream** | 一个连接上的多 stream |
| **报文格式** | 文本 | 文本 | **二进制分帧** | 二进制分帧 |
| **头部压缩** | ❌ | ❌ | **HPACK** | **QPACK** |
| **队头阻塞** | 有（每请求一个连接，反而少） | **HTTP 层有**（管线化） | **TCP 层有** | **基本消除** |
| **服务器推送** | ❌ | ❌ | ✅（**已废弃**） | ❌ |
| **握手延迟** | 1 RTT（TCP） | 1 RTT | 1 RTT | **1 RTT / 复用 0-RTT** |
| **连接迁移** | ❌ | ❌ | ❌ | ✅（Connection ID） |
| **Host 头** | ❌（不支持虚拟主机） | ✅ | ✅（`:authority` 伪头） | ✅ |
| **分块传输** | ❌ | ✅（chunked） | — | — |
| **断点续传** | ❌ | ✅（Range / 206） | ✅ | ✅ |

## 7.3 HTTP/1.0 的问题

| 问题 | 后果 |
|---|---|
| **每个请求新建 TCP 连接** | 每个资源都要 1 次握手（+ TLS），**RTT 成本爆炸**。一个含 30 个资源的页面要 30 次握手 |
| **没有 Host 头** | 一台服务器只能跑一个站点，**不支持虚拟主机**（一个 IP 一个域名） |
| **不支持 Range** | 不能断点续传，视频不能拖进度条 |
| **缓存控制弱** | 只有 `Expires`（绝对时间，受客户端时钟影响）和 `If-Modified-Since`（秒级精度） |
| **不支持分块传输** | 服务端必须知道 `Content-Length` 才能发，无法流式输出 |

**HTTP/1.0 时代前端的应对**：域名分片（把资源分散到 `static1.com`、`static2.com`...），因为浏览器对**单个域名**限制 6 个并发连接，多域名就能突破到 6×N。

## 7.4 HTTP/1.1 的改进（答案）

### 7.4.1 六项核心改进

| 改进 | 说明 | 解决了什么 |
|---|---|---|
| **① 持久连接（keep-alive）** | 默认不关闭 TCP 连接，后续请求复用 | **省掉每个请求的握手 RTT** ← 最关键 |
| **② 管线化（pipelining）** | 可以连续发多个请求，不用等前一个响应 | **理论上省 RTT**，但实际失败（见下） |
| **③ Host 头** | 请求里带域名 | 支持**虚拟主机**（一台服务器跑多个站点） |
| **④ 分块传输（chunked）** | `Transfer-Encoding: chunked`，边生成边发 | 支持**流式输出**（SSR、大文件） |
| **⑤ Range 请求** | 请求部分内容，返回 **206** | **断点续传、视频拖动** |
| **⑥ 缓存增强** | `Cache-Control`、`ETag`、`Vary` | 更精细的缓存控制 |
| （⑦ 新增方法） | PUT、DELETE、OPTIONS、TRACE、CONNECT | RESTful |
| （⑧ 100-continue） | 大文件上传前先问「能不能收」 | 避免白传大 body |

### 7.4.2 管线化为什么失败了（这是重点）

**管线化的设想很美**：

```
不用管线化（普通 keep-alive）：
  请求1 → 等响应1 → 请求2 → 等响应2 → 请求3 → 等响应3
  总时间 = 3 × RTT

用管线化：
  请求1 请求2 请求3 →（连续发出）
  ← 响应1 响应2 响应3
  总时间 ≈ 1 × RTT + 处理时间
```

**但 HTTP/1.1 规定：响应必须「按请求顺序」返回。**

因为 HTTP/1.1 是**文本协议**，没有「消息 ID」这种东西，客户端无法区分「这个响应是对哪个请求的」。所以只能靠**顺序**来对应。

**这就导致了队头阻塞**：

```
请求1 请求2 请求3 连续发出
响应1 很慢（比如要查数据库 2 秒）
  → 响应2、响应3 即使已经生成好了，也必须等着
  → 客户端一个字节都收不到
```

**为什么浏览器实际关闭了管线化**：

| 原因 | 说明 |
|---|---|
| **队头阻塞没解决** | 一个慢请求卡住后面全部 |
| **中间设备兼容性差** | 很多代理/服务器不支持管线化，会出错 |
| **收益不明显** | 现代浏览器开 6 个连接已经能并行，管线化收益小 |
| **无法重试** | 管线化中某个请求失败，后面的响应无法对应 |

> **面试话术**：「HTTP/1.1 引入了管线化，理论上可以连续发多个请求省 RTT。但**响应必须按请求顺序返回**——因为文本协议没有请求 ID，只能靠顺序对应。所以一个慢请求会卡住后面所有响应，这就是 HTTP/1.1 的应用层队头阻塞。再加上代理兼容性差，浏览器实际都默认关闭了。」

### 7.4.3 keep-alive 的实际限制

**浏览器对同一域名最多开 6 个并发 TCP 连接**（Chrome/Firefox，这是实现约定，不是协议规定）。

```
一个页面有 30 个资源
    ↓
6 个连接，每个连接串行处理 5 个资源
    ↓
如果某个资源很慢，它所在的连接就被占住
```

**这就是 HTTP/1.1 时代「域名分片」的原因**：`a.com`、`b.com`、`c.com` 各 6 个连接 = 18 并发。

**（HTTP/2 之后这个手段反而有害，见 7.8）**

## 7.5 HTTP/2 的核心改进

### 7.5.1 二进制分帧（一切的基础）

**HTTP/1.1 是文本协议**，报文是 `GET /path HTTP/1.1\r\nHost: ...`。
**HTTP/2 把一切切成「帧（frame）」**，每个帧有统一的 9 字节头：

```
┌──────────────────────────────────────────────┐
│ Length (24)  │ Type (8) │ Flags (8)          │
├──────────────────────────────────────────────┤
│ R │        Stream Identifier (31)            │
├──────────────────────────────────────────────┤
│              Frame Payload ...               │
└──────────────────────────────────────────────┘
```

**帧类型**（常用的几种）：

| 类型 | 名称 | 作用 |
|---|---|---|
| 0x0 | DATA | 消息体数据 |
| 0x1 | **HEADERS** | 请求/响应头 |
| 0x2 | PRIORITY | 流优先级 |
| 0x3 | RST_STREAM | 重置流 |
| 0x4 | SETTINGS | 连接配置 |
| 0x5 | PUSH_PROMISE | 服务器推送 |
| 0x6 | PING | 心跳 |
| 0x7 | GOAWAY | 关闭连接 |
| 0x8 | WINDOW_UPDATE | 流量控制 |
| 0x9 | CONTINUATION | 头部续帧 |

**关键字段 `Stream Identifier`（31 位）**：**这就是「多路复用」的实现基础**——每个帧带一个 stream id，接收方按 id 把帧重新组装成不同的请求/响应。

**二进制的好处**：
- 解析快（不用解析文本、不用处理各种换行变体）
- 无歧义（文本协议的大小写、空格、换行都有坑）
- 可以精确控制边界（帧有长度字段）

### 7.5.2 多路复用（HTTP/2 最核心的能力）

```
HTTP/1.1（6 个连接，每个串行）
  conn1: [===请求1===][=请求7=]
  conn2: [===请求2===][=请求8=]
  conn3: [===请求3===]...
  ...

HTTP/2（1 个连接，帧交错）
  一个 TCP 连接上：
  HEADERS(stream1) DATA(stream1) HEADERS(stream2) DATA(stream3)
  DATA(stream2) HEADERS(stream3) DATA(stream1) ...
       ↑ 帧可以任意交错，接收方按 stream id 重组
```

**效果**：
- **一个域名一个连接**（不再需要域名分片）
- **消除了 HTTP 层的队头阻塞**（请求 1 的响应慢，不影响请求 2 的响应返回）
- 减少了 TCP 握手和慢启动的开销（只建一个连接）

### 7.5.3 HPACK 头部压缩

**问题**：HTTP/1.1 的头部是纯文本，而且**大量重复**。一个请求带 1KB 的 Cookie 和 User-Agent，100 个请求就是 100KB 的重复头部。

**HPACK 的三板斧**：

| 机制 | 说明 |
|---|---|
| **静态表** | 预定义 **61 个**常见头部（`:method: GET`、`:status: 200`、`content-type`…），用 1 个字节的索引表示 |
| **动态表** | 连接级别的「已发送头部」字典，第二次发同样的头只需一个索引 |
| **Huffman 编码** | 对字面值做 Huffman 压缩（高频字符用短编码） |

**效果**：头部体积通常能**压缩 85%~95%**。

**一个细节（加分）**：HPACK 的动态表是**有序更新**的——如果某个 HEADERS 帧丢了，后续帧无法解码。但因为 HTTP/2 跑在 TCP 上（有序交付），所以这个问题不会显现。**到了 HTTP/3（QUIC 允许乱序），就必须换成 QPACK**，用「显式同步」来解决。

### 7.5.4 服务器推送（已被废弃）

**设想**：客户端请求 `index.html`，服务器**主动**把 `app.js`、`style.css` 一起推过去，省掉客户端的发现和请求时间。

**为什么废弃**：

| 原因 | 说明 |
|---|---|
| **推送的内容客户端可能已有缓存** | 服务器不知道客户端缓存状态，推了白推，浪费带宽 |
| **无法精确控制优先级** | 推的东西可能抢占了更关键资源的带宽 |
| **实现复杂、收益不稳定** | 实测提升很小，某些场景反而变慢 |
| **Chrome 106（2022）正式移除** | 现在只剩 `103 Early Hints` 作为替代方案 |

**替代方案**：`<link rel="preload">` + **103 Early Hints**（服务器先回一个 103 告诉浏览器「去预加载这些」，再慢慢生成 200）。

> 面试如果问「HTTP/2 服务器推送」，答完机制要**主动补一句「已经废弃了，Chrome 106 移除，现在用 103 Early Hints 替代」**——这能立刻体现你的资料是新的。

### 7.5.5 HTTP/2 的问题：TCP 层队头阻塞

**这是 HTTP/2 最大的坑，也是 HTTP/3 存在的理由。**

```
一个 TCP 连接上有 5 个 stream（5 个资源在并行下载）
    ↓
底层有一个 TCP 段丢失
    ↓
TCP 的「有序交付」要求：后面的段即使收到了，也不能交给应用层
（因为要给应用层一个连续的字节流）
    ↓
HTTP/2 的所有 5 个 stream 全部卡住，等那一个段重传
    ↓
【TCP 层队头阻塞】
```

**更糟的是**：HTTP/1.1 时代开 6 个连接，丢包只卡住 1 个连接（1/6 的资源受影响）。
**HTTP/2 只有 1 个连接，丢包卡住全部资源。**

**所以在丢包率高的网络（弱网、移动网络）上，HTTP/2 可能比 HTTP/1.1 还慢。**

> **这是 HTTP/2 最反直觉的结论，也是最高频的追问。** 一定要记住：**HTTP/2 解决了 HTTP 层的队头阻塞，但引入了（或者说暴露了）TCP 层的队头阻塞。**

## 7.6 HTTP/3 的改进

### 7.6.1 换掉 TCP：QUIC over UDP

```
HTTP/1.1:  HTTP  →  TCP
HTTP/2:    HTTP  →  TCP（多路复用，共享 TCP 的队头阻塞）
HTTP/3:    HTTP  →  QUIC（基于 UDP）  ← 每个 stream 独立
```

**QUIC 在 UDP 之上自己实现了什么**：

| 能力 | 说明 |
|---|---|
| **可靠传输** | 自己的包序号 + ACK + 重传 |
| **按 stream 独立** | **每个 stream 有自己的偏移量**，丢包只影响该 stream |
| **拥塞控制** | 在**用户态**实现，可以快速迭代新算法（如 BBR），不用等内核升级 |
| **TLS 1.3 内置** | 传输握手和加密握手**合并**，首次 1-RTT，复用 0-RTT |
| **连接迁移** | 用 **Connection ID** 标识连接，不用四元组 |
| **头部压缩 QPACK** | 支持乱序解码（解决 HPACK 在 QUIC 上的队头阻塞） |

### 7.6.2 三个关键收益

#### ① 消除队头阻塞

```
QUIC 的 stream 1 丢了一个包
    ↓
stream 2、3、4 的包继续按序交付给应用
    ↓
只有 stream 1 等重传
```

**为什么能做到**：因为 QUIC 给**每个 stream 独立编号和偏移量**，不需要像 TCP 那样维护「全局连续字节流」。

#### ② 握手更快：1-RTT / 0-RTT

```
TCP + TLS 1.2：TCP 1 RTT + TLS 2 RTT = 3 RTT
TCP + TLS 1.3：TCP 1 RTT + TLS 1 RTT = 2 RTT
QUIC（首次）： 1 RTT（传输握手和 TLS 合并）
QUIC（复用）： 0 RTT（用上次的 session ticket，第一个包就带数据）
```

**0-RTT 的安全代价**：0-RTT 的数据**没有前向安全**，而且可能被**重放攻击**（攻击者录下 0-RTT 包重放）。所以 0-RTT **只能用于幂等请求**（GET）。

#### ③ 连接迁移

```
TCP 用「四元组」标识连接：(源IP, 源端口, 目的IP, 目的端口)
    ↓
手机从 WiFi 切到 4G，源 IP 变了
    ↓
四元组变了 → TCP 连接断开 → 要重新握手
```

```
QUIC 用 Connection ID 标识连接
    ↓
IP 变了，但 Connection ID 不变
    ↓
连接继续，不用重新握手（正在下载的视频不卡）
```

**这是移动端体验的质变**——地铁里刷视频不断流。

### 7.6.3 为什么是「换掉 TCP」而不是「改 TCP」

| 原因 | 说明 |
|---|---|
| **TCP 在内核里，升级太慢** | 改 TCP 要等操作系统升级，全球几十亿设备，十年推不完 |
| **中间设备干扰（OSSification）** | 防火墙/NAT/负载均衡对 TCP 的「异常行为」会重置连接，新特性无法穿透 |
| **UDP 是「白纸」** | 在用户态实现，浏览器/App 升级就生效；且 UDP 在中间设备眼里是「普通流量」 |
| **可以快速迭代** | 拥塞控制算法、帧格式都能在用户态快速试错 |

**代价**：
- **UDP 在很多企业网/运营商被限速或封禁** → 需要回退到 TCP（HTTP/2）
- **CPU 开销更高**（用户态协议栈，没有内核优化）
- **调试工具不成熟**（抓包后是加密的 QUIC，Wireshark 支持有限）

## 7.7 队头阻塞的三层含义（本册最核心的辨析）

**这是这道题的分水岭。绝大多数人只会说「HTTP/2 解决了队头阻塞」，这是不完整的。**

| 层 | 现象 | 谁有这个问题 | 谁解决了 |
|---|---|---|---|
| **① 应用层（HTTP）队头阻塞** | 前一个请求的响应没回来，后一个响应必须等着（因为文本协议靠顺序对应） | **HTTP/1.1 管线化** | **HTTP/2 多路复用**（stream id 可乱序） |
| **② 传输层（TCP）队头阻塞** | 一个 TCP 段丢失，所有 stream 的数据都不能交付（因为 TCP 要求有序） | **HTTP/2** | **HTTP/3（QUIC）** |
| **③ 头部压缩层（HPACK）队头阻塞** | 动态表是有序更新的，前面的 HEADERS 帧丢失会导致后续无法解码 | HTTP/2 理论上有（但 TCP 有序，不显现） | **HTTP/3 用 QPACK**（显式同步） |

**一句话总结**：

> **HTTP/2 解决的是 ①，但暴露了 ②。HTTP/3 解决的是 ②（和 ③）。**

**面试时的标准答法**：

> 「队头阻塞有三层。**第一层是 HTTP/1.1 的应用层队头阻塞**——管线化时响应必须按请求顺序返回，因为文本协议没有请求 ID。**第二层是 TCP 层队头阻塞**——HTTP/2 用多路复用解决了第一层，但所有 stream 共享一个 TCP 连接，丢一个段就全卡住，而且比 HTTP/1.1 开 6 个连接更糟。**第三层是头部压缩的队头阻塞**，HTTP/2 的 HPACK 动态表有序更新，HTTP/3 用 QPACK 解决。所以严格说，**HTTP/2 只是把队头阻塞从应用层挪到了传输层**，HTTP/3 才真正解决。」

## 7.8 HTTP/2 下前端实践要怎么改（高频追问）

**这是「知不知道理论」和「做没做过项目」的分界线。**

| HTTP/1.1 时代的优化 | HTTP/2 下该怎么办 | 原因 |
|---|---|---|
| **域名分片**（static1/2/3.com） | **合并成 1~2 个域名** | 多域名 = 多 TCP 连接 = 多握手 + 多份慢启动，反而更慢 |
| **雪碧图 / 图片合并** | **不再需要**（可以拆成独立小图） | 多路复用下多个小图并行下载，且拆分后缓存粒度更细 |
| **Base64 内联小图** | **减少内联** | 内联会阻塞 CSS/HTML 解析，且无法单独缓存 |
| **打包成一个大 bundle** | **代码分割，按需加载** | 不必为了「减少请求数」而合并；拆分后缓存命中率更高 |
| **CSS/JS 全部内联进 HTML** | **只内联关键 CSS**（首屏） | 内联增加 HTML 体积，且破坏缓存 |
| — | **用 `preload` / `prefetch` 控制优先级** | HTTP/2 的流优先级实现效果差，Chrome 已改用 Extensible Priorities |

**但有两件事不变**：

1. **减少请求数仍然有价值**——每个请求都有头部开销（即使 HPACK 压缩了）、都占用 stream、都要参与优先级调度
2. **关键路径仍然要优化**——HTTP/2 不会让你变快，它只是**让并行的成本变低**；真正的速度还是靠 CDN、缓存、减少字节数

> **面试话术**：「HTTP/2 之后，前端优化从『减少请求数』转向『优化关键路径』。域名分片、雪碧图这些 HTTP/1.1 时代的手段应该拆掉，因为多域名会多建连接，反而拖慢。但减少字节数、CDN、缓存这些永远不会过时。」

## 7.9 常见坑

| 坑 | 正确说法 |
|---|---|
| 说「HTTP/2 解决了队头阻塞」 | 只解决了 **HTTP 层**的，**TCP 层**反而更严重 |
| 说「HTTP/2 一个连接比 6 个连接一定快」 | 弱网丢包时可能更慢（TCP 队头阻塞） |
| 说「HTTP/2 支持服务器推送所以更好」 | 服务器推送**已废弃**（Chrome 106 移除） |
| 说「HTTP/3 是 UDP 所以不可靠」 | QUIC 在 UDP 上**自己实现了可靠传输** |
| 说「HTTP/1.1 的管线化提升了性能」 | 实际因为队头阻塞，**浏览器默认关闭** |
| 说「HTTP/2 需要 HTTPS」 | 规范上不要求，但**所有浏览器都只支持 h2 over TLS**（h2c 基本没人用） |
| 说「keep-alive 是 HTTP/1.1 才有的」 | HTTP/1.0 就有 `Connection: keep-alive`，只是 1.1 **默认开启** |
| 说「HTTP/2 的头部压缩能压 90%，所以大小无所谓了」 | 压缩的是**重复**，新内容仍要传；且动态表有大小限制 |
| 说「HTTP/3 一定比 HTTP/2 快」 | 在网络质量好时差别很小；优势在**弱网、移动、切换网络**场景 |
| 说「域名分片在 HTTP/2 下还有用」 | **有害**，多建连接抵消了多路复用收益 |

## 7.10 答题模板

### 30 秒版

> HTTP/1.0 每次请求都新建 TCP 连接；HTTP/1.1 加了持久连接、Host 头、chunked、Range，还试过管线化，但因为响应必须按顺序返回有队头阻塞，实际没人用；HTTP/2 用二进制分帧加多路复用，一个连接并行多个 stream，还加了 HPACK 头部压缩，解决了 HTTP 层的队头阻塞；HTTP/3 换成基于 UDP 的 QUIC，让每个 stream 独立重传，解决了 TCP 层的队头阻塞，顺带有了 1-RTT 握手和连接迁移。

### 2 分钟版（推荐，含队头阻塞三层）

> 我按「每个版本解决什么问题」来讲，这样最容易记住。
>
> **HTTP/1.0 的核心问题是连接成本**：每个请求都新建 TCP 连接，一个 30 个资源的页面就要 30 次握手。而且没有 Host 头，不支持虚拟主机；没有 Range，不能断点续传。
>
> **HTTP/1.1 加了六样东西**：持久连接（keep-alive，默认开启，省掉握手 RTT）、Host 头（虚拟主机）、chunked（流式输出）、Range + 206（断点续传）、更强的缓存头（Cache-Control、ETag、Vary）、更多方法。还试了**管线化**，理论上可以连续发多个请求省 RTT，但 HTTP/1.1 是文本协议、没有请求 ID，**响应必须按顺序返回**，一个慢请求就卡住后面全部——这就是应用层的队头阻塞，加上代理兼容性差，浏览器实际默认关闭了。
>
> **HTTP/2 的突破是二进制分帧**：把报文切成带 stream id 的帧，一个 TCP 连接上多个 stream 可以任意交错，接收方按 id 重组。这就**消除了 HTTP 层队头阻塞**。再加 HPACK 头部压缩，静态表 61 项加动态表加 Huffman，头部能压 85% 以上。服务器推送曾经是亮点，但**已经废弃了**，Chrome 106 移除，现在用 103 Early Hints 替代。
>
> **但 HTTP/2 有个大坑**：所有 stream 共享一个 TCP 连接，**丢一个 TCP 段，所有 stream 都卡住**，因为 TCP 要求有序交付。这比 HTTP/1.1 开 6 个连接还糟——那时候丢包只卡 1/6 的资源。所以在弱网下 HTTP/2 可能更慢。
>
> **HTTP/3 就是来解决这个的**：换掉 TCP，用基于 UDP 的 QUIC。QUIC 在用户态自己实现可靠传输，**每个 stream 独立编号和重传**，丢包只影响那一个 stream。顺带拿到三个好处：握手合并成 1-RTT、复用可以 0-RTT、用 Connection ID 做**连接迁移**——手机从 WiFi 切 4G 连接不断。头部压缩也换成 QPACK，支持乱序解码。
>
> 为什么是换掉 TCP 而不是改 TCP？因为 TCP 在内核里，升级要等操作系统，全球几十亿设备推不动；而且中间设备会把 TCP 的异常行为当成攻击重置掉。UDP 是白纸，浏览器升级就生效。
>
> 最后补充一个工程影响：HTTP/2 之后，域名分片、雪碧图、Base64 内联这些 HTTP/1.1 时代的优化应该拆掉，因为多域名会多建连接，反而拖慢。优化重心从「减少请求数」转向「优化关键路径」。

### 追问表

| 追问 | 回答要点 |
|---|---|
| 队头阻塞有几层？ | 三层：HTTP 应用层（管线化）、TCP 传输层、HPACK 头部压缩层 |
| HTTP/2 解决队头阻塞了吗 | 只解决 HTTP 层，TCP 层反而更严重 |
| 为什么 HTTP/1.1 的管线化没人用 | 响应必须按顺序返回，慢请求卡全部；代理兼容差 |

| HPACK 怎么压缩 | 静态表 61 项 + 动态表 + Huffman |
| 服务器推送为什么废弃 | 不知道客户端缓存、抢占带宽、收益不稳，Chrome 106 移除 |

| HTTP/2 必须 HTTPS 吗 | 规范不要求，但浏览器只支持 h2 over TLS |
| HTTP/2 下还要域名分片吗 | 不要，有害；多域名会多建连接 |
| HTTP/2 下雪碧图还要吗 | 不需要，多路复用下多个小图并行更优 |
| HTTP/3 一定更快吗 | 弱网/移动/切网场景明显；网络好时差别小 |

## 7.11 速记卡

```
主线
  所有版本都在解决「一个连接上怎么高效并发传多个资源」

1.0 → 1.1 的六项
  keep-alive（默认开，省握手 RTT）
  Host 头（虚拟主机）
  chunked（流式输出）
  Range + 206（断点续传）
  Cache-Control / ETag / Vary（缓存增强）
  新方法 PUT/DELETE/OPTIONS
  + 管线化（失败：响应必须按序 → 应用层队头阻塞）

1.1 → 2
  二进制分帧（9 字节头 + stream id）← 一切的基础
  多路复用（一个连接多 stream 交错）
  HPACK（静态表 61 + 动态表 + Huffman，压 85%+）
  服务器推送（已废弃，Chrome 106 移除，换 103 Early Hints）
  问题：TCP 层队头阻塞（丢一段卡所有 stream）

2 → 3
  换 QUIC（UDP）：stream 独立重传 + 用户态拥塞控制 + TLS1.3 内置
  握手：1-RTT / 复用 0-RTT（0-RTT 无前向安全、可重放，只用于幂等）
  连接迁移：Connection ID 而非四元组
  头部压缩 QPACK（支持乱序）
  为什么不改 TCP：内核升级慢 + 中间设备 OSSification

队头阻塞三层（核心）
  ① HTTP 应用层：1.1 管线化，响应按序 → HTTP/2 解决
  ② TCP 传输层：丢一段卡所有 stream → HTTP/3 解决
  ③ HPACK 动态表有序 → QPACK 解决
  ★ HTTP/2 只是把队头阻塞从应用层挪到传输层

前端实践变化
  拆掉：域名分片、雪碧图、Base64 内联、大 bundle
  保留：减少字节、CDN、缓存、关键路径优先
  新增：preload / prefetch / 103 Early Hints
```
