## 7.1 一句话结论

**HTTP/1.0 每个请求新建一条 TCP 连接；HTTP/1.1 默认持久连接并引入管线化，但响应必须按序返回，管线化未落地；HTTP/2 用二进制分帧 + 多路复用消除 HTTP 层队头阻塞，所有 stream 共享一条 TCP 连接，队头阻塞下沉到传输层；HTTP/3 改用基于 UDP 的 QUIC，每个 stream 独立重传。**

主线：**如何在一条连接上并发传输多个资源。**

## 7.2 演进总表（必背）

| 维度 | HTTP/1.0（1996） | HTTP/1.1（1997） | HTTP/2（2015） | HTTP/3（2022） |
|---|---|---|---|---|
| **传输层** | TCP | TCP | TCP | **UDP（QUIC）** |
| **连接** | 每请求一条连接 | **持久连接（keep-alive）默认开** | 单连接多路复用 | 单连接多路复用 |
| **并发方式** | 多开连接（单域名约 6 条） | 多开连接 + 管线化（未落地） | **一条连接上的多 stream** | 一条连接上的多 stream |
| **报文格式** | 文本 | 文本 | **二进制分帧** | 二进制分帧 |
| **头部压缩** | ❌ | ❌ | **HPACK** | **QPACK** |
| **队头阻塞** | 无 HTTP 层（受单域名连接数上限约束） | **HTTP 层有**（管线化） | **TCP 层有** | **基本消除** |
| **服务器推送** | ❌ | ❌ | ✅（**已废弃**） | ❌ |
| **握手** | 每条连接 TCP 1 RTT（+ TLS） | 同左 | 一条连接 TCP 1 RTT + TLS（ALPN 协商 `h2`） | QUIC 与 TLS 1.3 合并；复用可 0-RTT |
| **连接迁移** | ❌ | ❌ | ❌ | ✅（Connection ID） |
| **Host 头** | ❌（不支持虚拟主机） | ✅ | ✅（`:authority` 伪头） | ✅ |
| **分块传输** | ❌ | ✅（chunked） | — | — |
| **断点续传** | ❌ | ✅（Range / 206） | ✅ | ✅ |

## 7.3 HTTP/1.0 的问题

| 问题 | 后果 |
|---|---|
| **每个请求新建 TCP 连接** | 每个资源多一次 TCP（及 TLS）握手，30 个资源就是 30 次 |
| **没有 Host 头** | 一个 IP 只能对应一个站点，不支持虚拟主机 |
| **不支持 Range** | 不能断点续传，视频不能拖进度 |
| **缓存控制弱** | 只有 `Expires`（绝对时间，受客户端时钟影响）和 `If-Modified-Since`（秒级精度） |
| **不支持分块传输** | 服务端必须先知道 `Content-Length`，无法边生成边发 |

## 7.4 HTTP/1.1 的改进（答案）

### 7.4.1 六项核心改进

| 改进 | 说明 | 解决了什么 |
|---|---|---|
| **① 持久连接（keep-alive）** | 默认不关闭 TCP 连接，后续请求复用 | 省掉重复握手 |
| **② 管线化（pipelining）** | 连续发多个请求，不等前一个响应 | 理论省 RTT，实际失败（见 7.4.2） |
| **③ Host 头** | 请求里带域名 | 虚拟主机：一台服务器跑多个站点 |
| **④ 分块传输（chunked）** | `Transfer-Encoding: chunked`，边生成边发 | 流式输出（SSR、大文件） |
| **⑤ Range 请求** | 请求部分内容，返回 **206** | 断点续传、视频拖动 |
| **⑥ 缓存增强** | `Cache-Control`、`ETag`、`Vary` | 更精细的缓存控制 |
| （⑦ 新增方法） | PUT、DELETE、OPTIONS、TRACE、CONNECT | RESTful |
| （⑧ 100-continue） | 大文件上传前先问能否接收 | 避免白传 body |

### 7.4.2 管线化失败的原因

```
普通 keep-alive：请求1 → 响应1 → 请求2 → 响应2（串行）
管线化：        请求1 请求2 请求3 连续发出 → 响应1 响应2 响应3 按序返回
```

HTTP/1.1 是**文本协议**，没有请求 ID，响应只能靠顺序与请求对应，因此规定**响应必须按请求顺序返回**。响应 1 迟迟不返回时，已生成的响应 2、3 必须排队，客户端收不到任何字节——这是应用层队头阻塞。

浏览器实际关闭管线化的原因：

| 原因 | 说明 |
|---|---|
| 队头阻塞未解决 | 一个慢响应卡住后面全部响应 |
| 中间设备兼容性差 | 代理/服务器实现不一致 |
| 失败后无法对应 | 某个请求失败，后续响应与请求无法重新匹配 |

### 7.4.3 keep-alive 的实际限制

浏览器对同一域名最多开 6 条并发 TCP 连接（Chrome/Firefox 的实现约定，非协议规定）。30 个资源要在 6 条连接上串行分批，慢资源会占住所在连接；HTTP/1.1 时代因此用**域名分片**（`a.com`、`b.com`、`c.com` 各 6 条）扩到 18 并发。HTTP/2 下单连接即可并发，域名分片的取舍见 7.8。

## 7.5 HTTP/2 的核心改进

### 7.5.1 二进制分帧

HTTP/1.1 报文是文本（`GET /path HTTP/1.1\r\nHost: ...`）；HTTP/2 把一切切成帧，每帧统一 9 字节头：

```
┌──────────────────────────────────────────────┐
│ Length (24)  │ Type (8) │ Flags (8)          │
├──────────────────────────────────────────────┤
│ R │        Stream Identifier (31)            │
├──────────────────────────────────────────────┤
│              Frame Payload ...               │
└──────────────────────────────────────────────┘
```

常用帧类型：

| 类型 | 名称 | 作用 |
|---|---|---|
| 0x0 | DATA | 消息体数据 |
| 0x1 | **HEADERS** | 请求/响应头 |
| 0x2 | PRIORITY | 流优先级 |
| 0x3 | RST_STREAM | 重置流 |
| 0x4 | SETTINGS | 连接配置 |
| 0x5 | PUSH_PROMISE | 服务器推送 |
| 0x6 | PING | 心跳 |
| 0x7 | GOAWAY | 关闭连接 |
| 0x8 | WINDOW_UPDATE | 流量控制 |
| 0x9 | CONTINUATION | 头部续帧 |

**`Stream Identifier`（31 位）是多路复用的实现基础**：每个帧带 stream id，接收方按 id 把帧重组成各自的请求/响应；客户端发起的 stream id 为奇数。

二进制的好处：解析不必处理文本的换行与大小写变体；帧头有长度字段，边界明确。

### 7.5.2 多路复用

```
HTTP/1.1（6 条连接，每条串行）
  conn1: [=请求1=][=请求7=]   conn2: [=请求2=][=请求8=] ...

HTTP/2（1 条连接，帧交错）
  HEADERS(1) DATA(1) HEADERS(2) DATA(3) DATA(2) HEADERS(3) ...
  ↑ 帧可任意交错，接收方按 stream id 重组
```

效果：一条连接承载全部请求，省掉重复握手与慢启动；**HTTP 层队头阻塞消失**——慢请求不再阻塞其他 stream 的响应。

用 node `http2` 起 h2c 服务可复现：三条请求复用同一连接（同一客户端端口），stream 1/3/5 并发，stream 1 延迟 300 ms 期间 stream 3、5 已先返回。

### 7.5.3 HPACK 头部压缩

HTTP/1.1 的头部是纯文本，同一站点下每个请求都重复携带 Cookie、User-Agent 等字段，开销随请求数线性增长。

| 机制 | 说明 |
|---|---|
| **静态表** | 预定义 **61** 个常见头部（`:method: GET`、`:status: 200`、`content-type`…），用 1 字节索引表示 |
| **动态表** | 连接级的「已发送头部」字典，重复头部只发索引 |
| **Huffman 编码** | 对字面值做 Huffman 压缩 |

压缩率取决于头部重复度：重复部分退化为索引，新出现的头部仍要传字面值。

动态表按序更新，某个 HEADERS 帧丢失会导致后续帧无法解码。HTTP/2 跑在 TCP 上（有序交付），该问题不显现；**QUIC 允许乱序，HTTP/3 因此换成 QPACK**，用显式同步解决。

### 7.5.4 服务器推送（已被废弃）

设想：客户端请求 `index.html`，服务器主动把 `app.js`、`style.css` 推过去，省掉客户端的发现与请求。

| 废弃原因 | 说明 |
|---|---|
| 不知道客户端缓存状态 | 推了已有资源，白占带宽 |
| 无法精确控制优先级 | 推送内容可能抢占关键资源的带宽 |
| 实现复杂、收益不稳 | 提升有限，部分场景反而更慢 |
| **Chrome 106（2022）默认关闭** | 现由 `103 Early Hints` 替代 |

替代方案：`<link rel="preload">` + 103 Early Hints（先回 103 告知要预加载的资源，再返回 200）。

### 7.5.5 HTTP/2 的问题：TCP 层队头阻塞

```
5 个 stream 共享一条 TCP 连接
  → 一个 TCP 段丢失
  → TCP 要求有序交付：后到的段也不能上交应用层
  → 5 个 stream 全部等待该段重传
```

对比 HTTP/1.0/1.1：丢包只卡住其中一条连接（6 条中的 1 条）；HTTP/2 只有一条连接，丢包卡住全部 stream，高丢包网络下可能比 HTTP/1.1 更慢。

## 7.6 HTTP/3 的改进

### 7.6.1 换掉 TCP：QUIC over UDP

```
HTTP/1.1、HTTP/2:  HTTP → TCP
HTTP/3:            HTTP → QUIC（基于 UDP），每个 stream 独立
```

QUIC 在 UDP 之上自行实现：

| 能力 | 说明 |
|---|---|
| **可靠传输** | 自己的包序号 + ACK + 重传 |
| **按 stream 独立** | 每个 stream 有独立偏移量，丢包只阻塞该 stream |
| **拥塞控制** | 用户态实现，换算法不必等内核升级（如 BBR） |
| **TLS 1.3 内置** | 传输握手与加密握手合并；复用时可 0-RTT |
| **连接迁移** | 用 **Connection ID** 标识连接，不用四元组 |
| **头部压缩 QPACK** | 支持乱序解码，解决 HPACK 在 QUIC 上的阻塞 |

### 7.6.2 三个关键收益

#### ① 消除队头阻塞

QUIC 给每个 stream 独立编号与偏移量，不维护全局连续字节流：stream 1 丢包时，stream 2、3、4 的数据照常交付，只有 stream 1 等待重传。

#### ② 握手合并与 0-RTT

TCP + TLS 是两次串行握手（先建连接，再协商加密）；QUIC 把传输握手与 TLS 1.3 合并，首次连接不必等 TCP 建连完成后再做 TLS。会话复用时可用 0-RTT：首个包就携带应用数据。

0-RTT 的代价：这批数据**没有前向安全**，且可被**重放**，因此只用于幂等请求（GET）。

#### ③ 连接迁移

TCP 用四元组（源 IP、源端口、目的 IP、目的端口）标识连接：手机从 WiFi 切到 4G，源 IP 变化即连接断开，需要重新握手。QUIC 用 Connection ID 标识连接，IP 变化后连接继续。

### 7.6.3 为什么是「换掉 TCP」而不是「改 TCP」

| 原因 | 说明 |
|---|---|
| **TCP 在内核里** | 改 TCP 要等操作系统升级，存量设备推进极慢 |
| **中间设备干扰（ossification）** | 防火墙/NAT/负载均衡会把 TCP 的异常行为当作攻击重置 |
| **UDP 的中间设备视角** | UDP 被视为普通流量，新协议可在用户态部署 |
| **可快速迭代** | 拥塞控制、帧格式都能在用户态试错 |

代价：企业网/运营商可能对 UDP 限速或封禁，需要回退 HTTP/2；用户态协议栈 CPU 开销更高；抓包后是加密的 QUIC，调试工具支持有限。

## 7.7 队头阻塞的三层含义（本册最核心的辨析）

| 层 | 现象 | 谁有这个问题 | 谁解决了 |
|---|---|---|---|
| **① 应用层（HTTP）队头阻塞** | 前一个响应没回来，后续响应必须等待（文本协议靠顺序对应） | **HTTP/1.1 管线化** | **HTTP/2 多路复用**（stream id 可乱序） |
| **② 传输层（TCP）队头阻塞** | 一个 TCP 段丢失，所有 stream 的数据都无法交付 | **HTTP/2** | **HTTP/3（QUIC）** |
| **③ 头部压缩（HPACK）队头阻塞** | 动态表按序更新，前面的 HEADERS 帧丢失会导致后续无法解码 | HTTP/2 理论上有（TCP 有序，不显现） | **HTTP/3 的 QPACK**（显式同步） |

**HTTP/2 解决 ①，同时暴露 ②；HTTP/3 解决 ② 和 ③。**

## 7.8 HTTP/2 下前端实践要怎么改（高频追问）

| HTTP/1.1 时代的优化 | HTTP/2 下怎么做 | 原因 |
|---|---|---|
| **域名分片**（static1/2/3.com） | **合并成 1~2 个域名** | 多域名 = 多条 TCP 连接 = 多次握手与慢启动 |
| **雪碧图 / 图片合并** | **拆成独立小图** | 多路复用可并行下载，拆分后缓存粒度更细 |
| **Base64 内联小图** | **减少内联** | 内联阻塞 CSS/HTML 解析，且无法单独缓存 |
| **合并成大 bundle** | **代码分割、按需加载** | 不必为减少请求数而合并，拆分后缓存命中率更高 |
| **CSS/JS 全量内联进 HTML** | **只内联关键 CSS** | 内联增大 HTML 体积且破坏缓存 |
| — | **用 `preload` / `prefetch` 控制优先级** | RFC 7540 的流优先级实现不一致，已被 RFC 9218 Extensible Priorities 取代 |

仍不变：减少请求数仍有价值（每个请求都有头部开销、占用 stream、参与优先级调度）；关键路径仍需优化——HTTP/2 降低的是并行成本，速度仍取决于 CDN、缓存与字节数。

## 7.9 常见坑

| 坑 | 正确说法 |
|---|---|
| 「HTTP/3 是 UDP 所以不可靠」 | QUIC 在 UDP 上自己实现了可靠传输与重传 |
| 「HTTP/2 必须 HTTPS」 | 规范允许明文 h2c（node `http2` 可直连），但浏览器只走 TLS 并用 ALPN 协商 `h2`；协商不到时 TLS 握手直接失败（`ERR_SSL_NO_APPLICATION_PROTOCOL`） |
| 「keep-alive 是 HTTP/1.1 才有的」 | HTTP/1.0 已有 `Connection: keep-alive` 扩展，1.1 改为默认开启 |
| 「HPACK 能压 90%，头部大小无所谓」 | 压缩的是重复部分，新头部仍要传字面值；动态表有大小上限 |
| 「HTTP/3 一定比 HTTP/2 快」 | 优势集中在弱网、移动、切网场景；网络质量好时差异很小 |

## 7.10 答题模板

### 30 秒版

- **1.0**：每请求一条连接，缺 Host / Range / chunked。
- **1.1**：持久连接 + Host + chunked + Range + 缓存头；管线化因响应必须按序返回而未落地。
- **2**：二进制分帧 + stream 多路复用 + HPACK，消除 HTTP 层队头阻塞。
- **3**：QUIC over UDP，stream 独立重传，QPACK 支持乱序解码。

### 结构化提纲

按「版本 → 它解决的瓶颈 → 新引入的问题」组织，每段只给一条结论：1.0 连接成本 → 1.1 连接复用与管线化失败 → 2 分帧与多路复用、残留 TCP 层阻塞 → 3 独立 stream 与连接迁移。结尾用 7.7 的三层队头阻塞收束，再用 7.8 说明前端优化重心的转移。

### 追问表

| 追问 | 回答要点 |
|---|---|
| 队头阻塞有几层？ | 三层：HTTP 应用层、TCP 传输层、HPACK 头部压缩层（见 7.7） |
| 为什么管线化没人用？ | 文本协议没有请求 ID，响应必须按序返回，慢响应卡住全部 |
| HTTP/2 多路复用怎么实现？ | 二进制分帧 + stream id，帧可交错，接收方按 id 重组 |
| HTTP/3 为什么用 UDP？ | 绕开 TCP 层队头阻塞；TCP 在内核与中间设备中难演进 |
| 0-RTT 有什么风险？ | 无前向安全、可被重放，只用于幂等请求 |
| 连接迁移怎么实现？ | 用 Connection ID 而非四元组标识连接 |

## 7.11 速记卡

```
1.0 → 1.1
  keep-alive（默认开，省握手）
  Host（虚拟主机） / chunked（流式） / Range + 206（续传）
  Cache-Control / ETag / Vary
  新方法 PUT/DELETE/OPTIONS
  管线化：响应按序 → 应用层队头阻塞 → 浏览器关闭

1.1 → 2
  二进制分帧（9 字节头 + stream id）
  多路复用（一条连接多 stream 交错）
  HPACK（静态表 61 + 动态表 + Huffman）
  服务器推送：已废弃（Chrome 106），改用 103 Early Hints
  残留问题：TCP 层队头阻塞

2 → 3
  QUIC over UDP：stream 独立重传 + 用户态拥塞控制 + TLS 1.3 内置
  0-RTT：无前向安全、可重放，只用于幂等请求
  连接迁移：Connection ID
  QPACK：支持乱序解码
  不改 TCP 的原因：内核升级慢 + 中间设备 ossification

队头阻塞三层
  ① HTTP 应用层：1.1 管线化 → 2 解决
  ② TCP 传输层：丢一段卡全部 stream → 3 解决
  ③ HPACK 动态表按序 → QPACK 解决

前端实践
  拆掉：域名分片、雪碧图、Base64 内联、大 bundle
  保留：减少字节、CDN、缓存、关键路径
  新增：preload / prefetch / 103 Early Hints
```
