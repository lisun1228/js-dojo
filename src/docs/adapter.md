# 适配器模式（Adapter Pattern）
## 核心定义
> **将一个类/对象的接口，转换成客户期望的另一个接口，让原本因为接口不兼容而不能一起工作的类可以协同工作。**

一句话记忆：**做一层「翻译转换层」，不改原有代码，把旧接口包装成新接口。**

> 关键词：**接口转换**。不是增强功能（装饰器），不是控制访问（代理），**只做接口适配**。

## 角色
1. **目标接口 Target**：客户希望使用的接口（我们想要的统一格式）
2. **被适配者 Adaptee**：原有旧对象/旧接口，接口格式不匹配
3. **适配器 Adapter**：包装 Adaptee，实现 Target 接口，内部调用旧接口，做参数转换

## 适用场景
1. 引入第三方库，第三方方法参数、返回值格式和项目规范不一致，写适配器包装一层
2. 老项目旧接口，不能修改源码，但需要对接新业务
3. 统一多个不同来源接口的返回格式

## JS Demo（对象适配器，前端最常用）
> 场景：老接口返回 `{code:0, msg:'ok', data:{userName:'张三'}}`
> 新项目统一规范要求：`{success:true, message:'ok', result:{name:'张三'}}`
> 不能修改老接口源码，写适配器做字段映射

```js
// 被适配者 Adaptee：旧接口（不能改动）
const oldApi = {
  request() {
    return {
      code: 0,
      msg: 'ok',
      data: {
        userName: '张三'
      }
    }
  }
}

// 适配器 Adapter：包装旧接口，转换成目标格式
const apiAdapter = {
  fetch() {
    const oldRes = oldApi.request()
    // 字段映射，接口转换
    return {
      success: oldRes.code === 0,
      message: oldRes.msg,
      result: {
        name: oldRes.data.userName
      }
    }
  }
}

// 业务代码（客户），只使用目标接口 fetch()
const res = apiAdapter.fetch()
console.log(res)
// { success: true, message: 'ok', result: { name: '张三' } }
```

## Class版本（类适配器，了解即可，JS很少用）
```js
// 目标接口 Target
class Target {
  getInfo() {}
}

// 被适配者
class OldService {
  oldGet() {
    return { userName: '李四' }
  }
}

// 适配器，继承旧服务，实现目标接口
class Adapter extends OldService {
  getInfo() {
    const oldData = this.oldGet()
    return { name: oldData.userName }
  }
}

const adapter = new Adapter()
console.log(adapter.getInfo())
```

## 前端真实业务例子
1. 后端多个微服务返回数据结构不一致，统一封装适配器，前端业务层拿到统一结构
2. 第三方SDK方法名和参数和项目规范不同，适配器包装一层
3. 兼容不同浏览器API，把差异化API统一成一套调用方式

# 🔥面试重点区分（高频对比题）
### 适配器 vs 装饰器模式
- **适配器：转换接口**。改变对外暴露的方法/参数格式，**接口变了**。目的：兼容。
- **装饰器：增强功能**。对外接口保持完全不变，**接口原样保留**，在前后加逻辑。目的：增强。

> 举例：
> 适配器：插头是三孔，插座两孔 → 转换头（接口变了）
> 装饰器：给杯子套保温套，杯子还是原来杯子，喝水接口不变，多了保温能力。

### 适配器 vs 代理模式
- **适配器**：转换接口，为了兼容旧代码
- **代理**：接口不变，控制访问、预处理、缓存，不改变接口

### 适配器 vs 策略模式
- **适配器**：包装已有对象，**改接口**，解决兼容问题
- **策略**：多个平等算法，**接口一致**，动态切换算法

## ✅优点
1. 复用已有旧代码，**不用修改原有对象源码**，符合开闭原则
2. 隔离新旧代码，业务层不用关心底层数据差异
3. 统一对外接口，简化上层业务代码

## ❌缺点
- 增加一层包装，多了代码复杂度；过多适配器会难以维护
- 额外一层调用，轻微性能损耗（前端基本感知不到）

## 面试口述总结
适配器模式是创建一个中间适配层，包装原有接口，**转换接口格式**，让接口不兼容的对象可以一起工作；适配器只做转换，不修改原有代码。它和装饰器最大区别：适配器改变接口，装饰器保持接口不变，只增强能力。
