# 深度优先，而非体量优先

面对任何新需求，目标永远是**更深入的版本**，而不是**更大的版本**。

- 更深：同一问题上多一层因果、多一条边界、多一个可验证的证据，范围不变
- 更大：多一个模块、多一个分类、多一组配置、多一份文档，范围膨胀

判断标准只有一条：**这次改动让"原来那件事"更可信，还是让"要做的事"变多了？**

## 触发时机

用户提出新需求、新题目、新教程、新功能时，**先按下面的流程改题，再动手实现**。已经在实现中的追加需求同样适用。

仅当需求是机械转述（改错别字、调格式、执行一条明确命令）时可跳过，跳过不必解释。

## 改题前必须先回答的四问

四问的答案要落到本项目的具体对象上（文件名、`categories` 条目、`DemoPanel`、真实命令），不允许停在"专家会考虑周全性"这类空话。

### 1. 该领域的顶尖专家会做哪些我没有要求的事情

找出用户没写、但做了才会被认可为专业的动作。典型来源：验收标准、失败模式、边界与不适用场景、可复现的证据。答案要能直接转成待办项，不能只是"会更严谨"。

### 2. 他们会从哪些最原始的素材入手，而不是我已经整理好的素材

用户给的往往是加工过的结论（一句口号、一份清单、一个已定型的方案）。要倒推更上游的一手材料：

- 项目内：真实代码、既有 rules 的写法与颗粒度、`src/router/tutorials.ts` 这类唯一数据源、历史提交
- 项目外：领域原始文献、规范原文、真实失败记录与返工原因

如果找不到一手素材，就明确写出"缺什么素材、拿不到会有什么风险"，不要用猜测填空。

### 3. 他们会使用的具体方法和工具

写出可执行的动作，而不是方法论名词。例如：以 diff 形式给出改题前后对照、用一张反例表区分深与浅、为每条要求配一个可判定的验收命令（`npm run lint` / `npm run build` / 实际点击 Demo）、用一次真实试跑验证规则会不会空转。

### 4. 除了你我之外，还有什么可以证明结果是正确的

必须给出**第三方可复核**的证据，优先级从高到低：

1. 可自动执行的检查（lint、format、build、类型检查、测试）
2. 可复现的产物（diff、渲染截图、控制台输出）
3. 与他人的一致性与可复现性（同一题目在冷启动会话/另一模型下产出一致结论）
4. 领域内的公认标准或原始文献

只有"我说它对"不构成证据。

## 改题流程

1. 用一句话写出**原题的真实意图**（去掉实现细节后剩下的那句）
2. 回答四问，每问 2-5 条，必须点名具体文件或具体命令
3. 重写题目，输出 diff 形式的对照：`原题 → 新题`，并说明每处改动对应四问中的哪一问
4. 给新题补上：范围边界（明确不做什么）、验收标准（可执行）、证据要求
5. 自检：新题的字数与条目数不应显著增长；如果变长了，检查是否把"更深"写成了"更多"，删掉新增的范围

## 反例对照

| 更大的版本（拒绝）     | 更深入的版本（采用）                            |
| ---------------------- | ----------------------------------------------- |
| 新增一个分类和三篇教程 | 同一篇教程补上反例、边界和一条可点击验证的 Demo |
| 规则里再列十条"要严谨" | 把每条要求改写成能判定真假的验收项              |
| 加一份设计说明文档     | 给出改题前后的 diff，并说明每处改动由哪一问驱动 |
| 让方案覆盖更多场景     | 明确不适用场景，并说明为什么在这里不适用        |
| 声称"已符合专家水准"   | 给出可复现的检查命令、产物或第三方对照结果      |

## 输出约束

- 回答四问后再改题，不要一边答一边写代码
- 改题结论要显式说"不做什么"，避免用扩范围换取"完整感"
- 每条验收标准必须能在本仓库里执行或复现，否则降级为待确认问题
- 不为了显得深入而增加文件；能改现有文件的，不新建
